# 테스트 전략

pokeHelper 의 테스트 설계를 표준 QA 용어로 정리한 문서다.

**이 문서는 계획이 아니라 기록이다.** 아래 내용은 모두 `backend/tests/` 에 실제로
존재하는 테스트를 읽고 매핑한 것이고, 각 항목에 파일과 줄 번호를 붙였다.
미구현·미측정 항목은 숨기지 않고 그렇게 표시했다.

- 측정 시점: **2026-11-18**
- 테스트 함수: **588개** (`pytest.mark.parametrize` 전개 전 기준)
  - 단위 426 / 통합 128 / 복구 리허설 33 / 시스템 1
- 마지막으로 기록된 실행 (파라미터화 전개 후, 2026-11-18)
  - 기본 실행: **665 passed** (리허설 33 deselected)
  - 복구 리허설: **33 passed** — `pytest -m rehearsal`. 전용 컨테이너가 필요해
    기본 실행에서 제외돼 있다 ([ADR-014](adr/014-restore-rehearsal.md))

## 1. 테스트 레벨

이 프로젝트의 레벨 구분은 "무엇을 격리했는가"로 정의한다.

| 레벨 | 위치 | 수 | 격리 범위 | 외부 의존 |
|---|---|---|---|---|
| **단위** | `tests/unit/` | 426 | 순수 함수 1개 ~ 모듈 1개 | 도메인 없음 / 수집 테스트 더블 |
| **통합** | `tests/integration/` | 128 | 라우터↔스키마↔도메인, 서비스↔실제 DB, **DB 계정 권한**, **지표 노출·경보 참조** | Postgres |
| **복구 리허설** | `tests/rehearsal/` | 33 | 백업·복구·계정 스크립트 ↔ 전용 Postgres (DROP·복구 포함) | Postgres (전용 컨테이너) |
| **시스템** | `tests/test_health.py` | 1 | 앱 기동 + HTTP 계약 | 없음 |
| **E2E** | — | **0** | — | — |

### 1-1. 단위 — 두 종류로 갈린다

**(가) 도메인 (`tests/unit/domain/`, 374) — 모킹이 없는 것이 설계의 결과다**

`app/domain/` 은 DB·HTTP·LLM·환경변수를 import 하지 않는다 (`CLAUDE.md` 1-5).
입력은 dataclass, 출력은 dataclass, 순수 함수만이다.

**그 결과 도메인 단위 테스트에 mock·stub·patch 가 하나도 없다.** 테스트 더블이
없으므로 "모킹이 실제 동작과 달라서 통과했다"는 실패 양식이 구조적으로 발생하지
않는다. 도메인 계층의 의존성 0 규칙은 아키텍처 취향이 아니라 **테스트 가능성을
위한 결정**이었다.

**(나) 수집 어댑터 (`tests/unit/ingestion/`, 31) — 더블이 있고, 그 한계를 적는다**

`app/ingestion/` 은 성질상 네트워크와 시계에 의존한다. 그래서 여기서는 테스트
더블을 쓴다. **(가)의 "더블이 없다"는 주장이 여기에는 적용되지 않는다.**

| 더블 | 대체 대상 | 종류 |
|---|---|---|
| `httpx.MockTransport` + `Recorder` | HTTP 전송계층 | 스텁 + 스파이(요청 경로 기록) |
| `FakeClock` | `time.monotonic` | 페이크 |
| `RecordingSleep` | `asyncio.sleep` | 스파이(대기 시간 기록) |

더블을 쓰는 대가가 있다. **실제 API 응답이 우리 가정과 다르면 테스트는 통과하고
운영만 깨진다.** 샘플 응답이 실측이 아니라 파서가 읽는 필드에서 역산해 만든
것이기 때문이다 — 파서와 샘플이 같은 가정에서 나왔으므로 가정 자체가 틀렸으면
둘 다 같이 틀린다. 이 한계는
[`tests/fixtures/championsbattledata/README.md`](../backend/tests/fixtures/championsbattledata/README.md)
에 표로 명시했고, 실호출 1회로 승격하는 절차도 거기 적어뒀다 (아직 하지 않았다).

시계를 더블로 바꾼 효과는 측정됐다. 같은 테스트 20건이 **실제 대기 31.78초 →
0.62초**다. 느린 테스트는 결국 아무도 돌리지 않으므로, 이건 편의가 아니라
테스트가 유지되기 위한 조건이다.

### 1-2. 통합 — 두 종류를 구분한다

**(가) API 계약** — `tests/integration/test_calc_ev_tune.py` (46)

`TestClient` 로 `POST /api/v1/calc/ev-tune` 를 호출한다. 검증 대상은 **계산 정확도가
아니라 스키마↔도메인 변환과 계약**이다. 계산 자체는 단위 테스트가 맡는다
(파일 독스트링에 그렇게 명시돼 있다). 레벨별 책임을 중복시키지 않는다.

- `TestOpenApi:300` — 생성된 OpenAPI 스키마 자체를 검증한다. 프론트가 여기서 타입을
  자동 생성하므로(`CLAUDE.md` 6장) 스키마가 깨지면 타입이 조용히 틀린다.
- `TestInputBounds:324`, `TestValidation:259` — 입력 경계와 거부 응답
- `TestInternalGuards:312` — 도메인 예외가 500 으로 새지 않는지

**(나) DB·파이프라인** — `test_db_schema.py` (19), `test_ingest.py` (17), `test_scheduler_commands.py` (11)

**실제 Postgres 16 을 쓴다. SQLite 로 대체하지 않는다.**

```
tests/integration/test_db_schema.py:3
  이 스키마의 핵심 장치가 부분 유니크 인덱스(WHERE is_active)와 CHECK 제약인데,
  둘 다 방언에 따라 동작이 다르거나 아예 없다. 가짜 DB 에서 통과하는 테스트는
  이 스키마를 지켜주지 못한다.
```

CI 도 같은 선택을 한다 — GitHub Actions 에 `postgres:16-alpine` 서비스를 띄우고
`alembic upgrade head` 와 시드 적재를 거친 뒤 pytest 를 돌린다
(`.github/workflows/ci.yml`). 마이그레이션을 빠뜨리면 이 단계에서 깨진다.

ETL 통합 테스트는 **외부 API 를 호출하지 않는다.** 수집기가 `StatsSource` 인터페이스로
분리돼 있어 가짜 출처를 주입한다. 네트워크에 의존하는 테스트는 불안정하고, 출처에
요청을 보내는 것도 피해야 한다 (`CLAUDE.md` 8-2).

### 1-3. 시스템 — 1건뿐이다

`tests/test_health.py` 가 FastAPI 앱을 띄워 `/health` 응답 본문을 단정한다.
이게 현재 시스템 레벨의 전부다. API 가 `POST /api/v1/calc/ev-tune` 하나뿐인 단계라
시스템 레벨을 더 쌓을 표면이 아직 없다.

### 1-4. E2E — 없다

프론트엔드는 Phase 3 에서 들어온다. 현재 `frontend/` 에는 테스트 파일이 없고,
CI 의 frontend job 은 `eslint` / `typecheck` / `build` 만 돈다. 브라우저를 구동하는
E2E 는 **아직 존재하지 않는다.**

## 2. 테스트 유형

| 유형 | 이 프로젝트에서 | 상태 |
|---|---|---|
| **기능 테스트** | 명세(`CLAUDE.md` 5장) 대비 동작 검증. 대부분의 테스트 | 운영 중 |
| **구조 테스트** | 커버리지 | **측정만 가능, CI 게이트 없음** |
| **변경관련 테스트** | 회귀 — 골든 케이스, 변경 탐지기, 데이터 불변식 | 운영 중 |

### 2-1. 기능 테스트

기대 동작의 출처가 `CLAUDE.md` 5장(계산 명세)이다. 명세가 코드보다 먼저 있고,
테스트가 명세의 각 조항을 가리킨다. 예:

- `test_stats.py:19` → `CLAUDE.md` 5-1 검산표
- `test_effort.py:15` → `CLAUDE.md` 5-0 (스탯당 32, 총합 66)
- `test_damage.py:85` → `CLAUDE.md` 5-2 의 A/B 경계 예시
- `test_ev_solver.py:252` → `CLAUDE.md` 5-4 규칙 5

### 2-2. 구조 테스트 — 솔직한 현황

`pytest-cov` 가 의존성에 있고(`backend/pyproject.toml:21`), `CLAUDE.md` 6장이
**도메인 커버리지 90% 이상**을 목표로 선언한다. 그러나:

- `pyproject.toml` 의 `addopts` 에 `--cov` 가 없다
- CI 의 pytest 단계에 커버리지 측정·임계값 검사가 없다

즉 **커버리지는 목표로 선언돼 있지만 자동으로 측정·강제되지 않는다.**
현재 구조적 보장을 실질적으로 떠받치는 것은 §3-5 의 전수 조합 테스트다
— 공식 하나에 대해 25,245개 입력 조합을 전부 돌리면 그 함수의 분기는 남지 않는다.

> 개선 항목: CI 에 `--cov=app/domain --cov-fail-under=90` 추가. 미적용.

### 2-3. 변경관련(회귀) 테스트

CI 가 모든 PR 과 `main`/`develop` push 에서 전체 테스트를 돌린다. 그 위에
**의도적으로 깨지도록 설계한** 테스트가 세 종류 있다.

**(가) 골든 케이스** — `test_stats.py:19`, `test_speed.py:23`

한카리아스 스피드 4라인(169 / 154 / 122 / 109)을 동결했다. 실수치 공식이나
보정 적용 순서를 건드리면 즉시 깨진다.

**(나) 변경 탐지기** — `test_damage.py:82`

```python
class TestModifierChainIsOptionA:
    """ADR-003 A안 고정. B안으로 바꾸면 이 테스트가 깨져야 한다."""
```

데미지 보정 체인이 ADR-003 의 A안임을 테스트로 못 박았다. "깨져야 한다"가 독스트링에
명시돼 있다 — 이 테스트가 깨지는 것은 **버그가 아니라 설계 변경의 신호**다.

**(다) 데이터 불변식** — `test_typechart.py:29`, `test_nature.py:29`

```python
class TestDataFile:
    """생성된 데이터 자체의 불변식. 재생성 시 깨지면 출처가 변한 것이다."""
```

시드 데이터는 외부 출처에서 생성기로 만든다(`backend/scripts/generate_*.py`).
생성기를 다시 돌렸을 때 18타입·무효 8건·성격 25개 같은 불변식이 깨지면
**코드가 아니라 출처가 변했다**는 뜻이다. 테스트 대상이 코드가 아니라 데이터인 경우다.

## 3. 적용한 테스트 설계 기법

실제 테스트 파일을 읽어 매핑했다. **쓰지 않은 기법은 적지 않았다** — 조합 테스트(pairwise),
유즈케이스 테스트, 분류 트리 기법 등은 이 프로젝트에 없다.

표준 기법과, 표준 기법명으로 분류되지 않는 것을 구분해 적는다. 후자는 제목에
**(교과서 기법 아님)** 을 붙였다 — 없는 기법을 쓴 것처럼 적는 건 증빙을 망치는 짓이다.

### 3-1. 동등 분할 (Equivalence Partitioning)

입력·출력을 같은 거동을 보이는 클래스로 나누고 클래스마다 대표값을 테스트한다.

| 분할 대상 | 클래스 | 위치 |
|---|---|---|
| 타입 상성 배율 | 0 / 0.25 / 0.5 / 1 / 2 / 4 (6개) | `test_typechart.py:143` |
| 성격 보정 | 1.1 / 1.0 / 0.9 (3개) | `test_stats.py:83` |
| 포인트 증가 거동 | 상승 / 무보정 / 하락 (3개, 거동이 각각 다르다) | `test_stats.py:48` |
| 기술 분류 | 물리 / 특수 / 변화 | `test_damage.py:360` |

**분할이 비어 있지 않은지도 테스트한다**는 점이 특이하다:

```python
# test_typechart.py:159
def test_every_multiplier_value_is_reachable(self, chart):
    """6개 배율이 모두 실제로 나온다 — 표가 비어 있지 않다는 확인."""
```

동등 분할의 전형적 실패는 "클래스를 나눴는데 그 클래스에 해당하는 입력이 실제로는
존재하지 않는" 경우다. 각 배율이 실제 타입 조합으로 도달 가능한지 확인해 그걸 막았다.

### 3-2. 경계값 분석 (Boundary Value Analysis)

유효/무효 경계의 **양쪽**을 집는다. 이 프로젝트에서 가장 많이 쓴 기법이다.

| 경계 | 집은 값 | 위치 |
|---|---|---|
| 노력치 총합 상한 66 | 66 유효 / 67 거부 (인접 쌍) | `test_effort.py:52` |
| 스탯당 상한 32 | 32 유효 / 33 거부 / 음수 거부 | `test_effort.py:38` |
| 버림 경계 `.5` | 정확히 .5 가 나오는 5지점 | `test_stats.py:103` |
| 확정타 판정 | 16/16 · 1~15/16 · 0/16 | `test_damage.py:376` |
| 최소 데미지 | 0 → 1 로 올림 / 무효는 0 유지 | `test_damage.py:116` |
| 추월 | 동속은 추월이 아니다 (`>` 이지 `>=` 가 아니다) | `test_speed.py:75` |
| 솔버 예산 | 예산 0 / 정확히 66 소진 / 스탯 상한 도달 | `test_ev_solver.py:605` |
| 랭크 단계 | ±6 범위 밖 거부 | `test_stats.py:287` |
| 요청 간격 | 첫 요청 / 정확히 1초 / 0.999초 / 30초 | `test_request_gate.py:53,60` |
| 수집 `limit` | 0 거부 (아무것도 안 한 것을 성공으로 만든다) | `test_championsbattledata.py:274` |

경계값 테스트가 **틀린 구현의 결과까지 함께 단정**한다:

```python
# test_stats.py:103
def test_half_is_floored(self, base_stat, modifier, exact, floored, if_rounded):
    result = calc_stat(base_stat, 0, modifier)
    assert result == floored, f"{exact} 는 버림해서 {floored} 여야 한다"
    assert result != if_rounded, "반올림 연산이 들어갔다"
```

둘째 단정이 핵심이다. `27.5 → 27` 만 확인하면 "버림이 맞다"가 아니라 "우연히 맞았다"일
수 있다. 반올림했을 때의 값(`28`)과 **다름**을 함께 단정해야 버림/반올림을 구별한다.
파이썬 기본 `round()` 는 은행가 반올림이라 `27.5→28`, `38.5→38` 로 일관되지도 않아
한쪽만 보면 통과할 수 있다.

### 3-3. 결정 테이블 (Decision Table)

조건 조합과 기대 결과를 표로 만들고 각 행을 테스트한다.

**날씨 × 기술 타입 → 배율** (`test_damage.py:301`, 8행)

| 날씨 | 기술 타입 | 배율 |
|---|---|---|
| 쾌청 | 불꽃 / 물 / 풀 | 1.5 / 0.5 / 1.0 |
| 비 | 물 / 불꽃 | 1.5 / 0.5 |
| 없음 | 불꽃 | 1.0 |
| 모래 / 설경 | 바위 / 얼음 | **1.0 (미구현)** |

마지막 행이 중요하다. 모래바람·설경은 데미지 배율이 아니라 스탯 단계에 작용해서
아직 구현하지 않았는데, **그 사실을 표의 한 행으로 명시**했다. 미구현을 공백으로
두면 나중에 "구현했는데 테스트가 없다"와 구분되지 않는다.

**우선도 × 스피드 × 트릭룸 → 행동 순서** (`test_speed.py:145`)

조건 3개의 조합. 트릭룸이 스피드를 뒤집지만 **우선도는 못 뒤집는다**는 규칙이
`test_trick_room_does_not_invert_priority:154` 로 고정돼 있다.

### 3-4. 상태 전이 테스트 (State Transition)

메타 스냅샷에 수명이 있다. 전이마다 테스트가 붙는다.

```
 [적재]──▶ 비활성 ──검증 통과──▶ 활성 ──새 스냅샷──▶ 비활성 ──기한 경과──▶ [삭제]
              │                      │
          검증 실패                기한 경과
              │                      │
              ▼                      ▼
        활성 전환 안 함          삭제하지 않음(보존)
```

| 전이 | 검증 내용 | 위치 |
|---|---|---|
| 비활성 → 활성 | 새 스냅샷이 활성, 구 스냅샷이 비활성으로 | `test_ingest.py:180` |
| 검증 실패 시 | **적재는 되고 활성화만 막힌다** | `test_ingest.py:128` |
| 전이 도중 | 활성이 둘인 순간이 DB 제약으로 불가능 | `test_db_schema.py:216` |
| 만료 + 비활성 | 삭제된다 | `test_ingest.py:249` |
| 만료 + 활성 | **삭제하지 않는다** (서비스가 볼 메타가 사라진다) | `test_scheduler_commands.py:109` |
| 삭제 시 | 하위 행이 cascade 로 함께 지워진다 | `test_db_schema.py:247` |

"활성 스냅샷은 항상 정확히 하나"를 애플리케이션 코드가 아니라 **부분 유니크 인덱스로
DB 가** 보장하고, 그 보장을 `IntegrityError` 가 실제로 발생하는지로 테스트한다.
애플리케이션으로 막으면 전환 도중 둘 다 활성인 순간이 생긴다.

### 3-5. 전수 조합 테스트 (Exhaustive Testing)

입력 공간이 작을 때는 샘플링하지 않고 전부 돈다.

```python
# test_stats.py:108
def test_matches_math_floor_across_full_range(self):
    """종족값 1~255 x 포인트 0~32 x 보정 3종 완전 탐색."""
```

**255 × 33 × 3 = 25,245 조합.** 기대값을 `math.floor(raw * numerator / 10)` 로
독립 계산해 전부 대조한다(§4-2 참조). 입력 공간이 유한하고 작으므로 경계값을
고를 필요 없이 경계가 전부 포함된다.

- `test_typechart.py:146` — 전체 타입 조합이 유효 배율만 내는지
- `test_typechart.py:72` — 18타입이 전부 공격자로 표에 있는지

이 기법이 가능한 이유도 도메인 계층이 순수 함수이기 때문이다. DB 를 타면 25,245번
돌릴 수 없다.

### 3-6. 부정 테스트 / 오류 추정 (Negative Testing / Error Guessing)

유효하지 않은 입력에 **명확히 실패하는지** 확인한다. 거의 모든 도메인 테스트 파일에
`TestInputValidation` 클래스가 있다.

| 추정한 오류 | 기대 동작 | 위치 |
|---|---|---|
| 방어/공격 실수치 0, 음수 위력 | 도메인 예외 | `test_damage.py:434` |
| 종족값 0 / 음수 | 도메인 예외 | `test_stats.py:159` |
| 존재하지 않는 타입 문자열 | 도메인 예외 | `test_typechart.py:184` |
| 방어 타입 0개 / 3개 | 도메인 예외 | `test_typechart.py:171` |
| 모르는 도구 id | **fail-closed** — 무시하지 않고 실패 | `test_ev_solver.py:868` |
| 성격 상승 2개 / 하락 2개 / HP 보정 / 쌍이 아님 | 도메인 예외 (4종) | `test_ev_solver.py:397` |
| HP 종족값 1 (껍질몬) | 거부 — 챔피언스에 없어야 하는 입력 | `test_stats.py:144` |

**fail-closed 가 테스트로 고정돼 있다**는 점이 이 프로젝트의 특징이다. 모르는 입력을
조용히 건너뛰면 "이 기술 채용률 0%" 같은 **틀린 화면**이 나온다. 그래서 모르는
항목은 예외로 터뜨리는 것이 기대 동작이고, 그걸 테스트가 지킨다 (ADR-005).

### 3-7. 메타모픽 관계 단정 (Metamorphic Testing)

> ISTQB 기본 설계 기법 목록에는 없지만, **기대값을 모르는 상황**에 대한 표준적
> 대응이다. 절대값 대신 **입력을 바꿨을 때 출력이 지켜야 하는 관계**를 단정한다.
> 이 프로젝트에서 왜 필요했는지는 §4 참조.

| 관계 | 단정 내용 | 위치 |
|---|---|---|
| 교환 | 보정 적용 순서가 결과를 바꾸지 않는다 (A안의 정의) | `test_damage.py:95` |
| 교환 | 방어 타입 순서가 상성을 바꾸지 않는다 | `test_typechart.py:137` |
| 단조 | 16 roll 이 비감소 | `test_damage.py:107` |
| 단조 | 랭크 배율이 단계에 단조 | `test_stats.py:280` |
| 단조 | 스피드 4라인이 빠른 순으로 정렬 | `test_speed.py:47` |
| 순서 | `min_percent ≤ max_percent` | `test_damage.py:417` |
| 선형 | HP 는 포인트에 선형 | `test_stats.py:139` |
| 비교 | 상승보정이 하락보정보다 더 멀리 닿는다 | `test_speed.py:87` |
| 반전 | 트릭룸이 일반 결과를 정확히 뒤집는다 | `test_speed.py:138` |
| 증가 | 급소가 데미지를 늘린다 | `test_damage.py:328` |
| 극대성 | 어떤 대안 선택지도 다른 선택지의 부분집합이 아니다 | `test_ev_solver.py:319` |

**왜 이게 중요한가**: 위 관계들은 데미지 체인이 ADR-003 의 A안이든 B안이든 **성립해야
한다.** 즉 오라클이 불확실한 영역에서도 유효한 검증이다. 공식이 확정되지 않았다는
이유로 테스트를 미루지 않을 수 있었던 근거다.

### 3-8. 차등 단정 (Differential Assertion)

> 표준 기법명이 아니다. §3-7 의 변종으로, **틀린 구현을 넣었다면 결과가 달라진다는
> 것을 테스트가 직접 증명**하는 형태다. 테스트가 동어반복이 아님을 테스트가 보인다.

세 번째 사례는 요청 간격의 기준이다 (`test_request_gate.py:105`).
"이전 요청이 **끝난** 시각"과 "**시작한** 시각" 중 어느 쪽을 기준으로 삼아도
대부분의 테스트는 같은 결과를 낸다. 응답이 오래 걸린 경우에만 답이 갈린다.

| 기준 | 의미 | 응답이 2초 걸린 뒤 |
|---|---|---|
| 끝난 시각 (채택) | 요청 사이에 1초의 정적 | 1초 더 기다린다 |
| 시작한 시각 | 초당 1요청 (rate limit) | 즉시 다음 요청 |

그래서 그 한 케이스가 **기준을 고정하는 유일한 테스트**다. 기준이 뒤집히면
이 테스트만 깨진다. 테스트 이름에 그 사실을 적었다 —
`test_a_slow_response_does_not_excuse_the_gap`.

```python
# test_stats.py:42
def test_multiplying_before_adding_would_differ(self):
    """성격 보정을 먼저 곱하면 값이 어긋난다 — 순서가 실제로 중요하다는 증명"""

# test_damage.py:181
def test_zero_item_multiplier_would_not_be_enough(self):
    """왜 별도 플래그가 필요한지 — item=0 은 1을 돌려준다."""
```

두 번째가 특히 유용하다. "무효는 0, 그 외 0 은 1로 올림"이라는 규칙 때문에
도구 배율 0 으로는 무효를 표현할 수 없다. 그래서 별도 `is_immune` 플래그를 뒀는데,
**그 설계가 필요했던 이유 자체를 테스트가 보존**한다. 나중에 누가 "플래그 없이
배율 0 으로 충분한데?" 라고 물으면 이 테스트가 답한다.

### 3-9. 전제 선행 단정 (교과서 기법 아님)

표준 기법명을 억지로 붙이지 않는다. 확인하는 것은 **"이 테스트가 실제로 무언가를
검증했다"** 는 전제 그 자체다.

복구 리허설이 이 장치를 필요로 한다. 리허설의 본체는 "백업 → 전체 테이블 DROP →
복구 → 전후 비교" 인데, **DROP 이 조용히 실패하면 전후 비교가 전부 통과한다.**
아무것도 파괴되지 않았으니 아무것도 복구할 필요가 없었고, 테스트는 초록이다.
이건 거짓 음성(false negative) 중에서도 가장 알아채기 어려운 종류다 — 깨지지 않고,
깨질 이유도 없어 보인다.

```python
# tests/rehearsal/test_restore_rehearsal.py
class TestDestructionActuallyHappened:
    def test_all_tables_were_dropped_before_restore(self, rehearsal):
        assert rehearsal.tables_after_destroy == 0

    def test_there_was_something_to_lose(self, rehearsal):
        """파괴 전에 테이블과 행이 실제로 있었다. 빈 DB 를 복구해도 전후는 같다."""
        assert len(rehearsal.before.row_counts) >= 9
        assert sum(rehearsal.before.row_counts.values()) > 0
```

두 번째가 첫 번째보다 미묘하다. 테이블이 0 개인 DB 를 백업하고 복구하면 전후는
완벽하게 같다 — 네 층 전부 통과한다. **"비교해서 같았다"는 "검증했다"가 아니다.**
비교 대상이 비어 있지 않았다는 사실이 따로 단정돼야 한다.

같은 성질의 단정을 수집 테스트에서도 쓴다
(`tests/unit/ingestion/test_championsbattledata.py` 의
`test_wait_count_is_one_less_than_request_count` — 요청이 0 회면 대기도 0 회라
"대기 횟수 = 요청 횟수 - 1" 이 공짜로 성립하므로, 요청 횟수를 따로 단정한다).

### 3-10. 문서에 적힌 명령을 그대로 실행 (교과서 기법 아님)

테스트가 **환경을 전부 명시 주입하면, 사람이 실제로 치는 명령은 아무도 보지 않는다.**

리허설 29개와 권한 테스트 21개가 전부 초록인 상태에서
`docs/RUNBOOK.md` 의 1차 조치 명령이 동작하지 않았다. 테스트는 `PGHOST`·`PGUSER`·
`PGPASSWORD` 를 전부 넘기고 돌렸고, 문서에는 짧은 형태를 적었다. **검증한 명령과
안내한 명령이 달랐고 그 차이가 검증 범위 밖이었다** (JOURNAL 2026-11-17).

```python
# tests/rehearsal/test_ops_script_defaults.py
def test_backup_runs_as_the_read_only_account(self, tmp_path):
    result = run_script(BACKUP_SCRIPT, env=bare_env(BACKUP_DIR=str(tmp_path), ...))
    assert result.returncode == 0           # ① 문서가 거짓이 아니다
    assert "user=champs_read" in result.stderr   # ② 그때 최소 권한 계정을 쓴다
```

②가 없으면 ①을 **부트스트랩 슈퍼유저를 기본값으로 두어 쉽게 통과**시킬 수 있다.
편의가 계정 분리를 무력화하는 경로가 되므로, 두 단정이 함께 있어야 한다.

검증 방식: 수정 전 스크립트로 되돌려 4개가 전부 실패하는 것을 확인한 뒤
수정본으로 통과시켰다 (RED → GREEN). 통과만 보고 끝내면 단정이 실제로
그 결함을 잡는지 알 수 없다.

범위의 한계: `PGHOST` 의 기본값(`db`)은 테스트가 아니라 **실제 명령 실행**으로
확인했다. 테스트에서 그것까지 기본값에 맡기면 리허설이 개발 DB 를 향한다.

### 3-11. 백투백 테스트 (Back-to-Back Testing)

같은 입력을 **독립적으로 구현한 두 코드**에 넣고 결과를 비교한다. 신뢰할 수 있는
기대값이 없고, 기존 구현을 더 빠른 구현으로 **교체**할 때 쓴다.

노력치 솔버의 조합 탐색이 그 사례다. 전수 조합(데카르트 곱)을 분기한정으로
바꿨는데, 가지치기는 **성능만** 바꿔야 하고 답은 한 글자도 달라지면 안 된다.
그래서 전수 조합 오라클을 테스트 파일에 따로 적고 무작위 입력으로 대조한다.

```python
# tests/unit/domain/test_ev_solver.py
def brute_force_best(candidate_sets):
    """전수 조합 오라클.

    ★ 구현을 호출하지 않고 이 파일에 따로 적는다. 오라클이 구현과 코드를
    공유하면 같은 실수를 같이 하고, 그러면 대조가 아무것도 증명하지 않는다.
    """

class TestCombinationSearchMatchesBruteForce:
    def test_random_inputs_agree(self, chart, catalog):
        ...
        assert ev_solver._best_combination(sets) == brute_force_best(sets)
        assert compared >= 200, f"비교한 입력이 {compared}건뿐이다"
```

핵심은 **오라클이 구현과 코드를 공유하지 않는 것**이다. 구현의 헬퍼를 불러 쓰면
그 헬퍼의 버그는 양쪽에서 똑같이 발현해 대조를 통과한다.

실제로 이 테스트가 결함을 잡았다. 증분 병합이 `0 > 0` 이 거짓이라 `{SPEED: 0}`
키를 생략했고, **배분과 총합은 같은데 딕셔너리가 달라서** 379건이 어긋났다.
기존 단위 테스트 474개는 전부 통과했다 — 값이 같으면 통과하는 단정뿐이었기 때문이다.

이 기법은 [ADR-008](adr/008-solver-search-strategy.md) 이 **교체 조건으로 미리
요구해둔 것**이다("선형 스캔 결과와 대조하는 테스트를 먼저 만든다"). 되돌리는 조건에
검증 방법까지 적어두면 나중에 그 조건이 발동할 때 무엇부터 할지가 정해져 있다.

> §3-7(메타모픽)·§3-8(차등)과의 차이: 메타모픽은 **한 구현 안에서** 입력 관계로
> 출력 관계를 단정하고, 차등 단정은 **틀린 설계를 넣으면 달라진다**를 보인다.
> 백투백은 **두 구현의 출력을 직접 비교**한다.

### 3-12. 성능 회귀 감지 — 시간이 아니라 작업량 (교과서 기법 아님)

성능을 테스트로 고정할 때 **벽시계 시간을 단정하지 않는다.** 시간은 러너 부하에
따라 흔들려서 임계치를 넉넉히 잡아야 하고, 그러면 회귀를 놓친다. 대신 입력에 대해
**결정론적인 작업량**을 센다.

```python
# tests/unit/domain/test_ev_solver.py
class TestPruningKeepsTheSearchSmall:
    def test_eight_wide_constraints_stay_under_a_thousand_nodes(self, ...):
        monkeypatch.setattr(ev_solver, "_merge_one", counted)
        ...
        # 실측 506 노드 (2026-11-18). 2배 여유를 두고 1000 으로 막는다.
        assert len(visited) < 1000, f"노드 {len(visited)}개 — 가지치기가 약해졌다"
```

제약 8개 × 파레토 전선 23개면 전수 조합은 `23^8 ≈ 783억` 이다. 이 입력으로
**시간**을 단정하려면 테스트가 끝나지 않는다. 노드 수는 0.6ms 에 센다.

민감도를 RED 로 확인했다. 가지치기 상한을 **12포인트만** 느슨하게 했더니 테스트가
10분을 넘겨 중단해야 했다 — 작업량 단정이 성능 저하를 실제로 잡는다.

한계: 노드 수가 **같은 노드당 비용**을 보장하지는 않는다. 노드 하나가 비싸지는
변경(예: 병합 안에서 데미지 계산)은 이 단정을 통과한다. 그래서 런북 6장에 실측
응답시간 기준선을 따로 둔다.

## 4. 테스트 오라클 문제와 해결 ★

이 문서의 핵심 항목이다.

### 4-1. 문제 — 신뢰할 수 있는 오라클이 없었다

테스트 오라클은 "기대값을 무엇으로 정하는가"다. 포켓몬 챔피언스는:

- **공식 계산 명세가 공개되지 않았다.** 참조할 수 있는 건 비공식 팬 자료뿐이다.
- 본가 시리즈와 **엔진이 다르다.** 기술 위력·명중이 패치로 조정됐고 PP 가
  `{1, 8, 12, 16, 20}` 로 정규화됐다 (ADR-009). 본가 데이터를 가정하면 조용히 틀린다.
- 데미지 보정 체인이 **두 안으로 갈린다.** 보정을 실수로 누적해 마지막에 한 번
  내림하는가(A안), 단계마다 내림하는가(B안).

A/B 는 경계에서 ±1 어긋난다. 그리고 그 1이 결론을 뒤집는다:

| 안 | 계산 (기초 100, 난수 0.85, 자속 1.5, 약점 2배) | 결과 | 상대 HP 255 일 때 |
|---|---|---|---|
| A | `floor(100 × 3.0 × 0.85)` | **255** | **확정 1타** |
| B | `floor(100×0.85)=85 → floor(85×1.5)=127 → ×2` | **254** | **난수 1타** |

"확정 1타"와 "난수 1타"는 선출 판단이 달라지는 차이다. 즉 **오라클의 1 오차가 제품의
답을 바꾼다.** 이 상태에서 "계산 엔진을 테스트했다"고 말하려면 오라클을 다뤄야 했다.

### 4-2. 해결 — 오라클을 네 종류로 나눠 쓴다

신뢰도가 다른 오라클을 섞지 않고, 각각 무엇을 보장하는지 구분했다.

| 오라클 | 신뢰 근거 | 보장 범위 | 이 프로젝트의 적용 |
|---|---|---|---|
| **명세 오라클** | 공식이 확정된 영역 | 정확한 기대값 | 실수치 4라인 169/154/122/109 (`test_stats.py:19`) |
| **파생 오라클** | 독립 구현과 대조 | 전 입력 공간 | `math.floor` 로 25,245 조합 대조 (`test_stats.py:108`) |
| **메타모픽 오라클** | 공식과 무관한 관계 | 관계만 (절대값 아님) | §3-7 의 11개 관계 |
| **골든(동결) 오라클** | 실측값 | 측정한 케이스만 | `golden_damage.json` — **현재 0건** |

**실수치는 명세 오라클이 있다.** `CLAUDE.md` 5-1 의 축약 공식이 확정이고, 검산표
4케이스를 골든으로 동결했다. 여기는 오라클 문제가 없다.

**파생 오라클이 두 번째 안전망이다.** `calc_stat()` 의 기대값을 테스트가
`math.floor(raw * numerator / 10)` 로 **독립적으로 다시 계산**해 대조한다. 구현을
복사한 게 아니라 다른 경로로 같은 답에 도달하는지 보는 것이라, 구현과 테스트가
같은 실수를 공유하기 어렵다.

**데미지는 명세 오라클이 없다.** 그래서 두 가지로 나눠 대응했다:

1. **관계는 지금 테스트한다** (메타모픽). 순서 무관·단조성·min≤max 는 A안이든
   B안이든 성립해야 하므로 공식 확정과 무관하게 유효하다.
2. **절대값은 동결하고 미결로 표시한다.** A안을 구현하되 `TestModifierChainIsOptionA`
   로 못 박고, ADR-003 의 상태를 `채택` 이 아니라 **`잠정 채택`** 으로 남겼다.

### 4-3. 동결 규칙이 오라클 신뢰성을 보장하는 방식

`CLAUDE.md` 6장:

> 골든 케이스가 깨지면 **절대 테스트 기대값을 수정해서 통과시키지 않는다. 엔진을 고친다.**

같은 규칙이 데이터 파일 자체에도 박혀 있다 (`tests/fixtures/golden_damage.json`
의 `_meta.rules`). 왜 이 규칙이 신뢰성을 만드는가:

**기대값을 고칠 수 있으면 테스트는 동어반복이 된다.** 실패할 때마다 기대값을 현재
출력으로 맞추면, 테스트는 "구현이 지금 내는 값"을 재확인하는 장치로 퇴화한다.
그 시점에 오라클은 구현에 종속되고, **독립된 진실의 원천이 사라진다.**
회귀를 탐지할 능력도 함께 사라진다 — 바뀐 값이 항상 정답이 되기 때문이다.

기대값을 동결하면 방향이 반대가 된다. 테스트가 구현보다 상위에 있고, 불일치는
**구현이 틀렸다는 신호**로만 읽힌다.

### 4-4. 그 규칙의 예외를 실제로 판정한 사례

규칙을 선언하는 것과 압박 상황에서 지키는 것은 다르다. 이 프로젝트에는
**기대값을 고친 기록이 두 건** 있고, 왜 그게 금지 조항에 걸리지 않는지 각각 남겼다.

#### 사례 1 — 외운 한글명이 틀렸다 (2026-11-09)

`docs/decisions/JOURNAL.md` 2026-11-09 항목:

- **증상**: 테스트 4건 실패. `jolly` 의 한글명이 '천진난만'이 아니라 '명랑'으로 나왔다.
  `roughskin` 도 '거친피부'가 아니라 '까칠한피부'였다.
- **확인**: 데이터가 맞았다. 천진난만은 Naive(스피드↑ 특방↓), 명랑이 Jolly(스피드↑ 특공↓)다.
- **처리**: 기대값을 고쳤다.
- **구분 근거**: *"금지되는 건 엔진이 틀렸는데 기대값을 맞추는 것이고, 여기서는 내가
  외운 한글명이 틀렸다. 보정 쌍 교차검증이 '이 한글명은 스피드↑ 특공↓ 성격의 것'임을
  이미 보장한 상태였다."*

판정 기준을 일반화하면:

> **오라클 자체가 틀렸다는 외부 근거가 독립적으로 확인될 때만** 기대값을 고치고,
> 그 근거를 기록한다. 구현을 통과시키려고 고치는 것과는 방향이 반대다.

여기서 "독립적"이 결정적이다. 성격은 **상승/하락 스탯 쌍**으로 교차검증돼 있었다 —
즉 구현이 아닌 제3의 사실이 데이터를 뒷받침했다. 그 장치가 없었다면 기대값을
고칠 근거가 없었고, 구현을 의심했어야 한다.

같은 항목의 "배운 것"이 그 원칙을 한 줄로 적어뒀다:
*"검증 장치가 통과한 데이터와 내 기억이 충돌하면 기억을 먼저 의심한다.
장치는 근거를 제시할 수 있고 기억은 못 한다."*

#### 사례 2 — 테스트의 명세 해석이 틀렸다 (2026-11-17)

`docs/decisions/JOURNAL.md` 2026-11-17 두 번째 항목.

- **증상**: 요청 예절 게이트를 구현한 뒤 1건 실패. `assert [1.0] == []`.
- **쟁점**: 기대 동작이 무엇인지가 이 건의 쟁점 자체였다. 처음 적은 기대값은
  "응답이 2초 걸렸으면 다음 요청은 즉시 나간다"였고, 그 근거로 독스트링에
  "이미 2초의 공백이 있었다"고 적혀 있었다.
- **확인**: 그 근거가 거꾸로였다. 응답에 걸린 2초는 **출처가 우리 요청을 처리한
  시간**이고, 조용한 간격이 아니다.
- **처리**: 구현을 두고 기대값을 고쳤다.
- **구분 근거**: `CLAUDE.md` 8-6 의 문구 — "요청 **간** 최소 1초 **지연**",
  "고정 rate limit 이 없다고 몰아치지 않는다". 둘 다 보수적인 쪽을 가리킨다.

여기서도 "독립적"이 결정적이다. 근거가 **구현이 아니라 규칙 문서**였다.
구현이 그렇게 생겼으니 맞다고 한 게 아니라, 규칙 문서의 문구가 구현 쪽 해석을
지지했다. 문구가 반대였다면 구현을 고쳐야 했다.

이 사례의 값은 **판정 기준을 미리 적어둔 효과**에 있다. 위 일반화된 기준이
이 문서에 먼저 있었기 때문에, 실패를 마주한 순간 "고쳐도 되나"를 즉흥으로
판단하지 않았다. 확인할 것(외부 근거가 독립적인가)이 정해져 있었다.

#### 사례 3 — 오라클이 본 것이 불변식이 아니었다 (2026-11-17)

복구 리허설의 3층(제약·인덱스 생존)에서 제약 정의 문자열을 전후로 비교했는데
`ck_moves_category` 하나가 달랐다.

```
복구 전: ANY ((ARRAY['physical'::character varying, ...])::text[])
복구 후: ANY (ARRAY[('physical'::character varying)::text, ...])
```

**독립적 근거 두 개**로 오라클이 틀렸다고 판정했다.

1. `pg_get_constraintdef` 은 저장된 문자열이 아니라 **파스 트리를 다시 렌더링한
   결과**다. pg_dump 가 식을 직렬화하고 복구가 다시 파싱하면 캐스트 위치가
   재배치된다. 두 식은 같은 검사다 — PostgreSQL 의 동작이고 우리 코드와 무관하다.
2. **집행 여부를 보는 테스트가 따로 통과했다.** `TestConstraintsStillEnforce` 가
   위반을 실제로 INSERT 해서 `ck_moves_category` 가 거부하는 것을 확인한다.

즉 지키려는 불변식은 "렌더링 문자열이 같다"가 아니라 "같은 검사가 집행된다"였다.
오라클이 불변식보다 좁은 것을 보고 있었다.

고친 방향은 **기대값을 느슨하게 한 것이 아니라 셋으로 쪼갠 것**이다.

| 단정 | 엄격도 |
|---|---|
| 제약 **이름** 집합 동일 | 원문 그대로 비교. 하나라도 사라지거나 생기면 실패 |
| 제약 **정의** 동일 | 캐스트·괄호·공백을 걷어낸 형태로 비교. 값 목록이 바뀌면 여전히 실패 |
| 제약 **집행** | 위반을 INSERT 해서 거부되는지 (정의 비교로는 대체 불가) |

세 번째가 핵심이다. 카탈로그에 정의가 남아 있어도 인덱스가 `INVALID` 상태면
막지 못한다. **"정의가 있다"와 "집행된다"는 다른 단정이다** — ADR-013 에서 요청
간격 상수가 선언돼 있는데 지켜지지 않았던 것과 같은 구조가 반복됐다.

### 4-5. 미해결로 남긴 것 (숨기지 않음)

| 항목 | 현황 |
|---|---|
| `golden_damage.json` | **스키마와 수집 규칙만 있고 `cases: []` — 0건.** 테스트에 연결되지도 않았다 |
| ADR-003 | **`잠정 채택`**. 게임 실측 전까지 확정이 아니다 |
| 데미지 절대값 | 명세 오라클 없음. 메타모픽 관계와 A안 동결로만 보호 |

골든 케이스 수집 규칙은 미리 정해뒀다 — **보정이 하나뿐인 케이스는 A/B 가 같은 값을
내므로 검증 가치가 없고, 자속+약점+급소처럼 배율이 3개 이상 겹치는 경계 케이스를
우선 수집한다.** 측정 설계를 먼저 하고 데이터를 나중에 채우는 순서다.

이 공백을 "테스트 부족"이 아니라 **"오라클 부재로 식별하고 범위를 표시한 상태"** 로
관리하는 것이 현재 전략이다. 측정 없이 숫자를 확정하면 틀린 확신이 코드에 들어간다.

## 5. LLM 출력 검증 전략

> **구현 상태**: Phase 4 는 **미구현**이다. `app/services/llm/` 디렉터리가 아직 없다.
> 아래는 `CLAUDE.md` 1장·7장과 `docs/DEVELOPMENT_GUIDE.md` 에 정의된 **설계**이고,
> 그중 `assumptions` 필드만 이미 구현·테스트돼 있다 (`app/schemas/ev_tune.py`,
> `test_calc_ev_tune.py:222`).
>
> `DEVELOPMENT_GUIDE.md` 는 작업용 내부 문서라 저장소에 포함하지 않는다
> (`.gitignore`). 공개된 근거는 `CLAUDE.md` 1장·7장이다.

### 5-1. 근본 원칙 — LLM 은 숫자를 만들지 않는다

`CLAUDE.md` 1-1:

> 데미지 %, 확정 n타, 스피드 실수치, 노력치 배분 — 전부 `app/domain/` 의
> 순수 함수가 계산한다. LLM 에게 "이 기술 몇 % 들어가?"를 묻는 코드는 절대 작성하지 않는다.

**테스트 전략의 관점에서 이 원칙의 의미**: LLM 출력은 비결정적이라 기대값을 단정할 수
없다. 그런데 사용자가 의존하는 것은 **수치**다. 수치를 전부 결정론적 경로로 밀어내면,
검증 불가능한 부분과 검증해야 하는 부분이 분리된다.

```
사용자 요청
   │
   ├─▶ domain 계산 ──────────▶ 수치   [결정론적 · 588개 테스트의 사정권]
   │       (데미지·스피드·상성)
   │
   └─▶ 계산 결과를 "사실 블록" JSON 으로 직렬화
           │
           ▼
       LLM 프롬프트 주입 ──▶ 해석·설명 텍스트  [비결정적 · 스키마로만 통제]
           │
           ▼
       Pydantic 응답 검증 ──▶ 실패 시 1회 재시도 후 실패 처리
```

경계가 명확하므로 **"계산이 맞는가"는 전부 테스트 가능한 쪽에 있다.**
LLM 쪽에서 통제하는 것은 정확성이 아니라 **형식과 참조 무결성**이다.

### 5-2. 각 장치가 막는 것

| 장치 | 막는 실패 | 상태 |
|---|---|---|
| 계산/LLM 경계 분리 | 환각 수치가 UI 에 숫자로 표시되는 것 | 설계 (1-1) |
| 프롬프트의 금지문 | 사실 블록에 없는 수치를 LLM 이 지어내는 것 | 설계 (7장) |
| JSON 스키마 강제 | 자유 텍스트가 검증 없이 클라이언트로 가는 것 | 설계 (7장) |
| 파싱 실패 시 1회 재시도 후 실패 | 깨진 응답이 조용히 통과하는 것 | 설계 (7장) |
| `evidence_refs` 강제 | **근거 없는 주장** — 어느 계산 결과를 참조했는지 못 밝히는 문장 | **설계만** |
| `assumptions` 필드 | **추정을 사실로 표시하는 것** | **구현·테스트됨** |

**프롬프트 금지문** (모든 프롬프트에 포함, `CLAUDE.md` 7장):

> 제공된 계산 결과 블록에 없는 수치는 절대 생성하지 마라.
> 필요한 수치가 없으면 "계산되지 않음"이라고 답하라.

**`evidence_refs`** (`docs/DEVELOPMENT_GUIDE.md`): 응답의 각 주장이 어느 계산 결과를
참조하는지 식별자로 가리키게 한다 (`"evidence_refs": ["damage_matrix[3]", "speed_tiers[0]"]`).
참조가 없는 주장은 응답 검증 단계에서 거른다. **LLM 이 계산 결과를 실제로 참조했는지를
기계적으로 확인**하기 위한 장치다. 설계 문서에만 있고 구현되지 않았다.

**`assumptions`** — 유일하게 이미 돌아가는 부분이다. 상대 파티 분석은 "범용 샘플 가정"이
전제이고, 그 전제를 응답 스키마의 `assumptions` 필드로 명시한다 (`CLAUDE.md` 1-3).
현재 노력치 솔버 API 가 같은 패턴을 쓴다 — 날씨·벽·급소 같은 전투 맥락이 결과를 바꿨다는
사실이 근거 문장에 드러나는지 테스트한다 (`test_ev_solver.py:751`).

### 5-3. 표현 규칙도 검증 대상이다

`CLAUDE.md` 1-3 이 금지하는 표현이 있다:

- "상대가 이 기술을 들고 있다" ✗ → "상위 3개 샘플 중 X%가 이 기술을 채용" ○
- "카운터" 를 조건 없이 쓰지 않는다 → 항상 `조건 + 무너지는 케이스` 를 함께 반환

이건 품질 요구사항이지 코드 규칙이 아니라, 응답 스키마가 구조로 강제해야 한다
(`조건` 과 `무너지는 케이스` 를 **필수 필드**로 두면 비워둘 수 없다).
Phase 4 에서 스키마를 만들 때 구현한다.

## 6. 현재 한계

증빙 문서이므로 부족한 것도 같이 적는다.

| 항목 | 현황 | 계획 |
|---|---|---|
| 커버리지 | `pytest-cov` 설치만. **CI 게이트 없음** | `--cov-fail-under=90` 추가 |
| 수집 샘플 응답 | **실측 아님** — 파서 가정에서 역산 (§1-1 나) | 실호출 1회로 승격 |
| 출처 표기 소비 | 인터페이스·데이터 흐름만. **읽는 코드 없음** | Phase 2-7 (화면 표기) |
| 골든 데미지 케이스 | **0건** (스키마만) | 게임 실측 필요 — 별도 트랙 |
| E2E | **없음** | Phase 3 프론트 도입 후 |
| 프론트 단위 테스트 | **없음** (lint·typecheck·build 만) | Phase 3 |
| LLM 응답 검증 | **미구현** | Phase 4 |
| 성능·부하 테스트 | **없음** | Phase 6 배포 후 |
| 응답 지연 경보 | 있음 (`PokehelperApiSlow`). 다만 **거짓 음성 쪽으로 기울여** 놨다 — 최소 트래픽 절 때문에 저트래픽 구간의 지연은 잡지 않는다 | 트래픽이 생기면 절을 다시 본다 |
| 솔버 최악 보장 | 분기한정으로 2.2초 → 96ms (ADR-017). 다만 **지수 시간이 사라진 게 아니라** 가지치기에 의존한다. 노드 상한 없음 | 노드 수 테스트가 1000 에서 깨지면 상한 재검토 |
| 후보 생성 비용 | 제약 8개 96ms 중 **95ms 가 `_candidates_for`**. 제약 수에 선형이라 지금은 무해 | 느려지면 여기부터 |
| 익스포터 지표 참조 | 교차검증 범위가 백엔드 노출분(`pokehelper_*`·`http_*`)이다. **익스포터가 내보내는 `up`·`pg_*`·`redis_*`·`container_*` 참조가 깨져도 통과한다** | 스택 띄워 타깃 상태로 확인 중 |
| 느린 쿼리 식별 | **없음** — `pg_stat_statements` 미활성 | 필요해질 때 |
| 경보 수신 | Alertmanager 없음. 경보가 UI 에만 뜬다. **지금 정확히 셋이라 다음 경보가 도입 조건을 발동시킨다** | 경보가 셋을 넘으면 (ADR-016) |
| 변이 테스트 | 없음 | 미계획 |
| CI 의 계정 분리 단계 | **아직 한 번도 돌지 않았다** — 러너에 `psql` 이 있다는 전제가 미실측 | 첫 PR 에서 확인 |
| 복구 리허설 CI 실행 | **없음** — 로컬에서 손으로 돌린다. 자동으로 회귀를 막지 못한다 | 러너에서 compose 프로필 기동 |
| ROLE(계정) 백업 | **없음** — `pg_dump` 에 계정이 안 들어간다. 빈 서버 완전 복구 불가 | `pg_dumpall --roles-only` (계정 분리 작업) |
| 운영 백업 전략 | 리허설이 증명하는 것은 **논리 백업의 왕복**뿐. 배포 대상 미결 | ADR-001 배포 결정 후 |
