# ADR-007: 데미지 보정을 세 계층으로 분리하고, 도메인은 결정된 배율만 받는다

- 상태: 채택 (2026-11-04)
- 관련: Phase 1, `domain/damage.py`, `domain/models.py`
- 관련 ADR: [ADR-003](003-damage-chain.md) 보정 체인 A안 / [ADR-004](004-postgres-jsonb.md) 시드 데이터

## 맥락

`damage.py` 를 설계하면서 적용할 보정 목록을 확정해야 했다. 개발자가 챔피언스에 존재한다고
확인해준 것은 날씨(쾌청·비·모래바람·설경), 벽, 트릭룸·원더룸, 급소 1.5배, 필드
(그래스필드의 지진 반감), 지저 상태의 지진 2배, 도구 효과였다.

이것들을 `CLAUDE.md` 5-2의 보정 체인
`stab * type * weather * crit * ability * item * screen * burn` 에 그대로 넣으려다
**셋이 성격이 다르다는 것이 드러났다.**

| 범주 | 적용 지점 | 해당 항목 |
|---|---|---|
| 스탯 단계 | 기초 계산 **전** | 화상(공격 0.5), 구애띠, 돌격조끼, 모래바람의 바위 특방, **원더룸**, 랭크 |
| 데미지 배율 | `apply_modifiers()` | 자속, 타입상성, 날씨(타입별), 급소, 벽, 필드, 생명의구슬 |
| 데미지와 무관 | — | **트릭룸** (턴 순서) |

**이 구분이 중요한 이유는 `floor` 다.** 공격을 먼저 반감하고 `floor(22 × 위력 × A / D)` 를
하는 것과 데미지를 나중에 반감하는 것은 경계에서 ±1 어긋난다. [ADR-003](003-damage-chain.md)
에서 A/B안이 다퉜던 바로 그 1이고, 확정/난수 판정을 뒤집는다.

**원더룸은 배율이 아니다.** 방어↔특방을 바꿔치기하므로 "어느 스탯을 분모로 쓰는가"를 고르는
구조적 선택이다.

또 하나의 제약이 있었다. 도구·특성·필드 배율을 구현하려면 **어느 도구가 몇 배인지 표**가
필요한데, `items.json` / `abilities.json` 이 없고 `CLAUDE.md` 9장이 게임 데이터의
파이썬 하드코딩을 금지한다. 조사 결과 챔피언스 전용 아이템 효과 목록은 공신력 있는 출처가
없었다 — championsbattledata 는 채용률 통계만 주고, champions-helper 는 생명의구슬 1.3과
단단한발톱 1.3 예시 둘뿐이며, 제3자 가이드는 수치가 서로 어긋났다.

## 선택지

### A안: 모든 보정을 하나의 배율 체인에 넣는다
- 장점: 구조가 단순하다. `CLAUDE.md` 5-2의 기존 서술을 그대로 따른다.
- 단점:
  - **틀린 값이 나온다.** 화상·구애띠를 데미지 단계에서 곱하면 스탯 단계의 floor 가 사라진다.
  - 원더룸을 표현할 수 없다. 배율이 아니기 때문이다.
  - 트릭룸처럼 데미지와 무관한 것이 섞여 들어온다.

### B안: 세 계층으로 분리하고, 도메인이 도구·특성까지 해석한다
- 장점: 호출자가 "구애스카프를 들었다"만 넘기면 끝난다. 사용이 가장 간단하다.
- 단점:
  - 도메인이 아이템·특성 데이터를 알아야 한다. 외부 의존성 0 원칙과 충돌한다.
  - 시드 데이터가 없어 지금은 파이썬에 하드코딩하는 수밖에 없다 — 9장 위반.
  - **검증되지 않은 배율이 엔진에 박힌다.** 정확도가 전부인 제품에서 가장 위험하다.

### C안: 세 계층으로 분리하고, 도메인은 **결정된 배율만** 받는다
- 장점:
  - 도메인이 순수하게 남는다. 게임 데이터를 모른다.
  - `Modifiers` 에 `screen` / `field` / `ability` / `item` 슬롯을 두면 **구조가 먼저 완성**되고,
    시드 데이터가 생기면 값만 넣으면 된다.
  - 검증 안 된 수치가 엔진에 박히지 않는다. 책임이 상위 계층으로 명확히 옮겨간다.
  - 화상만 예외로 도메인이 처리한다 — floor 의미를 엔진이 소유해야 하기 때문이다.
- 단점:
  - 호출자가 할 일이 늘어난다. "구애스카프 → 스피드 1.5" 변환을 누군가 해야 한다.
  - 그 해석 계층을 만들기 전까지는 도구 효과가 실제로 동작하지 않는다.
  - 슬롯만 있고 값이 없는 상태가 한동안 유지된다.

## 결정

**C안을 채택한다.**

- `domain/models.py` 의 `Attacker` / `Defender` 는 **이미 결정된 실수치**를 받는다.
  구애띠·돌격조끼·랭크·원더룸은 호출자가 반영한다.
- **화상만 도메인이 처리한다.** `Attacker.is_burned` 로 받아 물리 기술일 때 공격을
  기초 계산 전에 반감한다. `CLAUDE.md` 5-2의 보정 체인에서 `burn` 을 제거했다.
- `Modifiers` 는 8개 슬롯을 전부 노출한다. `stab` / `type_effectiveness` / `weather` /
  `crit` 은 엔진이 계산하고, `screen` / `field` / `ability` / `item` 은 호출자가 넘긴다.
- `applied_modifiers` 는 **1배인 보정도 전부 담는다.** "해당 없음"과 "계산을 빠뜨림"을
  구분할 수 있어야 설명이 성립한다.
- 모래바람·설경은 데미지 배율 1.0으로 둔다. 스탯 단계 효과이고 챔피언스의 정확한 규칙이
  확인되지 않았다.
- 아이템 효과 데이터(`items.json`)와 해석 계층은 **다음 작업으로 분리**한다.

## 근거

(2026-11-04, 개발자 본인 기록)

**보정을 어디까지 넣을 것인가**
챔피언스에는 날씨(쾌청·비·모래바람·설경), 벽, 트릭룸·원더룸이 모두 있고 급소 배율은 1.5배다.
필드도 있어서 그래스필드일 때 지진이 반감되고, 지저(구멍파기 등) 상태에서는 지진 위력이 2배다.
도구 효과도 잘 적용됐으면 한다.

**화상을 어디에 둘 것인가**
챔피언스 전용 자료를 따라간다.

**아이템을 어떻게 할 것인가**
아이템도 같이 적용하는 게 좋을 것 같아, 데이터를 찾아서 적용하기를 요청했다.
조사 결과 공신력 있는 챔피언스 전용 아이템 효과 목록이 없다는 점을 확인하고,
Claude 가 제안한 2단계 분리(이번에는 슬롯만, 다음에 `items.json`)에 동의했다.

## 포기한 것

- **즉시 동작하는 도구·특성·필드 효과.** 슬롯은 있지만 값을 채우는 계층이 없어
  당분간 호출자가 직접 숫자를 넘겨야 한다.
- **호출 편의.** "구애스카프를 들었다"가 아니라 "공격 실수치 1.5배를 반영한 값"을 넘겨야 한다.
  API 계층에서 이 변환을 반드시 만들어야 하고, 안 만들면 사용자가 쓸 수 없다.
- **5-2 원문과의 일치.** 보정 체인에서 `burn` 을 뺐다. 규칙 문서를 고쳐야 했다.
- **모래바람·설경의 스탯 효과.** 존재한다고 확인했지만 배율을 모르므로 구현하지 않았다.
  지금은 **없는 것처럼 동작한다** — 이 상태로 사용자에게 수치를 보여주면 모래 파티 계산이 틀린다.
- **n타(n≥2) 난수 확률.** roll 합의 분포가 필요해 아직 계산하지 않는다.
  `ko_summary` 는 "난수 2타"까지만 말하고 확률을 붙이지 않는다.

## 되돌리는 조건

- **호출 계층이 지나치게 복잡해지면**: 도구 해석을 매 호출마다 반복하게 되면,
  도메인 밖에 `BuildSpec -> (실수치, Modifiers)` 변환을 한 곳에 모은다.
  **도메인에 데이터를 넣는 쪽으로는 되돌리지 않는다.**
- **챔피언스가 본가와 다른 보정 구조로 확인되면**: 스탯 단계/데미지 단계 구분 자체를 다시 본다.
- **모래바람·설경 배율이 확인되면**: 스탯 단계 효과로 추가하고, 그때까지는
  해당 날씨에서 계산 결과에 가정을 명시하는 것을 검토한다.
