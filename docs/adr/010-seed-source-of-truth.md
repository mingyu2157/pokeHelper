# ADR-010: 마스터 데이터는 JSON이 원천이고 DB는 파생, 기본키는 showdown 문자열 id

- 상태: 채택 (2026-11-13)
- 관련: Phase 2-4, `app/db/models.py`, `scripts/load_seed_to_db.py`, `alembic/`,
  `CLAUDE.md` 1-4 / 1-5, `docs/DEVELOPMENT_GUIDE.md` 4-1
- 관련 결정: [ADR-005](005-name-mapping-defense.md) (한영 매핑), [ADR-009](009-move-data-source.md) (기술 출처)

## 맥락

Phase 2-4에서 DB 스키마를 만들면서 두 문서가 충돌했다.

- `CLAUDE.md` 1-4: **"마스터 데이터는 수집이 아니라 프로젝트가 직접 관리하는 시드 데이터
  (`backend/data/*.json`)로 둔다."** 이유는 "수집이 깨져도 계산 기능은 100% 살아있어야
  한다"였다.
- `DEVELOPMENT_GUIDE` 4-1: `pokemon` / `moves` / `abilities` / `items` 를 **정규화 테이블**로
  정의한다. 사용률 행이 FK로 포켓몬을 참조하고, 집계 쿼리가 이름을 조인해 붙인다.

둘 다 타당하다. 문제는 **"어느 쪽이 진실의 원천인가"를 정하지 않으면** 양쪽에 같은
데이터가 생기고, 어긋났을 때 무엇을 고쳐야 하는지 알 수 없다는 것이다.

Phase 2-1~2-3에서 만든 시드는 전부 JSON이고 생성기가 교차검증을 거쳐 만든다.
도메인 계층은 `app/core/seed.py`가 읽어 주입한 카탈로그를 받는다 (ADR-007).
즉 **계산 경로에 DB가 한 번도 등장하지 않는다.**

함께 결정해야 했던 것이 기본키다. 가이드는 `SERIAL` 정수 대리키에 `UNIQUE (dex_no, form_key)`
를 걸어뒀는데, Phase 2-1에서 championsbattledata가 **모든 폼에 `dex_number: null`** 을
준다는 것이 드러났다. 우리 JSON·한영 매핑·사용률 API 조인은 전부 `showdown_id`로 돈다.

## 선택지

### 진실의 원천

#### A안: JSON이 원천, DB는 파생 (적재 스크립트가 복사)
- 장점:
  - 원천이 하나다. 어긋나면 항상 DB가 틀린 것이고, 재적재하면 끝난다.
  - 계산 엔진이 DB 없이 돈다. `CLAUDE.md` 1-4의 "수집이 깨져도 계산은 살아있다"가 유지된다.
  - 시드 생성기의 교차검증(ADR-005/009)이 DB 진입 전에 이미 끝나 있다.
  - DB를 통째로 날리고 다시 만들 수 있다. 개발·테스트가 가벼워진다.
- 단점:
  - 같은 데이터가 두 곳에 존재한다. 적재를 잊으면 DB가 낡는다.
  - 마스터를 고치려면 JSON → 생성기 → 적재 3단계를 거친다. DB에서 한 줄 UPDATE 하는 것보다 번거롭다.

#### B안: DB가 원천, JSON은 초기 적재용
- 장점: 관계형 무결성과 마이그레이션 이력이 마스터까지 덮는다. 데이터가 한 곳에 있다.
- 단점:
  - **계산 엔진이 DB에 의존하게 된다.** `CLAUDE.md` 1-4의 근거가 무너진다.
  - 교차검증 로직(종족값·타입 대조, 양방향 유일성)을 마이그레이션 안으로 옮겨야 한다.
  - 시드 수정 이력이 마이그레이션 파일로 흩어져 "현재 값"을 읽기 어렵다.

#### C안: DB에 마스터를 두지 않음 (사용률 테이블에 문자열 id만 저장)
- 장점: 중복이 없다. 원천이 명확하다.
- 단점:
  - FK가 없어 **마스터에 없는 포켓몬의 수집 행이 조용히 들어온다.** 이름 매핑이 깨졌을 때
    이걸 잡아줄 장치가 사라진다.
  - "사용률 상위 20마리를 한글명과 함께" 같은 쿼리를 애플리케이션에서 조립해야 한다.

### 기본키

#### D안: `SERIAL` 정수 대리키 + `showdown_id` UNIQUE
- 장점: 관례적이다. 인덱스가 작다. 식별자가 바뀌어도 참조가 안전하다.
- 단점: ETL 단계마다 `showdown_id -> id` 조회가 끼어든다. **그 변환 지점이 전부 버그 후보다.**

#### E안: `showdown_id` 문자열을 그대로 기본키로
- 장점:
  - 변환이 없다. JSON 키 = 사용률 API 조인 키 = DB 기본키.
  - 디버깅 중 행을 보면 무엇인지 바로 읽힌다 (`garchomp` vs `447`).
- 단점:
  - 인덱스가 커진다 (이 규모에서는 무의미하다 — 263행).
  - 출처가 id를 바꾸면 FK가 걸린 행까지 전부 따라가야 한다.

## 결정

**A안 + E안.**

1. `data/*.json`이 마스터의 진실의 원천이다. `scripts/load_seed_to_db.py`가 한 방향으로만
   복사한다. **DB를 손으로 고치지 않는다** — 다음 적재에서 덮어쓰인다.
2. 계산 엔진(`app/domain/`)은 DB를 모른다. JSON 카탈로그를 주입받는다 (ADR-007 유지).
3. 마스터 테이블의 기본키는 `showdown` 식 문자열 id다. `dex_no`는 쓰지 않는다.
4. 한글명은 마스터 테이블의 `name_ko` 컬럼으로 **비정규화**한다. 원천은 여전히
   `name_map*.json`이고, 적재가 거기서 채운다. 조회마다 조인을 하나 더 붙이지 않기 위해서다.
5. 적재는 멱등하다. 시드에서 사라진 행은 **지우지 않고 보고만 한다** — 수집 데이터가
   FK로 참조 중일 수 있고, 조용히 지우면 그 행까지 CASCADE로 날아간다.
6. 도구의 `name_ko`는 nullable이다. 한영 매핑이 아직 없고(Phase 2-3c), 영문명을 대신
   넣으면 "한글명이 있다"고 거짓말하는 행이 생긴다.

## 포기한 것

- **마스터의 관계형 무결성 일부.** JSON에서 잘못된 값이 들어오면 DB는 막지 못한다 —
  CHECK 제약이 잡을 수 있는 범위(타입 중복, 변화 기술의 위력, 성격 보정 쌍)까지만 방어한다.
  나머지는 생성기의 교차검증이 책임진다.
- **DB에서 바로 고치는 편의.** 오타 하나를 고치려 해도 JSON → 생성기 → 적재를 거친다.
- **id 안정성.** 출처가 `showdown_id`를 바꾸면 FK가 걸린 수집 행까지 영향을 받는다.
  정수 대리키였다면 매핑 테이블만 고치면 됐다.
- **적재 누락 가능성.** JSON을 고치고 적재를 잊으면 DB가 낡은 채로 남는다. 이걸 잡는
  장치는 아직 없다 (아래 되돌리는 조건 참조).

## 되돌리는 조건

- **적재 누락이 실제로 사고를 내면** 적재 상태를 검사하는 장치를 넣는다 —
  시드 파일 해시를 DB에 기록하고 불일치 시 기동을 막는 쪽이 유력하다.
  지금은 문제가 난 적이 없어서 만들지 않았다.
- **사용자 입력 데이터가 마스터를 참조하기 시작하면**(Phase 5 파티 저장) id 안정성이
  중요해진다. 그때 `showdown_id` 변경 이력을 추적할 필요가 생기면 E안을 재검토한다.
- **출처가 `showdown_id` 체계를 바꾸면** 즉시 재검토한다. 지금은 263종이 전부 유일하고
  안정적이라는 관찰에 기대고 있다.
- **마스터가 수만 행 규모가 되면** 문자열 기본키의 인덱스 비용을 다시 잰다.
  (현재 263 + 515 + 202 + 25 + 22 = 1,027행이라 고려 대상이 아니다.)

## 결과

**2026-11-13: `pokemon_learnset` 을 뺀 판단이 틀렸다.**

이 ADR 작성 시점에 learnset 을 "출처 미정, 데이터 없음"을 이유로 스키마에서 제외했다.
그런데 **championsbattledata 인덱스의 `learnableMoveNames` 에 처음부터 있었다.**
우리가 Phase 2-1부터 매번 받아오던 바로 그 응답이다. 엔트리의 `summary` 안쪽만
파고들고 최상위 키를 끝까지 나열해보지 않아서 놓쳤다.

같은 종류의 실수를 두 번 했다 — Phase 2-2 에서도 "learnset 은 op.gg 에도 API 에도
없다"고 판단하고 외부 출처(gamewith.ai 등)를 후보로 적어뒀었다.

되살리면서 16,037쌍이 들어갔고, **그 과정에서 기술표의 누락도 드러났다.**
learnset 이 참조하는 `전기쇼크` 가 `moves.json` 515개에 없었다. op.gg 목록 페이지가
빠뜨린 것이고, 상세 페이지에는 챔피언스 수치가 있었다. 즉 **A안(JSON 원천)의
"교차검증이 DB 진입 전에 끝나 있다"가 실제로 작동했다** — 시드끼리 맞춰보는 자리가
있었기 때문에 잡혔다. DB 가 원천이었다면 두 데이터가 각자 마이그레이션으로
들어와 이런 대조를 할 자리가 없었다.

**배운 것: 가진 데이터끼리 교차시킬 수 있는 자리를 먼저 찾는다.** 새 출처를 늘리는
것보다 싸고, 이번처럼 이미 있는 데이터가 서로의 검증 장치가 된다.
