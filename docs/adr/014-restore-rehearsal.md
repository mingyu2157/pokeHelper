# ADR-014: 복구 리허설을 전용 DB 에서 스크립트 그대로 돌린다

- 상태: 채택 (2026-11-17)
- 관련: 운영 체계, `backend/scripts/backup.sh`, `backend/scripts/restore.sh`, `backend/tests/rehearsal/`
- 관련 결정: [ADR-012](012-airflow-docker-operator.md) (프로필로 감싸는 선례), [ADR-013](013-attribution-contract.md) (선언과 집행은 다르다)

## 맥락

백업 스크립트는 흔하고 **복구를 검증한 기록은 드물다.** 그리고 검증되지 않은 백업은
백업이 아니다 — 복구가 필요한 날에야 안 되는 것을 알게 된다.

이 저장소는 다른 영역에서 "선언과 집행은 다르다"를 이미 두 번 겪었다.
[ADR-013](013-attribution-contract.md) 에서 요청 간격 상수가 `1.0` 으로 선언돼 있고
설계 체크리스트에 체크까지 돼 있었는데 실제 호출 경로에서는 0초였다. 백업도 같은
모양이 될 수 있다 — `pg_dump` 를 부르는 스크립트가 있는 것과 그 산출물로 복구가
되는 것은 별개다.

그래서 **복구를 테스트로 증명**하기로 했고, 두 가지를 정해야 했다.

1. 리허설을 **어디서** 돌릴 것인가 — 리허설은 `DROP TABLE` 과 전체 복구를 한다
2. 테스트가 **무엇을** 실행할 것인가 — `pg_dump` 인가 우리 스크립트인가

1번이 문제인 이유: 통합테스트 93개가 `get_settings()` 의 `DATABASE_URL` 하나로
개발 DB(`db` 서비스)를 공유한다. 거기서 DROP 을 하면 개발 DB 와 시드가 날아가고
나머지 테스트가 전부 깨진다.

## 선택지

### 1. 리허설 DB 를 어디서 얻는가

#### A안: testcontainers 로 테스트가 Postgres 를 직접 띄운다
- 장점:
  - 테스트가 자기 인프라를 들고 있어 완전히 자기완결적이다. 사전 준비가 없다.
  - 업계 표준 도구를 쓴 경험이 남는다.
- 단점:
  - 테스트는 컨테이너 안에서 돈다(CLAUDE.md 6장). 컨테이너가 컨테이너를 띄우려면
    **`backend` 에 `/var/run/docker.sock` 을 마운트**해야 한다.
    [ADR-012](012-airflow-docker-operator.md) 에서 "로컬에서만 받아들이고 운영에서는
    반드시 바꾼다"고 적은 트레이드오프를 **한 군데 더 늘린다.**
  - 새 의존성이 하나 늘고, 첫 실행이 이미지 받는 시간만큼 느리다.

#### B안: compose 에 전용 서비스(`db-rehearsal`)를 두고 프로필로 감싼다
- 장점:
  - **docker.sock 을 건드리지 않는다.** 새 파이썬 의존성도 0 이다.
  - 자체 볼륨이라 개발 DB 와 완전히 격리된다. 아무리 망가뜨려도 안전하다.
  - `--profile rehearsal` 로 평소 `docker compose up` 에 영향이 없다 — ADR-012 가
    Airflow 에 쓴 방식과 같아서 일관성이 있다.
- 단점:
  - 테스트가 **자기 인프라를 들고 있지 않다.** 컨테이너를 먼저 띄워야 한다.
  - 그래서 "띄우는 걸 잊으면 조용히 건너뛰는" 실패 모드가 생길 수 있다.

#### C안: 양쪽을 다 만들고 비교한다
- 장점: 실측 비교가 기록으로 남는다.
- 단점: 세션이 1~2일로 늘어난다. 지원 마감이 가까워 감당할 수 없다.

### 2. 테스트가 무엇을 실행하는가

#### D안: 테스트가 `pg_dump` / `pg_restore` 를 직접 호출한다
- 장점: 간단하고, 스크립트가 없어도 돈다.
- 단점:
  - **`backup.sh` 에 대해 아무것도 증명하지 않는다.** PostgreSQL 이 동작한다는
    것만 확인된다. 그건 PostgreSQL 팀의 일이다.
  - 스크립트가 플래그를 바꾸거나 깨져도 테스트는 계속 초록이다.

#### E안: 테스트가 `backup.sh` / `restore.sh` 를 subprocess 로 실행한다
- 장점:
  - **스크립트가 테스트 대상이 된다.** 검증 대상이 우리 백업 절차와 일치한다.
  - 운영자가 치는 명령과 테스트가 돌리는 명령이 같다.
- 단점:
  - 스크립트가 도는 컨테이너에 `pg_dump` 가 있어야 한다 → dev 이미지에 DB
    클라이언트를 설치해야 한다.
  - 표준출력 형식이 테스트와 운영 자동화의 계약이 된다. 바꾸면 양쪽이 깨진다.

## 결정

**1번은 B안, 2번은 E안.**

세부 사항:

1. `db-rehearsal` 서비스 + `rehearsal-pgdata` 볼륨, `profiles: ["rehearsal"]`.
   포트를 열지 않는다 — 호스트 5432 는 개발 DB 가 쓴다.
2. 리허설 스위트는 **기본 실행에서 제외**한다 (`addopts` 의 `-m "not rehearsal"`).
   프로필로 가려진 컨테이너가 필요해서, 포함하면 평소 `pytest` 가 환경에 따라
   빨갛게 된다. 대신 명시적으로 불렀을 때 컨테이너가 없으면 **건너뛰지 않고
   실패한다** — 조용히 건너뛰는 리허설은 리허설을 안 한 것과 같다 (B안의 단점에
   대한 대응이다).
3. 검증은 네 층이다. 층마다 **놓치는 것이 다르다.**

   | 층 | 단정 | 이 층이 없으면 놓치는 것 |
   |---|---|---|
   | 1 | 행 수 | — |
   | 2 | 내용 체크섬 | 행 수는 같고 값이 깨진 복구 |
   | 3 | 제약·인덱스 | 데이터는 맞지만 **무결성 장치가 없는** DB |
   | 4 | 시퀀스 | 복구 직후 첫 INSERT 의 PK 충돌 |

   3층을 넣은 이유가 이 프로젝트에 특유하다. Phase 2-4 의 핵심 장치가 부분 유니크
   인덱스(`uq_meta_snapshot_active`)인데, 복구 후 그게 없으면 "활성 스냅샷은
   (레귤레이션, 포맷)당 하나"라는 불변식이 **데이터가 완벽한 상태로** 사라진다.
   그래서 정의 비교에 그치지 않고 **위반을 실제로 넣어 거부되는지** 본다.
4. "파괴가 실제로 일어났는지"를 먼저 단정한다. DROP 이 조용히 실패하면 나머지
   단정이 전부 공짜로 통과한다 — 아무것도 검증하지 않은 채로.
5. **DB 클라이언트의 메이저 버전을 서버와 맞춘다.** 처음엔 "상위 클라이언트는
   하위 서버에 괜찮다"고 보고 Debian 기본 패키지(17)를 썼는데, 덤프에는 맞고
   **복구에는 틀렸다.** 리허설 테스트가 첫 실행에서 잡았다. 그래서 PGDG 저장소에서
   서버와 같은 16 을 받는다. 자세한 경과는 JOURNAL 2026-11-17 참조.
6. 스크립트는 `backend/scripts/` 에 둔다. 저장소 루트에 `scripts/` 를 새로 만들었다가
   **기존 `backend/scripts/` 패키지를 마운트로 가려** 통합테스트를 깨뜨렸다.
   운영 CLI 의 집은 이미 거기다 (`run_ingest.py`, `cleanup_snapshots.py`).

## 근거

두 결정 모두 **검토 결과 Claude 제안에 동의**.

- 리허설 DB 를 전용 compose 서비스로 두는 것 (B안)
- 테스트가 스크립트를 subprocess 로 실행하는 것 (E안)

## 포기한 것

- **testcontainers 경험.** 업계에서 널리 쓰는 도구를 안 써봤다는 공백이 남는다.
  "비교해보고 안 썼다"가 아니라 **"docker.sock 을 늘리지 않으려고 안 썼다"** 가
  정확한 서술이다. 성능·사용감을 실측해 비교한 적은 없다.
- **테스트의 자기완결성.** 리허설은 사람이 컨테이너를 먼저 띄워야 돈다.
  2번 항목으로 조용한 통과는 막았지만, **아무도 안 돌리는 것은 막지 못한다.**
- **CI 에서의 자동 실행.** 지금은 로컬에서 손으로 돌린다. CI 에 올리려면 러너에서
  compose 프로필을 띄우는 단계가 필요하고, 그건 아직 없다. 즉 이 리허설은
  **회귀를 자동으로 막아주지 않는다.** 사람이 기억해야 한다.
- **운영 환경과의 동일성.** 리허설은 compose 안의 Postgres 16 에서 돈다. 운영이
  RDS 라면 복구 절차 자체가 다르다(스냅샷 복원). 이 리허설이 증명하는 것은
  **논리 백업의 왕복**이고, 운영 백업 전략 전체가 아니다.
- **ROLE 백업.** `pg_dump` 는 데이터베이스 하나만 덤프한다. 계정과 클러스터 전역
  권한은 들어 있지 않아, 이 덤프만으로 빈 서버에 완전 복구가 되지 않는다.
  알려진 공백이고 계정 분리 작업에서 `pg_dumpall --roles-only` 로 다룬다.

## 되돌리는 조건

- **CI 에 올릴 때 재검토한다.** GitHub Actions 러너에서 compose 프로필을 띄우는 것이
  번거로우면 testcontainers 가 더 맞을 수 있다 — 러너에서는 docker.sock 노출의
  위험 성격이 로컬과 다르다(일회용 VM). 그때 A안을 다시 본다.
- **리허설이 다른 DB 를 더 필요로 하게 되면** (예: 계정별 권한 리허설) 전용 서비스를
  계속 늘릴지, 테스트가 띄우게 할지 다시 정한다. 서비스가 셋을 넘으면 B안의
  단순함이 사라진다.
- **운영 배포 대상이 정해지면** (ADR-001 의 배포는 아직 미결이다) 그 환경의 백업
  방식에 맞는 리허설을 따로 만든다. RDS 면 스냅샷 복원 리허설이고, 이 논리 백업
  리허설은 "애플리케이션 수준 복구" 용도로 남는다.
- **이 리허설이 6개월간 한 번도 실행되지 않았다면** 자동화되지 않은 검증은
  검증이 아니라는 뜻이다. CI 에 올리거나, 올릴 수 없다면 이 ADR 의 전제를 다시 쓴다.

## 결과

### 2026-11-17 — 첫 실행이 "백업은 되는데 복구가 안 되는" 조합을 잡았다

`pg_restore 17 → 서버 16` 이 `transaction_timeout` 때문에 실패했다. 덤프는 정상
생성되므로 **복구를 시도하지 않으면 영원히 모르는** 결함이었다. 이 한 건으로
E안(스크립트를 테스트 대상으로 삼는다)의 비용은 회수됐다.

### 2026-11-25 — 약속한 코드가 운영 이미지에 없었다

[ADR-020](020-production-topology.md) 세부사항 5 가 "운영판은 스냅샷으로 복원하고
**같은 4층을 비교**로 그대로 옮긴다"고 썼다. 그런데 그 4층은
`tests/rehearsal/conftest.py` 안에 있었고 **운영 이미지는 `tests/` 를 복사하지
않는다** (`backend/Dockerfile` prod 스테이지). 약속한 "같은 4층"을 운영에서 돌릴
방법이 11일간 없었다.

`backend/scripts/db_state.py` 로 추출하고 리허설이 import 하게 했다 —
`COPY ./scripts` 가 이미 있어 운영 이미지에 자동으로 실린다. 후보 셋 중
"운영용을 따로 쓴다"를 버린 이유는 **두 구현이 갈라지면 '복구가 맞다'는 말의
뜻이 환경마다 달라지기** 때문이다. 리허설 33건이 그대로 통과한 것이 추출이
깨끗했다는 증거다. 경과는 JOURNAL 2026-11-25 참조.

덤으로 `tests/unit/test_db_state_compare.py` 를 새로 썼다. 리허설은 **성공한
복구만** 만들어 내므로 "비교가 실패를 잡는지"를 증명하지 못한다 — 층 하나가
아무것도 안 보고 있어도 리허설은 초록이다. 망가진 복구를 손으로 만들어 층마다
들이민다. 현재 45건.

### 2026-11-26 — ★ `되돌리는 조건` 이 실제로 발동했다

이 ADR 은 `되돌리는 조건` 에 이렇게 썼다 — "운영 배포 대상이 정해지면 그 환경의
백업 방식에 맞는 리허설을 따로 만든다. **RDS 면 스냅샷 복원 리허설**이고, 이 논리
백업 리허설은 '애플리케이션 수준 복구' 용도로 남는다." 그리고 `포기한 것` 에는
"이 리허설이 증명하는 것은 **논리 백업의 왕복**이고, 운영 백업 전략 전체가
아니다"라고 적었다.

[ADR-020](020-production-topology.md) 으로 대상이 RDS 로 정해졌고, 9일 뒤 그 조건을
집행했다. **재검토 조건을 미리 정의해 둔 것이 그 자체로 작동했다.**

RDS PITR 리허설 실측:

| 항목 | 값 |
|---|---|
| 복구 가능 구간 | `2026-11-24T01:32:40Z` ~ `2026-11-26T12:51:46Z` (2.5일) |
| 보존 설정 | 7일 — ★ **보존 기간 ≠ 되돌릴 수 있는 기간** |
| 복원 (명령 → `available`) | **34분 6초** (그중 22분은 복원 후 자동 백업) |
| 전환 (시크릿 → 재배포 → 응답) | **4분 53초** |
| 1층 행 수 | 테이블 10개 / 17,220행 **완전 일치** |
| 2층 체크섬 | **완전 일치** |
| 3층 제약·인덱스 | 제약 27개 / 인덱스 21개 **완전 일치** |
| 4층 시퀀스 | 차이 2건 → ★ **PostgreSQL 설계였다** ([ADR-023](023-sequence-comparison-direction.md)) |

★ **4층이 정상 복구를 실패로 판정했다.** `nextval` 의 WAL 기록 주기(32회) 때문에
복원본의 `last_value` 가 최대 32 앞선다. 판정을 방향으로 바꿨고, 그 결정이
ADR-023 이다. 이 ADR 의 세부사항 3 이 정한 "4층" 자체는 유효하지만 **4층의
판정 방식은 복구 메커니즘에 따라 다르다**는 것이 드러났다.

★ **그리고 `포기한 것` 의 ROLE 공백이 PITR 경로에는 없었다.** `champs_app` 으로
복원본에 접속해 10개 테이블을 모두 읽었다. 즉 **PITR 복원본은 DB 계정과
비밀번호를 그대로 유지한다** — AWS 문서가 말하지 않던 칸이고, 이 리허설이
메웠다. `pg_dump` 가 담지 못하는 것을 PITR 는 담는다.

### 아직 메우지 못한 공백

- **CI 자동 실행은 여전히 없다.** 로컬 리허설도, 이 운영 리허설도 사람이
  기억해야 돈다. `포기한 것` 의 "아무도 안 돌리는 것은 막지 못한다"는 그대로다.
- ★ **쓰기가 있는 전환은 훈련하지 않았다.** 복원본이 받은 트래픽이 전부
  읽기였다. 실제 전환이라면 복원본에 쓰기가 쌓이고, 되돌릴 때 **그 쓰기를
  잃는다.** 이 훈련은 그 문제를 다루지 않았다.
- **DSN 셋 중 하나만 바꿨다.** `DATABASE_URL` 만 복원본으로 돌렸고
  `MIGRATION_DATABASE_URL` 은 원본을 가리킨 채였다. 실제 전환은 셋 다 필요하다.
- **리전 장애는 훈련하지 않았다.** 크로스리전 스냅샷 복사는 설계에만 있다.
- **`backing-up` 중 접속 가능 여부를 측정하지 않았다.** 이벤트 시각으로 추론만
  했다. 다음 리허설에서는 상태 대신 `psql` 접속을 폴링한다.
