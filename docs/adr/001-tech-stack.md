# ADR-001: 기술 스택 선정 (FastAPI · Next.js · PostgreSQL)

- 상태: 채택 (2026-09-20)
- 관련: Phase 0, `CLAUDE.md` 2장
- 기록: 소급 작성 (2026-11-03). 결정 당시 문서화하지 않아 뒤늦게 남긴다.
- 범위 밖: **배포 인프라는 이 ADR에서 결정하지 않는다.** 미결 상태이며 Phase 6에서 별도 ADR로 다룬다.

## 맥락

포켓몬 챔피언스 실전배틀 보조 SaaS를 만들기로 하고, 첫 줄을 쓰기 전에 스택을 정해야 했다.

그 시점에 확정돼 있던 제약은 네 가지였다.

1. **계산 엔진이 제품의 심장이다.** 데미지·실수치·노력치 솔버가 전부 결정론적 순수 함수여야 하고,
   정확도가 신뢰의 전부다. 기존 계산기와 값이 어긋나면 서비스의 존재 이유가 사라진다.
2. **LLM은 해석만 한다.** 숫자는 엔진이 만들고 LLM은 설명만 붙인다. LLM 호출이 실패해도
   계산 기능은 살아 있어야 하므로 두 경로가 분리된 구조가 필요했다.
3. **파티 공유 페이지의 SEO가 유일한 마케팅 채널이다.** 광고 예산이 없고 커뮤니티 확산과
   검색 유입에 의존한다.
4. **포트폴리오를 겸한다.** 1인이 운영 가능한 수준이어야 한다.

결정 주체는 1인 개발자이고, 선택지와 장단점은 **AI 어시스턴트와의 기획 대화에서 제시받았다.**
독립적인 벤치마크나 프로토타입 비교는 수행하지 않았다.

## 선택지

> ⚠️ **이 절은 2026-11-03에 소급 정리한 것이다.** 결정 당시 검토한 목록을 그대로 복원한 것이
> 아니라, 그때 고려된 축을 사후에 재구성한 내용이다. 당시 어떤 대안이 어떤 형태로 제시됐는지는
> 기록이 남아 있지 않다.

### 백엔드

| 안 | 장점 | 단점 |
|---|---|---|
| **Python + FastAPI** | 계산 로직이 수식처럼 읽힌다. 타입힌트 + Pydantic으로 스키마 강제, OpenAPI 자동 생성. LLM 생태계가 파이썬 중심 | 프론트와 언어가 갈려 타입 공유에 생성 단계가 필요. 런타임 성능이 Go·Rust보다 낮음 |
| Node.js + NestJS | 프론트와 언어 통일. 도메인 계산을 프론트에서 재사용 가능 | 계산 코드가 장황해지고, Number 단일 타입이 정수·소수 처리에 불리 |
| Django + DRF | 관리자·인증·마이그레이션 기본 제공 | 동기 중심이라 LLM I/O 대기에 불리. 프레임워크 구조가 도메인 격리 설계와 마찰 |
| Go | 성능과 배포 용이성 최상 | LLM·데이터 생태계가 약하고 1인 개발 속도가 느림 |

### 프론트엔드

| 안 | 장점 | 단점 |
|---|---|---|
| **Next.js (App Router)** | 공유 페이지를 SSR로 뽑아 검색 노출. 제약 3번에 직접 대응 | 서버/클라이언트 컴포넌트 경계 개념이 복잡. 서버 런타임이 필요 |
| React SPA (Vite) | 구조 단순, CDN만으로 배포 | 공유 페이지가 검색에 안 잡힘 — 유일한 유입 경로를 포기 |

### DB

PostgreSQL 16. 관계형 데이터가 중심이고 가변 스펙은 JSONB로 흡수한다.
**별도 NoSQL을 두지 않기로 한 판단은 ADR-004에서 따로 다룬다.**

## 결정

- 백엔드: **Python 3.12 + FastAPI**
- 프론트: **Next.js (App Router) + TypeScript** — 채택 시점 버전은 15
- DB: **PostgreSQL 16**, 캐시: Redis 7
- 배포: **미결.** Phase 6에서 결정한다.

## 근거

(2026-11-03, 개발자 본인 기록)

**백엔드 — FastAPI(Python)를 고른 이유**
TypeScript보다 Python 숙련도가 더 있다고 판단했다.
여기에 "계산 로직이 Python에서 읽기 쉽다"는 에이전트의 의견이 더해져 FastAPI로 정했다.

**프론트 — Next.js를 고른 이유**
에이전트의 추천을 그대로 따랐다. 프론트엔드에 큰 관심이 없어서 별도로 판단하지 않았다.

**배포**
아직 정하지 않았다. 기획 초안에 ECS Fargate라고 적혀 있지만 초안일 뿐이고,
프로젝트를 진행하면서 결정하기로 했다.

**선택지를 직접 비교했는가**
하지 않았다. 에이전트가 제시한 선택지와 장단점을 보고 결정했다.

## 포기한 것

- **언어 통일.** 프론트·백엔드가 갈려서 타입을 OpenAPI 생성 단계로 이어야 한다.
  도메인 계산을 프론트에서 재사용하는 길도 막힌다 — 클라이언트 측 즉시 계산이 필요해지면
  파이썬 로직을 TypeScript로 옮겨 적는 수밖에 없고, 그 순간 "진실의 원천이 하나"라는 원칙이 깨진다.
- **런타임 성능 상한.** 노력치 솔버의 탐색 공간이 커지면 파이썬이 먼저 한계에 닿는다.
- **Django 생태계.** 관리자 페이지·인증을 기본으로 얻는 길을 버리고 직접 조립하기로 했다.
- **검증된 비교의 부재.** 대안을 직접 돌려보지 않았으므로, 선택이 틀렸을 경우
  "해봤는데 아니었다"가 아니라 "안 해봤다"가 된다. 이 리스크를 안고 간다.

## 되돌리는 조건

- **계산 성능**: 노력치 솔버 또는 매치업 매트릭스의 p95 응답이 목표치를 넘기고 파이썬 수준의
  최적화로 해결되지 않으면, 계산 핵심만 Rust/Go 확장으로 분리한다. 전면 교체가 아니다.
- **SEO 효과**: 공유 페이지의 검색 유입이 운영 3개월 시점에 실측으로 무의미한 수준이면
  SSR의 근거가 사라진다. 그때 SPA + CDN 전환을 재검토한다.
- **LLM 응답 시간**: 동기 요청으로 감당이 안 되면 큐 기반 비동기로 요청 모델을 바꾼다.
  이 경우 스택이 아니라 API 설계가 바뀐다.
