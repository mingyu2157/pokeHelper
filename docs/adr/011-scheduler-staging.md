# ADR-011: 수집 스케줄링을 CLI 먼저, Airflow는 다음 단계로 분리

- 상태: 채택 (2026-11-13)
- 관련: Phase 2-6, `backend/scripts/run_ingest.py`, `backend/scripts/cleanup_snapshots.py`
- 관련 결정: [ADR-006](006-data-pipeline-stack.md) (데이터 파이프라인 스택)

## 맥락

Phase 2-5에서 ETL 본체(`services/ingest.py`)와 정리 함수(`delete_expired`)를 만들었다.
남은 것은 **그것들을 주기적으로 실행하는 장치**다.

`DEVELOPMENT_GUIDE`와 이전 결정(ADR-006)에서 **"Airflow는 Phase 2에서 사용"** 으로
잠정 합의해뒀다. 도입 이유도 솔직하게 기록돼 있다 — 운영 효율보다 **데이터 엔지니어링
학습과 경험**이 목적이다.

그런데 지금 돌려야 할 작업은 두 개뿐이다: 하루 한 번 수집, 만료 스냅샷 정리.
Airflow를 들이면 컨테이너 2~3개(scheduler, webserver, 메타데이터 DB)와 메모리 1~2GB가
늘어난다. **작업 두 개를 돌리려고 지불하는 비용치고는 크다.**

동시에, 이 프로젝트의 원칙 하나가 걸린다 — `CLAUDE.md` 1-4의 **"수집이 깨져도 계산
기능은 100% 살아있어야 한다"**. 스케줄러가 수집의 유일한 실행 경로가 되면,
스케줄러 장애가 곧 수집 장애가 된다.

## 선택지

### A안: Airflow를 바로 도입하고 DAG에서 수집 로직을 직접 호출
- 장점: 한 번에 끝난다. 중간 산출물이 없다.
- 단점:
  - 수집 로직이 DAG 안에 들어가면 **Airflow 없이는 수집을 돌릴 수 없다.**
    로컬에서 한 번 돌려보려고 Airflow를 띄워야 한다.
  - Airflow 도입과 ETL 실행 경로 설계가 한 브랜치에 섞여 리뷰 단위가 커진다.
  - 실패 시 원인이 "수집이 틀렸나 / DAG 설정이 틀렸나"로 갈려 디버깅이 느리다.

### B안: CLI 커맨드만 만들고 스케줄링은 cron/수동
- 장점: 작고 즉시 된다. 외부 의존이 없다.
- 단점:
  - 실패가 **조용하다.** 로그를 직접 열어야 안다.
  - 재시도·작업 간 의존(수집 성공 후 정리)을 직접 짜야 한다.
  - ADR-006의 학습 목적이 달성되지 않는다.

### C안: CLI를 먼저 만들고, 다음 단계에서 Airflow가 그 CLI를 호출
- 장점:
  - **Airflow DAG가 얇아진다.** DAG는 "언제, 몇 번 시도할지"만 알고 수집 로직은 모른다.
  - Airflow 없이도 수집이 돈다. 스케줄러 장애가 수집 불능으로 번지지 않는다.
  - 두 브랜치로 나뉘어 각각 작다. 실패 시 원인 구분이 쉽다.
  - 나중에 Airflow를 걷어내거나 다른 스케줄러로 바꿔도 진입점은 그대로다.
- 단점:
  - 두 단계라 Airflow 도입이 한 사이클 늦어진다.
  - 중간 상태(cron으로 돌릴 수 있는 CLI)가 잠시 존재한다.

## 결정

**C안.** 이번 단계에서 CLI 두 개를 만들고, Airflow는 다음 브랜치에서 이 CLI를 호출한다.

```
python -m scripts.run_ingest --format Singles --limit 50
python -m scripts.cleanup_snapshots [--dry-run]
```

세부 사항:

1. **종료 코드로 상태를 구분한다.** 이게 이 결정의 핵심이다.
   | 코드 | 뜻 |
   |---|---|
   | 0 | 활성 스냅샷이 갱신됐다 |
   | 1 | 수집 자체가 실패했다 (네트워크·HTTP·형식) |
   | 2 | 수집·적재는 됐지만 **활성화하지 못했다** |
   2번이 가장 위험하다 — 데이터는 저장됐지만 서비스가 보는 메타는 그대로다.
   이걸 성공으로 끝내면 스케줄러 UI가 초록으로 뜨고 매핑이 깨진 걸 며칠간 모른다.
2. **레귤레이션은 수집한 시즌 코드로 자동 생성한다.** 레귤레이션 정보를 주는 출처가
   없다. 자동 생성임을 `rules.auto_created`에 기록하고, 사람이 이름·기간을 채우면
   이후 수집이 덮어쓰지 않는다.
3. **시즌 코드는 구체 이름이어야 한다.** API가 주는 `"Current"`는 최신 시즌을 가리키는
   **별칭**이다(`seasons: ["Current", "M7", ...]`, 실제 폴더는 `M7`). 별칭을 그대로
   쓰면 시즌이 넘어갈 때 같은 레귤레이션에 다른 시즌 데이터가 섞인다.
   별칭을 벗길 수 없으면 추측하지 않고 실패한다.
4. `--dry-run`을 정리 커맨드에 둔다. 삭제는 되돌릴 수 없다.

## 포기한 것

- **Airflow 경험을 한 사이클 늦춘다.** ADR-006의 학습 목적이 그만큼 미뤄진다.
- **중간 상태가 생긴다.** 다음 브랜치 전까지 수집은 사람이 돌려야 한다.
  그동안 수집이 멈춰도 알아채는 장치가 없다.
- **재시도·작업 의존이 아직 없다.** 수집이 실패하면 그걸로 끝이고, 다음 실행까지
  이전 스냅샷으로 서비스한다. (설계상 안전하지만 자동 복구는 아니다.)

## 되돌리는 조건

- **작업이 5개를 넘거나 작업 간 의존이 복잡해지면** CLI 나열로는 관리가 안 된다.
  그 시점에 Airflow 도입을 앞당긴다.
- **Airflow 도입 후 DAG가 두꺼워지기 시작하면** 이 결정의 전제(DAG는 얇다)가 깨진 것이다.
  로직이 DAG로 새어 들어가고 있다는 뜻이므로 CLI 쪽으로 되돌린다.
- **로컬 메모리가 감당 안 되면** Airflow 대신 cron 또는 GitHub Actions 스케줄로 간다.
  진입점이 CLI라 전환 비용이 작다 — 그게 C안을 택한 이유이기도 하다.
