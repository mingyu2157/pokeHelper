# ADR-016: 관측 지표 선정과 경보 임계치

- 상태: 채택 (2026-11-17)
- 관련: 운영 체계, `infra/observability/`, `backend/app/services/observability.py`
- 관련 결정: [ADR-012](012-airflow-docker-operator.md) (Airflow·DockerOperator),
  [ADR-014](014-restore-rehearsal.md) (복구 리허설), [ADR-015](015-least-privilege-db-accounts.md) (DB 계정 분리),
  [ADR-013](013-attribution-contract.md) (선언과 집행은 다르다)

## 맥락

운영 상태를 아는 방법이 `docker compose logs` 뿐이었다. 그래서 세 질문에 답할 수 없었다.

1. **지금 느린가?** 비교할 기준선이 없다. "원래 이랬나"를 판단할 수 없다.
2. **수집이 멈췄나?** Airflow UI 를 열어야 알고, 그마저 "DAG 성공"만 보여준다.
   활성 스냅샷이 갱신됐는지는 별개 사실이다.
3. **무엇이 죽었나?** 컨테이너가 재시작을 반복해도 보고 있지 않으면 모른다.

`docs/RUNBOOK.md` 의 `6. API 응답 지연` 항목이 **`❌ 미검증`** 으로 비어 있던 것도
같은 이유다. 지연을 측정한 적이 없어서 1차 대응에 쓸 숫자가 없었다.

작업에 들어가기 전에 먼저 **측정**했다. 추측한 임계치로 만든 경보는 울려도
그게 이상인지 평소인지 구분할 수 없다.

| 케이스 | p50 | p95 | 최대 |
|---|---|---|---|
| `GET /health` | 2.6ms | 16.7ms | 22.5ms |
| `POST ev-tune` (outspeed 1개) | 3.3ms | 5.7ms | 19.0ms |
| `POST ev-tune` (survive 4개) | 55.8ms | — | 74.3ms |
| `POST ev-tune` (survive 7개) | 442ms | — | — |
| `POST ev-tune` (survive 8개 = 허용 최대) | **2,215ms** | 2,293ms | 2,509ms |

측정에서 두 가지가 드러났다.

- 솔버가 **정상 입력 범위 안에서 2.2초**를 쓴다. 원인은 `_best_combination` 의
  데카르트 곱이고 제약 8개면 390,625 조합이다 (JOURNAL 2026-11-17).
  이 ADR 의 범위가 아니지만 **임계치 선택을 지배한다.**
- 따라서 엔드포인트 하나의 임계치로는 안 된다. 수 ms 기준으로 잡으면 정상
  솔버 호출마다 울리고, 2.5초 기준으로 잡으면 API 가 10배 느려져도 조용하다.

## 선택지

### 1. ETL 신선도 지표를 어디서 만드는가

배치 작업은 스크랩 대상이 될 수 없다. 네 가지 방법이 있었다.

#### A안: Pushgateway
- 장점: 표준적인 방법. 배치가 끝날 때 값을 밀어넣는다.
- 단점:
  - 컴포넌트가 하나 늘고, 상태를 들고 있어서 자체로 장애점이 된다.
  - **DAG 의 종료 코드를 측정한다.** 수집이 "성공"했지만 활성 전환이 안 돼
    서비스가 낡은 메타를 보는 상태를 **초록으로 본다.**

#### B안: postgres_exporter 커스텀 쿼리 (`--extend.query-path`)
- 장점: 익스포터가 이미 있다. SQL 한 줄로 끝난다.
- 단점: v0.17.1 에서 **DEPRECATED** 다 (`--help` 로 확인).
  핵심 지표를 폐기 예정 플래그에 건다.

#### C안: `sql_exporter` 를 추가한다
- 장점: 커스텀 SQL 전용 도구. 유지되는 경로다.
- 단점: 익스포터가 넷이 된다. 지표 하나를 위해 컴포넌트를 늘린다.

#### D안: 우리 앱의 `/metrics` 가 DB 를 읽어 내보낸다
- 장점:
  - **과정이 아니라 결과를 측정한다.** "서비스가 바라보는 데이터가 얼마나
    오래됐는가" 는 DAG 의 종료 코드가 아니라 DB 의 상태다.
  - 컴포넌트가 늘지 않는다.
  - **pytest 로 검증할 수 있다.** 익스포터 설정은 테스트할 수 없다.
- 단점:
  - `/metrics` 가 DB 에 의존한다. 느리거나 죽으면 스크랩이 같이 영향받는다.
  - 지표 노출 코드가 애플리케이션에 들어온다.

### 2. 지연 히스토그램 버킷

#### E안: 라이브러리 기본값
- 장점: 설정이 없다.
- 단점: 경로별 버킷이 `(0.1, 0.5, 1.0)` 셋뿐이다. **2.2초가 전부 `+Inf` 로
  들어가서** 1.1초와 60초가 같은 칸에 있다. 경로별 `histogram_quantile` 이
  무의미해진다 — 정작 느린 엔드포인트 하나를 못 보는 대시보드가 된다.

#### F안: 실측 분포에 맞춘 버킷
- 장점: 측정한 범위(2.6ms ~ 2.5초) 전체에 해상도가 있다.
- 단점: 계열 수가 늘어난다. 솔버를 고치면 상단 버킷이 비게 되어 다시 봐야 한다.

### 3. 익스포터 계정의 권한 (ADR-015 와 충돌)

`postgres_exporter` 를 `champs_read` 로 돌리니 `wal` 콜렉터가 15초마다 실패했다.
`pg_ls_waldir()` 가 `pg_monitor` 를 요구한다.

#### G안: `champs_read` 에 `pg_monitor` 를 부여한다
- 장점: 익스포터의 모든 콜렉터가 돈다. 로그가 깨끗하다.
- 단점: **읽기 계정의 권한이 넓어진다.** ADR-015 의 되돌리는 조건
  ("읽기 계정의 용도가 갈리면")에 해당한다.

#### H안: `wal` 콜렉터를 끈다
- 장점: 계정 권한을 그대로 둔다.
- 단점: WAL 지표를 잃는다.

### 4. 스택을 상시 띄우는가

#### I안: 기본 기동
- 장점: 늘 보인다.
- 단점: 컨테이너 5개가 상시 메모리를 쓴다. 개발 중 부하가 섞여
  "원래 이렇게 느렸나"의 기준선이 흐려진다.

#### J안: `profiles: ["observability"]`
- 장점: Airflow·리허설과 같은 방식. 필요할 때만 띄운다.
- 단점: 켜는 것을 잊으면 아무것도 기록되지 않는다.

### 5. 경보를 몇 개, 어떤 임계치로

ETL 신선도 임계치 후보는 DAG 주기(매일 06:00, `catchup=False`)에서 나왔다.

| 후보 | 성질 |
|---|---|
| 26시간 | 한 번 거른 것도 즉시 안다. 일시적 외부 API 장애에도 야간에 울린다 |
| **30시간** | 한 번 실패는 다음 새벽 재시도로 덮이고, **연속 실패만** 울린다 |
| 50시간 (이틀) | 조용하지만 이틀치 낡은 메타로 서비스한다 |
| 14일 (`expires_at`) | 사실상 만료 직전. 너무 늦다 |

## 결정

**1번은 D안(우리 앱), 2번은 F안(실측 버킷), 3번은 H안(콜렉터 끄기),
4번은 J안(프로필), 5번은 경보 2개 + ETL 임계치 30시간.**

세부 사항:

1. **노출 지표** — 우리 것 넷을 내보낸다.

   | 지표 | 종류 | 용도 |
   |---|---|---|
   | `pokehelper_etl_last_success_timestamp_seconds{source,format}` | Gauge | 신선도 경보·패널 |
   | `pokehelper_etl_active_snapshots` | Gauge | **"한 번도 수집되지 않음"** 을 표현 |
   | `pokehelper_etl_freshness_refresh_failures_total` | Counter | 지표 자체를 믿을 수 있는가 |
   | `pokehelper_etl_freshness_last_refresh_timestamp_seconds` | Gauge | 마지막으로 DB 를 읽은 시각 |

2. ★ **타임스탬프 게이지만으로는 "한 번도 없었다"를 표현할 수 없다.**
   `time() - last_success > 30h` 는 계열이 존재할 때만 성립한다. 활성 스냅샷이
   0개면 계열이 없어 **경보가 조용히 울리지 않는다.** 그래서 개수 게이지를 두고
   경보식에 `or (pokehelper_etl_active_snapshots == 0)` 을 붙인다.
   "없음"과 "오래됨"은 다른 상태다.

3. **경과 시간이 아니라 유닉스 타임스탬프를 내보낸다.** 경과 시간을 직접
   내보내면 스크랩 간격만큼 어긋나고, 앱이 멈춘 동안 값이 고정돼 "오래됨"을
   놓친다. 경과는 PromQL 의 `time()` 이 계산한다.

4. **스크랩 때 DB 를 읽는다. 백그라운드 루프가 아니다.** 주기 태스크를 두면
   lifespan·취소·테스트에서의 유령 요청을 다뤄야 한다. 대신 캐시(15초)와
   타임아웃(2초)으로 비용을 가둔다.

5. ★ **DB 조회가 실패하면 직전 값을 유지한다. 0 으로 떨구지 않는다.**
   타임스탬프 게이지에서 0 은 "1970년"이고, 그건 "오래됨"이 아니라 "무한히
   오래됨"으로 읽혀 **거짓 경보**가 된다. 실패는 카운터로 따로 센다.

6. `/metrics` 를 **자기 자신의 요청 지표에서 제외**한다. 포함하면 15초 간격이
   분당 4건의 상수로 깔려 실제 사용자 트래픽이 그 아래 묻힌다.

7. **`/metrics` 는 외부에 노출하지 않는다.** 경로별 지연·오류율은 내부 정보다.
   지금은 로컬 compose 전용이고, 배포 시 ALB 수준에서 막는다.

8. **경보는 둘뿐이다.** 울려도 아무도 아무것도 하지 않는 경보는 나머지 경보의
   신뢰도를 깎는다. 지연 경보를 아직 넣지 않은 이유도 같다 — 솔버가 정상 입력에서
   2.2초를 쓰는 상태라 어떤 임계치를 넣어도 그 경로가 지배한다.

9. **경보마다 `severity` 와 `runbook` 을 필수로 한다.** 무엇을 해야 하는지 없는
   경보는 소음이다. 테스트가 이 둘의 존재를 단정한다.

10. ★ **경보가 참조하는 지표명을 테스트가 교차검증한다.**
    PromQL 에서 없는 지표는 오류가 아니라 **빈 결과**다. 오타난 이름을 참조하는
    규칙은 유효하고, 평가되고, 영원히 울리지 않는다. `promtool check rules` 도
    문법만 보므로 잡지 못한다. 지표를 내보내는 쪽(파이썬)과 참조하는 쪽(YAML/JSON)이
    다른 언어라 어떤 도구도 알려주지 않는다.

## 근거

**1~4번 (우리 앱 노출 / 실측 버킷 / 콜렉터 끄기 / 프로필)** — 검토 결과 Claude
제안에 동의.

**5번, ETL 임계치 30시간** — 만약 수집 성공한지 하루가 지나도 **여유 6시간을 두고
아침에 확인할 수 있도록** 30시간으로 결정했다.

## 포기한 것

- **WAL 지표.** `wal` 콜렉터를 껐다. 복제를 쓰게 되면 다시 본다.
- **ETL 실행 시간·행 수.** 지금 측정하는 것은 **결과(신선도)** 뿐이다.
  "어제보다 수집이 느려졌다"는 알 수 없다. 느려지는 것이 문제가 된 적이 없어
  미루지만, 알 수 없는 것으로 남는다.
- **응답 지연 경보.** 솔버 결정 전까지 없다. 즉 **지금 API 가 느려져도 경보는
  울리지 않는다.** 대시보드를 봐야 안다.
- **`/metrics` 의 DB 의존.** DB 가 느리면 스크랩도 느려진다. 타임아웃 2초로
  끊지만, 그 2초는 스크랩 지연으로 나타난다.
- **익스포터 설정의 테스트.** 교차검증은 `pokehelper_*` 에만 걸린다.
  `up`·`pg_*`·`redis_*`·`container_*` 를 참조하는 패널이 깨져도 테스트는 통과한다.
  그쪽은 스택을 띄워 눈으로 확인했다 (아래 결과).
- **경보 수신 경로.** Alertmanager 가 없다. 경보는 Prometheus UI 에만 뜨고
  **아무에게도 전달되지 않는다.** 로컬 관측이라 받아들이지만, 전달되지 않는
  경보는 절반이다.
- **Grafana 비밀번호.** `admin/admin` 이다. 로컬 전용이고 포트도 로컬에만 열린다.
- **상시 관측.** 프로필이라 켜는 것을 잊으면 그 구간의 기록이 없다.

## 되돌리는 조건

- **솔버를 고치면 2번(버킷)과 8번(지연 경보)을 다시 본다.** 상단 버킷(2/3/5초)이
  비게 되고, 그때 비로소 경로별 지연 경보의 임계치를 실측으로 정할 수 있다.
- **복제를 구성하면 3번을 다시 본다.** WAL 지표가 필요해지고, 그때는 G안
  (`pg_monitor` 부여)이 맞다. 지금 H안인 이유는 "쓰지 않는 지표" 였기 때문이다.
- **ETL 신선도 경보가 거짓으로 울리기 시작하면** 30시간을 50시간으로 넓힌다.
  반대로 한 번의 실패도 즉시 알아야 하게 되면 26시간으로 좁힌다.
- **`/metrics` 가 스크랩 타임아웃을 유발하면** D안을 버리고 C안(`sql_exporter`)
  으로 옮긴다. 판단 기준은 `scrape_duration_seconds` 가 타임아웃에 닿는지다.
- **배포하면 7번이 강제된다.** `/metrics` 를 막지 않으면 경로별 지연·오류율이
  외부에 공개된다. 배포 대상이 정해질 때(ADR-001) 함께 다룬다.
- **경보가 셋을 넘어가면** Alertmanager 를 도입한다. 지금은 UI 로 충분하다.
  (2026-11-18: `PokehelperApiSlow` 가 추가돼 **정확히 셋이 됐다.** 다음 경보가
  이 조건을 발동시킨다. `rules/alerts.yml` 머리말에 그 사실을 적어뒀다.)

## 결과

**2026-11-17 (작업 당일) 확인한 것**

- 스크랩 타깃 4개(`backend`/`postgres`/`redis`/`cadvisor`) 전부 `up`.
- `champs_read` 로 `pg_up=1`, `pg_stat_database_numbackends=3`,
  `pg_stat_user_tables` 10개 테이블 수집됨. **익스포터에 `pg_monitor` 없이도
  우리가 쓰는 지표는 전부 나온다** (`wal` 만 예외였고 그래서 껐다).
- `promtool check config` SUCCESS, 규칙 2개 인식.
- Grafana 가 프로비저닝으로 대시보드를 적재함 (`pokehelper-overview`).
- ★ **`PokehelperEtlStale` 이 실제 데이터에서 발화했다.** 개발 DB 의 활성
  스냅샷이 73.0시간 전이어서, 손으로 만든 상황이 아니라 **진짜 낡은 상태를 첫
  시도에 잡았다.** `activeAt=13:49:42` 에 조건이 참이 되어 `pending` 으로 들어가고
  `for: 10m` 을 채운 뒤 `firing` 으로 전이하는 것까지 확인했다.
  (`pending` 은 "조건이 참" 이고 `firing` 은 "경보가 나갔다" 다. 둘을 같은 것으로
  적으면 `for` 가 동작하는지 검증하지 않은 셈이 된다.)
- 교차검증 테스트를 지표명 한 글자를 고쳐 RED 확인함
  (`pokehelper_etl_active_snapshot` → 실패, 원복 후 통과).

**2026-11-18 — 솔버를 고친 뒤 (ADR-017)**

- **버킷(2번)은 그대로 둔다.** `ev-tune` 이 2,215ms → 96ms 가 되어 상단
  버킷(2/3/5초)은 비었지만, 비어 있는 버킷은 비용이 거의 없고 **회귀하면 그때
  필요하다.** 지금 상단을 잘라내면 다시 느려졌을 때 "1초 이상"으로만 보인다.
  하단(10/25/50/100/250ms)이 현재 분포를 가른다 — `/health`(2.6ms)와
  제약 1개(15.9ms), 제약 4·8개(53~96ms)가 서로 다른 칸에 떨어진다.
  다만 제약 4개와 8개는 **같은 칸(`le=0.1`)** 이다. 둘을 구분하려면 버킷을 더
  촘촘히 해야 하는데, 지금 그 구분으로 할 일이 없어서 하지 않았다.
- **지연 경보(8번)를 넣었다** — `PokehelperApiSlow`. 이 ADR 의 첫 번째 되돌리는
  조건을 실행한 것이다.

  | 항목 | 값 | 근거 |
  |---|---|---|
  | 임계치 | p95 > **0.5초** | 실측 최악 96ms 의 5배. **ADR-017 되돌리는 조건과 같은 값**이라, 이 경보가 그 조건을 사람 대신 지켜본다 |
  | 최소 트래픽 | **0.05 req/s** (10분 창에 약 30건) | ★ p95 는 표본이 적으면 p95 가 아니다 |
  | 창 / 대기 | rate `10m` / `for: 5m` | 발견까지 최대 15분. warning 이고 호출기가 아니다 |

  ★ **최소 트래픽 절이 이 경보의 핵심이다.** 트래픽이 거의 없을 때 느린 요청
  하나가 들어오면 **그게 곧 p95 가 된다.** 개발 중 호기심으로 던진 요청 한 건에
  경보가 울리면 사람은 경보를 끄는 법을 먼저 배우고, 그러면 나머지 둘도 같이
  죽는다. 트래픽이 아예 없으면 양쪽 다 빈 결과라 경보는 평가되지 않는다 —
  의도한 동작이다. 아무도 안 쓰는데 느릴 수는 없다.

  검증: 임계치만 0.005초로 낮춘 임시 규칙을 **최소 트래픽 절은 실제 값 그대로**
  두고 올려서, 요청 200건을 보낸 뒤 `pending` → `firing` 전이와 `handler` 라벨이
  양쪽 절의 조인을 넘어 살아 오는 것까지 확인했다. 임시 규칙은 지웠다.

  ▲ **검증 과정에서 내 확인 방법이 먼저 틀렸다.** 경보 상태를 `grep '"state":"firing"'`
  로 봤는데, `/api/v1/alerts` 응답이 한 줄 JSON 이라 **이미 울리고 있던
  `PokehelperEtlStale` 의 `firing` 에 매칭됐다.** 통과로 읽힐 뻔했다.
  JSON 은 파싱해서 확인하고, 문자열로 훑지 않는다.

- **교차검증 범위를 넓혔다.** 이 경보는 `http_request_duration_seconds_bucket` 을
  참조하는데, 기존 교차검증은 `pokehelper_*` 만 봤다. 즉 **이름을 오타내도 아무도
  안 잡는 상태로 경보를 추가할 뻔했다.** `http_*` 를 범위에 넣었다 — 우리가 이름을
  짓지 않았다고 오타가 안 나는 게 아니고, 라이브러리를 올리면 이름이 바뀔 수도 있다.
- ★ **이 ADR 의 측정이 ADR-017 을 찾아냈다.** 경보 임계치를 정하려고 실측한 것이
  2.2초를 드러냈고, 버킷이 기본값이었다면 1.1초와 60초가 같은 칸에 들어가
  **고친 뒤에도 고쳐진 것을 확인할 수 없었다.** 관측성을 먼저 만든 값이 여기서 나왔다.
