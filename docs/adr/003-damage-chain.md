# ADR-003: 데미지 보정 체인 A안(최종 1회 내림) 잠정 채택

- 상태: **잠정 채택** (2026-09-22) — 게임 내 실측 전까지 확정이 아니다
- 관련: Phase 1, `domain/damage.py`, `CLAUDE.md` 5-2
- 기록: 소급 작성 (2026-11-03). 출처 조사는 이 날짜에 수행했다.

## 맥락

Lv.50 고정이라 데미지 기초 계산은 다툼의 여지가 없다.

```
기초 = floor(22 × 위력 × 공격실수치 / 방어실수치)
기초 = floor(기초 / 50) + 2
```

문제는 **그 뒤 보정(자속·타입상성·날씨·급소·특성·도구·벽·화상)과 난수를 어떤 순서로 적용하고
어디서 내림하느냐**다. 여기서 두 방식이 갈리고, 경계에서 결과가 ±1 어긋난다.

기초 100, 난수 0.85, 자속 1.5, 약점 2배인 경우:

| 안 | 계산 | 결과 |
|---|---|---|
| A | floor(100 × 3.0 × 0.85) | **255** |
| B | floor(100×0.85)=85 → floor(85×1.5)=127 → ×2 | **254** |

상대 HP가 255면 **A안은 확정 1타, B안은 난수 1타다.** 1 차이가 "이 기술로 잡히는가"라는
답 자체를 뒤집는다. 이 서비스는 그 판정을 파는 제품이므로 추측으로 넘길 수 없는 지점이었다.

챔피언스는 본가와 별개 엔진이므로 본가 규칙을 그대로 가정할 수 없었다.

## 선택지

### A안: 보정을 실수로 누적하고 맨 마지막에 한 번만 내림
```
mod = stab × type × weather × crit × ability × item × screen × burn
roll_i = floor(기초 × mod × r_i)      for r_i in {0.85, 0.86, ..., 1.00}
```
- 장점:
  - **보정끼리의 순서가 결과에 영향을 주지 않는다.** 순서를 틀릴 여지가 없어 구현이 단순하고 버그가 줄어든다.
  - 챔피언스 전용 가이드(champions-helper.com)가 최종 데미지를 `floor(보정 데미지 × 난수)`
    하나로만 표기하는 것과 일치한다.
  - 새 보정(특성·아이템·필드)을 추가할 때 끼워 넣을 위치를 고민하지 않아도 된다.
- 단점:
  - 중간 내림이 없어 B안보다 데미지가 크게 나온다. 경계에서 과대평가 쪽으로 틀릴 수 있다.
  - 근거가 비공식 팬 자료 한 곳이다.

### B안: 본가 5세대 이후 방식 — 단계마다 내림, 난수를 자속·상성보다 먼저 곱함
- 장점:
  - 본가에서 오래 검증된 방식이다. 챔피언스가 본가 코드를 물려받았다면 이쪽이 맞다.
  - 본가 커뮤니티의 축적된 조정 지식과 값이 어긋나지 않는다.
- 단점:
  - 보정 적용 순서가 결과를 바꾸므로 순서 하나만 틀려도 조용히 어긋난다.
  - `poke_round`(정확히 .5면 내림) 같은 보조 함수가 추가로 필요하다.
  - 챔피언스가 본가와 별개 엔진이라는 전제와 충돌한다.

## 결정

**A안을 잠정 채택한다.**

구현 제약을 함께 둔다.
- 보정 적용은 `domain/damage.py` 의 **단일 함수 `apply_modifiers()` 안에서만** 일어난다.
  A↔B 전환이 이 함수 하나 수정으로 끝나야 한다. 보정 곱셈이 다른 곳에 흩어지면 안 된다.
- 난수는 평균값 하나가 아니라 **0.85~1.00의 16단계를 전부 계산해 리스트로 반환**한다.
- 확정타 판정은 16개 roll 중 상대 HP 이상인 개수로 한다.
- 파이썬 기본 `round()`는 은행가 반올림이라 어느 안을 택하든 사용하지 않는다.

**상태를 `채택`이 아니라 `잠정 채택`으로 둔다.** 근거가 되는 자료가 전부 비공식이고,
게임 내 실측을 아직 수행하지 않았다.

## 포기한 것

- **본가 호환성.** A안을 택하면 본가 계산기와 경계 케이스에서 값이 어긋난다.
  본가 감각으로 접근한 사용자가 "다른 계산기와 다르다"고 느낄 수 있고, 그때 우리가 틀렸다고
  오해받을 위험을 안는다.
- **확정성.** 비공식 자료 한 곳에 기대어 Phase 1 전체를 쌓는다. 나중에 B안으로 뒤집히면
  골든 케이스와 솔버 결과를 전부 다시 검증해야 한다. `apply_modifiers()` 격리로 코드 수정
  범위는 줄였지만, **검증 비용은 줄이지 못한다.**
- **즉시 검증.** 실측을 미뤘으므로 그때까지는 "맞다고 믿고 쓰는" 상태로 진행한다.

## 되돌리는 조건

- **게임 내 실측과 불일치**: 배율이 3개 이상 겹치는 케이스(자속+약점+급소 등)에서 실제 데미지가
  B안과 일치하면 즉시 B안으로 전환한다. 보정이 하나뿐인 케이스는 A/B가 같은 값을 내므로
  검증에 쓸 수 없다 — **경계 케이스를 우선 수집한다.**
- **공식 자료 공개**: 게임사가 공식 계산식을 공개하면 그것을 따른다.
- **사용자 제보**: 실제 대전 결과와 우리 판정이 어긋난다는 제보를 받으면, 먼저 골든 케이스로
  재현한 뒤 이 ADR을 재검토한다. 제보를 받고 바로 상수를 조정하지 않는다.
