# ADR-021: AWS 접근 방식과 Terraform 실행 권한

- 상태: 채택 (2026-11-19)
- 관련: Phase 6, `infra/terraform/ACCESS.md`, `infra/terraform/iam.tf`
- 관련 결정: [ADR-015](015-least-privilege-db-accounts.md) (DB 계정 최소 권한 — 같은 원칙을 IAM 에 반복한다),
  [ADR-019](019-deployment-target-and-prerequisites.md) (배포 대상),
  [ADR-020](020-production-topology.md) (운영 구성)

## 맥락

Terraform 을 도입하면서 질문이 나왔다 — **"IAM 계정을 직접 만들어 인프라를
생성하는 경험이 없어지는 것 아닌가?"**

없어지지 않는다. IAM 이 **두 층으로 갈린다.**

| 층 | 누가 만드나 | 무엇인가 |
|---|---|---|
| ① 운영자 자격증명 | **손으로** (콘솔) | Terraform 을 돌릴 주체 |
| ② 워크로드 역할 | Terraform (`iam.tf`) | 태스크·스케줄러가 쓸 역할 |

★ **①은 Terraform 으로 만들 수 없다.** Terraform 이 AWS API 를 호출하려면
먼저 자격증명이 있어야 하는데, 그 자격증명을 Terraform 으로 만들 수는 없다.
state 버킷을 `bootstrap/` 으로 뺀 것과 같은 닭-달걀이다.

그리고 ②는 **콘솔보다 IAM 을 더 많이 가르친다.** 콘솔 마법사는 신뢰 정책을
숨기고 관리형 정책을 자동으로 붙인다. 무엇이 왜 붙었는지 모른 채 돌아간다.
Terraform 에서는 `assume_role_policy` 를 직접 쓴다.

이 프로젝트에는 같은 문제를 한 번 푼 전례가 있다 — ADR-015 에서 DB 계정을
DDL·DML·읽기로 쪼개고 **위반을 실제로 실행해서 거부되는지** 테스트했다.
IAM 에서 같은 원칙을 반복할지가 이 ADR 의 두 번째 질문이다.

## 선택지

### 1. 운영자 자격증명을 무엇으로 만드는가

#### A안: 루트 계정을 그대로 쓴다

- 장점: 아무 준비가 필요 없다.
- 단점: **루트는 권한을 제한할 수 없고, 유출되면 계정 전체를 잃는다.**
  선택지로 적되 검토 즉시 기각한다.

#### B안: IAM 사용자 + 장기 액세스 키

- 장점: 가장 흔하고 빠르다. `aws configure` 한 번이면 끝난다.
- 단점:
  - ★ **키가 `~/.aws/credentials` 에 평문으로 영구히 남는다.** 폐기하기 전까지
    유효하다. 실수로 커밋되어 계정이 털리는 사고의 1순위다.
  - MFA 강제와 키 로테이션을 손으로 관리해야 한다.

#### C안: IAM Identity Center (임시 자격증명)

- 장점:
  - ★ **장기 키가 디스크에 남지 않는다.** `aws sso login` 으로 받은 토큰은
    만료된다.
  - MFA 가 세션 단위로 걸린다.
  - 사용자가 늘면 그룹·권한 세트로 나눌 수 있다.
- 단점:
  - AWS Organizations 가 켜진다(단일 계정이어도 자동으로). 되돌리기가 번거롭다.
  - 설정에 30분쯤 든다. AWS CLI **v2** 가 필요하다.
  - 매번 `aws sso login` 을 해야 한다(토큰 만료 시).

### 2. Terraform 실행 권한을 어디까지 좁히는가

#### D안: `AdministratorAccess` 를 그대로 둔다

- 장점: 막히지 않는다. 개인 계정을 혼자 쓰는 만큼 현실적이다.
- 단점: "권한을 어떻게 관리했나"에 답할 거리가 없다. 실수로 무관한 자원을
  지울 수 있다.

#### E안: 처음부터 좁힌 정책을 쓴다

- 장점: 더 빨리 안전해진다.
- 단점: ★ **누락될 때마다 `apply` 가 중간에 죽는다.** Terraform 은 자원을
  순서대로 만들다가 권한이 없으면 거기서 멈추고, **절반만 만들어진 상태**가
  남는다. 되돌리는 것이 번거롭다.

#### F안: Admin 으로 시작해 **CloudTrail 로 측정한 뒤** 좁힌다

- 장점:
  - ★ **추측이 아니라 측정으로 좁힌다.** ADR-015 와 같은 방식이다.
  - 중간에 죽지 않는다. 전체 구축을 한 번 끝낸 뒤 좁힌다.
  - CloudTrail **Event history 는 무료**고 90일을 보관한다. 별도 trail 을
    만들 필요가 없으므로 S3 비용도 없다.
- 단점:
  - 반나절쯤 더 든다.
  - ★ **CloudTrail 은 실제로 호출된 것만 보여준다.** `apply` 만 보고 좁히면
    `destroy` 가 막힌다. 양쪽을 다 돌려봐야 한다.

### 3. CI 가 `terraform apply` 를 하는가

#### G안: 지금은 로컬에서만

- 장점: 변수가 하나다. 인프라를 만드는 동안 CI 까지 디버깅하지 않는다.
- 단점: ★ **배포가 한 사람의 노트북에 묶인다.** 재현성이 코드가 아니라
  사람에게 있다.

#### H안: 지금 GitHub Actions OIDC 까지 붙인다

- 장점: 저장소에 비밀값 없이 역할을 맡는다. 신뢰 정책에 저장소·브랜치 조건을
  직접 쓰므로 IAM 학습 가치가 높다.
- 단점: 인프라가 아직 다 안 만들어진 상태에서 변수가 둘로 늘어난다.

## 결정

**1 = C안(Identity Center), 2 = F안(Admin → CloudTrail 로 좁힘), 3 = G안(로컬만).**

세부 사항:

1. **루트 계정에 MFA 를 걸고 봉인한다.** 루트로는 결제와 계정 설정만 한다.
   일상 작업에 쓰지 않는다.

2. **Identity Center 인스턴스는 서울(`ap-northeast-2`)에 만든다.** 인스턴스
   리전은 나중에 못 바꾼다.

3. **권한 세트는 `PokehelperAdmin` 하나로 시작한다.** 좁힌 뒤 두 번째 권한
   세트(`PokehelperTerraform`)를 추가하고 전환한다. 처음부터 둘을 만들지 않는다.

4. **좁히는 근거는 CloudTrail Event history 다.** `apply` 와 `destroy` 를 **둘 다**
   돌린 뒤 호출된 `eventSource:eventName` 을 집계해 그 목록으로 정책을 만든다.
   별도 trail 을 만들지 않는다 — Event history(무료·90일)로 충분하다.

5. **워크로드 역할 셋은 Terraform 이 만든다** (`iam.tf`).

   | 역할 | 누가 쓰나 | 필요한 것 |
   |---|---|---|
   | 실행 역할 | ECS **에이전트** | ECR pull · 로그 그룹 쓰기 · **SSM 파라미터 읽기** |
   | 태스크 역할 | 컨테이너 **안의 앱** | 거의 없음. ECS Exec 을 쓰면 `ssmmessages:*` |
   | 스케줄러 역할 | EventBridge | `ecs:RunTask` + ★ `iam:PassRole` |

6. ★ **실행 역할과 태스크 역할을 구분해 주석에 명시한다.** 둘을 혼동하는 것이
   ECS 의 가장 흔한 함정이다. "SSM 파라미터를 못 읽는다"는 거의 항상 **실행
   역할** 문제인데 태스크 역할을 고치게 된다. `iam.tf` 에 그 사실을 적어둔다.

7. ★ **`iam:PassRole` 을 좁힌다.** 스케줄러가 ECS 에게 역할을 넘기려면 역할을
   넘길 권한이 따로 필요하다. `Resource` 를 우리 태스크 역할 두 개로 한정하고,
   `iam:PassedToService` 조건으로 `ecs-tasks.amazonaws.com` 에만 허용한다.
   넓게 열면 **그 역할을 가진 누구나 더 센 역할을 넘겨 권한을 올릴 수 있다.**

8. **손으로 하는 절차는 `infra/terraform/ACCESS.md` 에 적는다.** 콘솔 클릭은
   코드로 남지 않으므로, 남기지 않으면 다음에 재현할 수 없다.

## 포기한 것

- ★ **CI 자동 배포.** 지금 `apply` 는 로컬에서만 돈다. 즉 **배포 절차의
  재현성이 코드가 아니라 사람에게 있다.** 인프라 코드는 버전 관리되지만
  "누가 언제 무엇으로 돌렸는가"는 남지 않는다.
- ★ **좁힌 정책의 자동 검증.** ADR-015 에서는 "권한 없는 계정으로 위반을
  실행해 거부되는지"를 pytest 로 돌릴 수 있었다. **IAM 은 그렇게 못 한다** —
  테스트가 실제 AWS 에 요청을 보내야 하고, 그러려면 자격증명과 비용이 든다.
  따라서 좁힌 정책이 맞는지는 **`apply` 를 돌려보는 것 말고 확인할 방법이 없다.**
  같은 원칙을 적용했지만 집행 수단은 더 약하다. 숨기지 않고 적는다.
- **권한 경계(Permissions Boundary)와 SCP.** 단일 계정·1인 프로젝트에서는
  과하다. 계정이 둘 이상이 되면 다시 본다.
- **액세스 키 로테이션 절차.** Identity Center 를 쓰므로 장기 키가 없다.
  반대로 말하면 **장기 키 관리 경험은 얻지 못한다.**
- **`destroy` 권한의 분리.** 만드는 권한과 지우는 권한을 같은 역할이 갖는다.
  실수로 `destroy` 하는 것을 IAM 으로 막지 않는다 — `prevent_destroy` 로
  state 버킷만 보호한다.

## 되돌리는 조건

- **좁힌 정책이 `apply` 를 자주 막으면 넓힌다.** 다만 **넓힌 액션과 그 이유를
  기록한다.** 이유 없이 넓히기 시작하면 결국 Admin 으로 돌아간다.
- **CI 가 `apply` 하게 되면 결정 3을 뒤집고** GitHub OIDC 역할을 추가한다.
  판단 기준: 로컬에서만 배포하는 것이 실제로 문제가 되는 순간
  (예: 다른 기기에서 배포해야 할 때, 또는 배포 이력이 필요해질 때).
- **사용자가 둘 이상이 되면** 권한 세트를 역할별로 나눈다. 지금 하나인 것은
  나눌 대상이 없기 때문이다.
- **계정이 둘 이상이 되면** SCP·권한 경계를 다시 본다.
- **CloudTrail Event history 90일이 모자라면** trail 을 만든다. 90일 안에
  좁히는 작업을 끝내면 필요 없다.
