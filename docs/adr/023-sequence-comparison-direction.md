# ADR-023: 복구 비교의 4층(시퀀스)은 일치가 아니라 방향으로 판정한다

- 상태: 채택 (2026-11-27)
- 관련: 운영 체계, `backend/scripts/db_state.py`, Phase 6
- 관련 결정: [ADR-014](014-restore-rehearsal.md) (4층 비교의 출처), [ADR-020](020-production-topology.md) (결정 3 — DR 전략)

## 맥락

[ADR-014](014-restore-rehearsal.md) 가 복구 검증을 네 층으로 정했다. 4층은 시퀀스이고,
그 층을 둔 이유는 **복구 직후 첫 INSERT 가 PK 충돌하는 경우**를 잡는 것이었다.
데이터·제약이 모두 맞는데 시퀀스만 뒤처져 있으면 복구는 성공해 보이고 다음 쓰기에서
터진다.

구현은 1~3층과 같았다 — **값이 다르면 차이**. 로컬 리허설(`pg_dump`/`pg_restore`)에서는
`setval` 로 값을 그대로 복원하므로 이 판정이 문제없이 동작했고, 33건이 계속 초록이었다.

2026-11-26, 같은 비교를 **RDS PITR 복원본**에 처음 돌렸다
(`docs/decisions/JOURNAL.md` 참조). 1·2·3층은 완전히 일치했다 — 10개 테이블
17,220행, 제약 27개, 인덱스 21개. 4층만 차이를 냈다.

```
★ 차이 2건
  [4 시퀀스] 다름: meta_snapshots_id_seq 원본='3'   복원본='35'
  [4 시퀀스] 다름: pokemon_meta_id_seq   원본='150' 복원본='166'
```

조사 결과 **PostgreSQL 의 설계**였다. `nextval` 은 호출마다 WAL 에 적지 않고
**32회마다** 적으며, 그때 `현재값 + 32` 를 미리 기록한다. 복구가 그 선행 값으로
돌아오므로 복원본의 `last_value` 는 **최대 32 앞선다.**

| 시퀀스 | 원본 | 복원본 | 차 | 32칸 창에서의 위치 |
|---|---|---|---|---|
| `meta_snapshots_id_seq` | 3 | 35 | +32 | 막 기록한 직후 |
| `pokemon_meta_id_seq` | 150 | 166 | +16 | 창의 절반 |

둘 다 `0 ≤ 차 ≤ 32` 안에 있고 **둘 다 앞섰다.** 뒤처지는 일은 없다 — 그래야 PK
충돌이 안 나므로 PostgreSQL 이 일부러 선행 값을 적는 것이다.

즉 **PITR 복구는 정상인데 4층이 매번 빨간불을 낸다.** 그리고 매 복구마다 빨간불이
뜨면 운영자는 4층을 읽지 않게 된다. 그건 4층이 잡으려던 뒤처짐을 놓치는 길이다.
**거짓 양성이 그 층을 무력화한다.**

## 선택지

### A안: 그대로 둔다 — 사람이 판단한다

- 장점:
  - 코드를 바꾸지 않는다. 비교는 "다른 것을 다르다고 말한다"는 가장 단순한 계약을 유지한다.
  - 시퀀스가 앞선 사실이 **눈에 보이는 차이로** 남는다. 숨기지 않는다.
- 단점:
  - ★ **모든 PITR 복구가 빨간불이다.** 정상 결과에 종료 코드 1 이 붙는다.
  - 자동화에 쓸 수 없다. 종료 코드로 성패를 판정할 수 없으면 런북이 사람의 눈에 의존한다.
  - 경고 피로. 매번 "이건 괜찮은 차이"를 설명해야 하고, 그러다 진짜 뒤처짐을 같은 손짓으로 넘긴다.

### B안: `복원본 − 원본 ∈ [0, 32]` 를 정상으로 처리한다

- 장점:
  - 거짓 양성이 사라진다.
  - 32 를 넘는 선행은 여전히 차이로 올라온다 — "설명 가능한 범위"를 명시적으로 좁힌다.
- 단점:
  - ★ **PostgreSQL 내부 상수(`SEQ_LOG_VALS = 32`)에 결합된다.** 공개 API 가 아니고
    버전마다 바뀔 수 있다. 바뀌면 조용히 거짓 양성이 돌아오거나, 더 나쁘게는
    허용 범위가 실제보다 좁아져 정상 복구를 실패로 판정한다.
  - `CACHE` 절을 쓴 시퀀스는 선행 폭이 32 가 아니다. 지금은 쓰지 않지만 쓰면 깨진다.
  - 32 라는 수가 코드에 들어오면 **그 수가 왜 32 인지를 아는 사람만** 유지보수할 수 있다.

### C안: 방향만 본다 — `복원본 < 원본` 일 때만 차이

- 장점:
  - ★ **판정 기준이 이 층의 목적과 정확히 일치한다.** 4층은 PK 충돌을 막으려고
    있고, 충돌은 뒤처질 때만 난다. 앞선 것은 ID 를 건너뛸 뿐이다.
  - 어떤 상수에도 결합하지 않는다. `SEQ_LOG_VALS` 가 바뀌든 `CACHE` 를 쓰든 유효하다.
  - `<unused>` 를 0 으로 보면 **가장 위험한 경우**(원본 150 → 복원본 `<unused>`,
    즉 1 부터 다시 시작)가 자연히 "뒤처짐"으로 잡힌다.
- 단점:
  - **앞선 폭이 비정상적으로 큰 경우를 놓친다.** 복원본이 999999 로 앞서 있어도
    통과한다. PK 충돌은 안 나지만 ID 공간을 크게 버리는 것이고, 그게 다른 결함의
    징후일 수 있다.
  - "일치"보다 느슨한 기준이라, 비교의 계약을 설명하는 비용이 생긴다.

## 결정

**C안.** 더불어 두 가지를 붙인다.

1. ★ **앞선 사실을 버리지 않는다.** 차이에서는 빠지지만 `sequence_advances()` 가
   따로 돌려주고 CLI 가 `참고` 로 찍는다. 종료 코드에는 영향이 없다.

   ```
   참고 — 복원본에서 앞선 시퀀스 2개 (안전: PK 충돌 없음)
     meta_snapshots_id_seq  3 → 35  (+32)
     pokemon_meta_id_seq  150 → 166 (+16)
   ```

   정보를 숨기면 다음 사람이 같은 조사를 처음부터 반복한다. C안의 단점(큰 선행을
   놓친다)에 대한 부분적 대응도 된다 — 숫자가 눈에 보이면 이상한 폭은 사람이 알아챈다.

2. **판정할 수 없는 값은 통과시키지 않는다.** `last_value` 가 숫자도 `<unused>`
   도 아니면 `읽을 수 없음` 으로 차이에 올린다. fail-closed.

3. ★ **로컬 리허설(`tests/rehearsal/`)은 정확한 일치를 계속 요구한다.**
   그쪽은 `pg_dump`/`pg_restore` 경로이고 `setval` 이 값을 그대로 복원하므로
   앞서는 일이 애초에 없다. **복구 방식이 다르면 올바름의 기준도 다르다.**
   같은 코드로 통일하면 로컬에서 더 강했던 보장을 이유 없이 버린다.

## 포기한 것

- **비정상적으로 큰 선행을 탐지하는 능력.** 복원본이 ID 공간을 크게 건너뛰어도
  통과한다. `참고` 출력으로 사람 눈에는 보이지만, **자동 판정은 하지 않는다.**
  B안을 골랐다면 32 라는 상한이 그 역할을 했을 것이다.
- **"비교는 다른 것을 다르다고 말한다"는 단순한 계약.** 이제 층마다 판정 방식이
  다르고, 그걸 읽는 사람이 알아야 한다. 코드에 긴 주석과 이 ADR 이 그 비용이다.
- **두 복구 경로의 판정 통일.** 로컬 리허설과 운영 비교가 시퀀스에 대해 서로
  다른 기준을 쓴다. 의도한 것이지만, **"같은 4층"이라는 말이 이제 완전히 같지는
  않다.** ADR-020 세부사항 5 의 표현도 그만큼 느슨해졌다.
- **첫 실측 전에 알 수 있었다는 가정.** 이 규칙은 운영에서 거짓 양성을 한 번
  맞고 나서 만들어졌다. 설계 시점에 PostgreSQL 의 WAL 기록 주기를 알아봤다면
  처음부터 C 로 썼을 것이다. **로컬 리허설만으로는 드러나지 않는 종류의 결함**이
  있다는 증거로 남긴다.

## 되돌리는 조건

- **`<unused>` 를 0 으로 보는 것이 틀린 경우가 나오면** 다시 본다. 지금은
  "다음에 1 을 내준다"는 전제이고, `MINVALUE` 가 음수인 시퀀스를 쓰면 깨진다.
  이 프로젝트는 쓰지 않지만 쓰게 되면 조건을 고친다.
- **앞선 폭이 큰 복구가 실제 결함의 징후였던 사례가 생기면** B안의 상한을 다시
  검토한다. 그때는 32 가 아니라 **관측된 분포**로 상한을 정한다 — 그게 상수 결합을
  피하는 방법이다.
- **`참고` 출력을 아무도 읽지 않는 것이 확인되면** C안의 단점 대응이 실패한
  것이다. 그러면 앞선 시퀀스를 경고 종료 코드(예: 2)로 올릴지 결정한다.
- **시퀀스를 쓰는 테이블이 사라지면** (UUID PK 로 옮기는 등) 4층 자체의 존재
  이유가 약해진다. 그때 층을 셋으로 줄일지 본다.
