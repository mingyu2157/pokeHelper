# ADR-017: 제약 결합 탐색을 전수 조합에서 분기한정으로

- 상태: 채택 (2026-11-18)
- 관련: Phase 1, `domain/ev_solver.py`, [ADR-008](008-solver-search-strategy.md), [ADR-016](016-observability-metrics.md)

## 맥락

[ADR-016](016-observability-metrics.md) 작업에서 경보 임계치를 정하려고 API 지연을
실측하다가, `POST /api/v1/calc/ev-tune` 이 **제약 8개에서 2.2초** 를 쓰는 것을 봤다.
처음에는 "불가능 판정 시 충돌 분석이 비싼가" 로 짐작했는데 전부 `feasible: true`
였고, 코드를 읽으니 원인이 달랐다.

`_best_combination()` 이 제약별 후보 집합의 **데카르트 곱을 전수 순회**한다.

```python
for choices in product(*candidate_sets):
    merged, total = _combine(choices)
    if total > MAX_TOTAL_POINTS:   # ← 조합을 "만든 뒤"에 버린다
        continue
```

예산 초과 검사가 조합을 만든 **뒤** 에 있어서 순회 횟수를 전혀 줄이지 못한다.
계측한 조합 수는 정확히 `후보수^제약수` 였다.

| 입력 | 조합 수 | 실측 |
|---|---|---|
| SURVIVE ×4 | 625 | 46.5ms |
| SURVIVE ×7 | 78,125 | 456.6ms |
| SURVIVE ×8 | 390,625 | **2,268ms** |

### ★ 2.2초는 최악값이 아니라 표본 하나였다

위 표의 "후보 5개"는 **그 입력의** 파레토 전선 크기다. 전선은 입력에 따라 변한다.
1축 제약(OUTSPEED, KNOCKOUT)은 후보를 1개만 반환하므로 곱에 기여하지 않고,
**SURVIVE 만** HP·방어 2축이라 전선을 만든다 (ADR-008 결정).

종족값·기술 위력·상대 공격을 훑어 전선 최대치를 찾았다.

```
max frontier size: 23   (HP종족 60 / 방어종족 70 / 위력 80 / 상대공격 290)
제약 8개 → 23^8 = 78,310,985,281 조합
```

리프당 5.8μs 로 **약 126시간**이다. 입력은 전부 유효하다 — 제약 8개는
`MAX_CONSTRAINTS` 이내고 각 제약도 스키마를 통과한다. 즉 **문서화된 한도 안의
정상 요청 하나로 워커를 영구 점유**할 수 있다. 공개 배포 전에 닫아야 하는
가용성 결함이고, 성능 개선 과제가 아니다.

### ADR-008 은 이걸 예측했고, 처방은 틀렸다

[ADR-008](008-solver-search-strategy.md) `포기한 것`:

> 제약이 많아지고 SURVIVE 전선이 커지면 곱해져서 누적된다. **상한을 두지 않았다.**

예측은 정확했다. 그런데 같은 ADR 의 `되돌리는 조건` 은 대응책을 이렇게 적었다.

> 탐색이 병목이 되면, **1축 제약만 이진 탐색으로 바꾼다.**

1축 제약은 후보가 1개라 곱에 기여하지 않는다. 그 처방을 그대로 실행하면
제약당 평가를 33회에서 6회로 줄이고 **2.2초는 그대로 남는다.**
되돌리는 조건을 미리 적어둔 것은 옳았지만 **어느 계층이 병목인지 틀렸다.**

## 선택지

### A안: 전수 조합 유지 + 입력 상한 축소

`MAX_CONSTRAINTS` 를 8에서 2~3으로 내린다.

- 장점:
  - 코드 변경이 스키마 상수 한 줄이다. 탐색 로직을 건드리지 않으므로 답이 바뀔 위험이 0이다.
  - 상한이 명시적이라 최악 응답시간을 계산할 수 있다.
- 단점:
  - 전선 23개면 `23^3 = 12,167` 로 이미 수백 ms 다. 상한을 **2까지** 내려야 안전하다.
  - 제약 2개는 기능을 포기하는 수준이다. "최속 추월 + 특정 기술 버팀 + 특정 상대 확정 1타"는
    현실적인 조정 요구고, 그게 이 서비스의 차별화 지점이다 (`ev_solver.py` 모듈 독스트링).
  - 원인을 고치지 않고 입력을 좁히는 것이라, 전선이 더 커지는 입력이 발견되면 또 내려야 한다.

### B안: 분기한정 (branch and bound)

결합이 스탯별 `max` 라 **부분 조합의 총합은 단조 증가**한다. 중간에 상한을 넘으면
그 아래를 전부 버린다.

- 장점:
  - 최적성을 유지한다. 가지치기로 버리는 가지는 **이미 상한을 넘은** 가지뿐이다.
  - 입력 상한을 그대로 둘 수 있다.
  - 전수 탐색과 대조하는 차등 테스트로 등가성을 기계적으로 검증할 수 있다.
- 단점:
  - 최악의 경우에 대한 이론적 보장은 없다. 지수 시간이 사라지는 게 아니라 가지치기에 의존한다.
  - 재귀와 상한 계산이 들어가 코드가 길어진다. 상한을 한 칸이라도 낮게 잡으면
    **최적해가 조용히 사라진다** — 예외가 아니라 "1포인트 더 쓰는 답"이나 "불가능"이 나온다.

### C안: 근사 탐색 (탐욕 + 지역 탐색)

각 제약의 최소안을 합치고 초과분만 지역 탐색으로 줄인다.

- 장점: 다항 시간이 보장된다.
- 단점: **최적해 보장을 버린다.** 이 서비스는 "1포인트를 어디에 꽂는지"를 파는데,
  근사해는 그 1포인트를 틀릴 수 있다. CLAUDE.md 5-4 규칙 5("근사치를 정답인 척
  내놓지 않는다")와 정면으로 충돌한다.

### D안: 비동기 처리 + 타임아웃

요청을 큐에 넣고 결과를 폴링한다.

- 장점: 워커 점유를 구조적으로 막는다.
- 단점: 계산 자체는 여전히 126시간이다. **점유를 옮기는 것일 뿐 고치는 게 아니다.**
  API 모양과 프론트가 전부 바뀐다.

### 하위 결정: 노드 상한을 둘 것인가

B안을 택해도 최악의 경우 보장은 없다. 노드 수에 상한을 두고 초과 시 도메인 예외를
던질 수 있다.

| 후보 | 성질 |
|---|---|
| 상한 없음 | 실측 최대 533노드. 관측된 적 없는 실패 경로를 만들지 않는다 |
| 상한 + 실패 응답 | 최악 응답시간이 보장된다. 대신 에러 문구·프론트 처리·테스트가 늘어난다 |

## 결정

**B안(분기한정)을 채택하고, 노드 상한은 두지 않는다.**

구현은 `_best_combination()` 안에서만 바뀐다. 세 장치를 쓴다.

1. **씨앗 상한** (`_search_bound`) — 각 집합에서 총합이 가장 적은 후보만 골라 합친
   조합은 그 자체로 하나의 해다. 따라서 최적해는 그 값 이하이고, 예산 66도 넘을 수
   없다. `min(T0, 66)` 에서 출발하므로 **첫 리프를 기다리지 않고 1단계부터 자른다.**
2. **단조성 가지치기** — 부분 총합이 상한을 **초과하면** 중단한다. 같을 때는 자르지
   않는다. 총합이 같고 HP 가 더 실린 안이 이기는 규칙(`_prefers_hp`)이 살아 있어야 한다.
3. **잔여 하한** (`_suffix_minimums`) — 남은 집합의 최소 총합은 어차피 넘어야 하므로
   `max(부분총합, 남은최소)` 로 더 자른다.

★ **순회 순서는 바꾸지 않는다.** 집합을 크기순으로 정렬하면 가지치기가 더 강해지지만,
동점 처리와 근거 문장 순서가 달라진다. 성능 때문에 **출력이 바뀌면 안 된다.**

`_combine()` 은 삭제하고 `_merge_one()` 으로 대체했다. 전수 탐색은 조합마다 처음부터
합쳤지만 DFS 는 한 단계씩 증분 병합한다.

## 근거

**1. B안(분기한정) 채택** — 검토 결과 Claude 제안에 동의.

**2. 노드 상한을 두지 않음** — 검토 결과 Claude 제안에 동의.

선택지별 장단점을 설명으로 듣고 추천대로 가기로 했다. 별도의 추가 판단은 하지 않았다.

## 포기한 것

- **최악의 경우에 대한 이론적 보장.** 가지치기는 최적성은 보장하지만 다항 시간은
  보장하지 않는다. 노드 상한을 두지 않았으므로, 상한이 느슨해지는 입력이 발견되면
  응답이 다시 길어질 수 있다. 대신 [ADR-016](016-observability-metrics.md) 의 p95
  지연 패널이 그걸 **보이게** 한다 — 관측성을 먼저 만든 값이 여기서 나온다.
- **코드 단순함.** `product` 한 줄이 재귀 + 상한 계산 + 잔여 하한 세 조각으로 늘었다.
  가지치기 조건을 틀리면 조용히 틀린 답이 나오므로, 차등 테스트가 영구적으로 필요하다.
- **입력 상한의 재검토 기회 (A안).** `MAX_CONSTRAINTS = 8` 을 그대로 뒀다. 이 숫자는
  처음 정할 때 비용 곡선을 보지 않고 고른 값인데, 이번에도 근거를 만들지 않았다.
  지금은 8이 싸기 때문에 문제가 되지 않을 뿐이다.
- **전선 자체를 줄이는 길.** 파레토 전선 23개 중 실제로 쓸모 있는 안은 더 적을 수
  있다 (내구력 지표로 지배당하는 안을 미리 버리는 방법). 손대지 않았다 — 그건
  **답이 바뀌는** 변경이라 이 커밋의 범위가 아니다.

## 되돌리는 조건

- **노드 수가 1000을 넘는 입력이 나오면.** 테스트가 그 선에서 깨지도록 막아뒀다
  (실측 506의 2배). 깨지면 그때 노드 상한 + 실패 응답을 다시 검토한다.
- **p95 지연이 500ms 를 넘으면** (Grafana `API p95 지연` 패널). 지금 제약 8개가
  96ms 이므로 5배 여유다. 넘으면 원인이 결합인지 후보 생성인지 **다시 측정**한다 —
  ADR-008 이 틀린 계층을 지목한 것과 같은 실수를 반복하지 않는다.
- **제약 종류가 늘어 2축 이상 전선이 또 생기면.** 지금은 SURVIVE 하나뿐이다.
  전선을 만드는 제약이 둘 이상이면 곱이 다시 커지므로 결합 방식부터 재설계한다.
- **스탯당 상한(32)이나 총합(66)이 바뀌면.** 전선 크기 상한이 바뀌어 23이라는
  숫자가 무효가 된다.

## 결과

(2026-11-18 실측, 같은 커밋에서 측정)

**응답 시간** — `POST /api/v1/calc/ev-tune`, 7회 중 p50

| 입력 | 변경 전 | 변경 후 |
|---|---|---|
| SURVIVE ×1 | 3.3ms | 15.9ms |
| SURVIVE ×4 | 55.8ms | 53.3ms |
| SURVIVE ×8 | **2,215ms** | **96.0ms** |
| 전선23 × SURVIVE ×8 | 약 126시간 (추정) | **65.8ms** |

**탐색 노드 수** — 전선 23개 입력

| 제약 수 | 전수 조합 | 분기한정 노드 |
|---|---|---|
| 4 | 279,841 | 230 |
| 6 | 148,035,889 | 368 |
| 8 | 78,310,985,281 | **506** |

**등가성** — 무작위 입력 250건에서 전수 조합 오라클과 배분·총합·근거가 전부 일치.

**남은 비용은 결합이 아니라 후보 생성이다.** 제약 8개 96ms 중 탐색은 0.6ms 고,
나머지는 `_candidates_for()` 가 제약마다 데미지 계산을 돌리는 비용이다. 제약 수에
**선형**이므로 지금은 문제가 아니다. 다음에 느려지면 여기부터 본다.

**검증 과정에서 배운 것 두 가지**

1. **0인 키.** 증분 병합을 처음 짰을 때 `0 > 0` 이 거짓이라 `{SPEED: 0}` 키를
   생략했다. 배분과 총합은 같은데 딕셔너리가 달라서 차등 대조가 379건 어긋났다.
   값이 같다고 자료구조가 같은 게 아니다. 전수 탐색과 대조하지 않았다면 못 봤다.
2. **상한 품질이 곧 성능이다.** RED 검증으로 가지치기를 **12포인트만** 느슨하게
   했더니 테스트가 10분을 넘겨 중단해야 했다. 가지치기가 조금 약해지는 것과
   많이 약해지는 것 사이에 완만한 구간이 없다.
