# ADR-006: 데이터 파이프라인 스택 — Airflow는 Phase 2, Kafka·Spark는 Phase 7로 분리

- 상태: **잠정 결정** (2026-11-03) — Phase 2 착수 시 Airflow 부분을 확정한다
- 관련: Phase 2, Phase 7, `app/ingestion/`
- 관련 ADR: [ADR-002](002-data-source.md) 데이터 소스 / [ADR-004](004-postgres-jsonb.md) DB 구조

## 맥락

메타 통계 수집(Phase 2)을 설계하면서 데이터 파이프라인 스택을 정해야 했다.

개발자가 현재 데이터 엔지니어링 강의(Kafka · Spark · Airflow 기반 실시간 데이터레이크)를
수강 중이고, 배운 것을 이 프로젝트에 적용하고 싶다는 요구가 있었다.
**운영 효율보다 학습과 경험이 동기**임을 처음부터 밝혔다.

문제는 이 프로젝트의 데이터 성격이 해당 스택의 전제와 맞는지였다.

| 항목 | 이 프로젝트의 실제 |
|---|---|
| 갱신 주기 | championsbattledata가 **하루 1회** 래더 스냅샷 재구성 |
| 데이터 양 | 포켓몬 약 1,000종 × 행 수백 개. 단일 머신 메모리에 들어감 |
| 데이터 성격 | 배치 스냅샷. 연속 이벤트 스트림이 아님 |
| 보관 | [ADR-002](002-data-source.md) 약관이 **영구 미러·아카이브를 금지** |

마지막 항목이 결정적이었다. 강의의 중심 패턴인 데이터레이크는 **정의상 아카이브**인데,
약관이 "캐시 데이터로 영구 미러, 아카이브, 또는 이 API의 대체물을 만드는 것"을 금지한다.
기술적 적합성 이전에 **라이선스가 막는다.**

한편 이 프로젝트에도 진짜 이벤트 스트림이 발생하는 지점이 있다 — 다만 수집 데이터가 아니라
**사용자 행동**이다. 선출 훈련 모드(기능 ④)의 선택 이벤트, 복기 코치(기능 ③)의 턴별 로그,
`llm_usage` 토큰 로깅. 이것들은 우리가 생성하는 데이터라 라이선스 제약이 없고,
사용자가 늘면 실제로 스트림이 된다. 전부 Phase 7 영역이다.

## 선택지

### A안: 지금(Phase 2) Kafka · Spark · Airflow를 전부 도입
- 장점:
  - 강의 내용을 즉시 적용한다. 학습 목적을 가장 빠르게 달성한다.
  - 포트폴리오에 데이터 엔지니어링 스택이 드러난다.
- 단점:
  - 하루 1회 수 MB 배치에 Kafka를 쓰는 구성이 된다. **"왜 Kafka죠?"에 기술적으로 답할 수 없다.**
    면접에서 적합성 판단력을 의심받을 수 있다 — 스택을 안 쓴 것보다 나쁜 결과가 가능하다.
  - 데이터레이크 부분은 약관 위반이라 애초에 구현 불가.
  - Phase 2의 범위가 크게 늘어 Phase 1~3 진도가 밀린다.

### B안: Airflow만 Phase 2, Kafka·Spark는 실제 스트림이 생기는 Phase 7
- 장점:
  - **Airflow는 지금 진짜로 필요하다.** 하루 1회 스케줄, 실패 재시도, 백필, 태스크 의존성
    (수집 → 한영 매핑 검증 → 적재 → 캐시 만료), 요청 간 1초·동시성 1 제약의 DAG 강제 —
    전부 Airflow의 교과서적 용도다. 아카이브를 만들지 않으므로 약관과도 충돌하지 않는다.
  - Kafka·Spark는 사용자 이벤트가 생긴 뒤 붙인다. 그때는 "사용자 행동을 실시간 집계해
    개인화 피드백을 준다"는 설득력 있는 근거가 생긴다.
  - 각 기술이 쓰이는 이유를 설명할 수 있는 상태로 포트폴리오가 남는다.
- 단점:
  - Kafka·Spark 학습 적용이 Phase 7까지 미뤄진다. 그 시점에 도달하지 못하면 영영 안 쓰게 된다.
  - 학습 동기의 즉시 충족이 안 된다.

### C안: 이 프로젝트에는 Airflow만 쓰고, Kafka·Spark는 별도 토이 프로젝트
- 장점:
  - 공개 스트리밍 데이터셋을 쓰면 라이선스 제약 없이 강의 패턴을 그대로 구현할 수 있다.
  - 포트폴리오에 두 프로젝트를 따로 올리는 편이 "하나에 억지로 욱여넣은 것"보다 평가가 낫다.
- 단점:
  - 관리할 프로젝트가 둘로 늘어난다.
  - pokeHelper 자체의 기술 스택 폭은 좁아진다.

## 결정

**B안을 잠정 채택한다.**

- **Phase 2 — Airflow 도입.** 메타 수집 스케줄링·재시도·백필·태스크 의존성 관리.
- **Phase 7 — Kafka · Spark 재검토.** 사용자 행동 이벤트(선출 훈련, 복기 코치, `llm_usage`)가
  실제로 발생하는 시점에 도입 여부를 다시 판단한다.
- **데이터레이크는 이 데이터 소스로 구현하지 않는다.** 약관상 불가능하다.

Phase 2 착수 시점에 Airflow 운영 비용(로컬 컨테이너 추가, 스케줄러·웹서버 리소스,
ECS에서의 호스팅 방법)을 재평가하고 그때 상태를 `채택`으로 확정한다.

## 근거

(2026-11-03, 개발자 본인 기록)

**처음 제시한 요구**
가변 문서들은 공부 중인 데이터 엔지니어 강의(카프카·스파크·에어플로)에서 배운 지식을 활용해
실시간 데이터 파이프라인을 적용하고 싶다.
이 부분은 **실제 운영의 효율보다는 공부와 경험을 쌓고 싶어서** 이렇게 결정했고,
괜찮을지는 모르겠다고 함께 밝혔다.

**운영 복잡도를 고려했는가**
고려하지 않았다.

**Claude의 분석을 받은 뒤의 결정**
Claude가 (1) 하루 1회 배치에 Kafka는 맞지 않고, (2) 데이터레이크는 ADR-002 약관 위반이며,
(3) Airflow는 이 프로젝트에 정확히 맞고, (4) 진짜 이벤트 스트림은 Phase 7의 사용자 행동
데이터라는 점을 제시했다. 이를 받아들여
**"Airflow는 Phase 2에서 사용하고, Kafka·스파크는 이벤트 스트림이 발생하는 Phase 7에서
사용하기로 잠정 결정"** 했다.

## 포기한 것

- **학습 동기의 즉시 충족.** Kafka·Spark 적용이 Phase 7로 밀린다.
  Phase 7까지 가지 못하면 이 프로젝트에서는 끝내 쓰지 않게 된다.
- **기술 스택의 폭.** 지금 시점의 포트폴리오에는 Airflow만 남는다.
- **데이터레이크 구현.** 이 데이터 소스로는 어떤 경우에도 불가능하다.
  강의의 중심 패턴을 이 프로젝트에 적용할 수 없다.
- **Airflow의 운영 비용.** 스케줄러·웹서버·메타DB가 추가된다. 1인 운영 부담이 늘고
  배포 환경에서도 호스팅 방법을 따로 정해야 한다. cron + 스크립트로 끝낼 수 있는 규모를
  일부러 Airflow로 가져가는 측면이 있다 — **이것도 학습 가치를 고려한 선택**이다.

## 되돌리는 조건

- **Airflow 운영 부담 초과**: Phase 2에서 Airflow 자체 운영에 수집 로직보다 많은 시간이 들면,
  cron + 파이썬 스크립트로 내린다. 백필·재시도는 직접 구현한다.
- **Phase 7 도달 실패**: 사용자가 생기지 않아 Phase 7에 가지 못하면 Kafka·Spark는
  이 프로젝트에서 쓰지 않는다. 그 경우 별도 토이 프로젝트(C안)로 학습 목적을 충족한다.
- **수집 주기 변경**: 데이터 제공자가 실시간 또는 분 단위로 갱신 주기를 바꾸면
  스트리밍 도입 근거가 생긴다. 그때 재검토한다.
- **학습 우선순위 변경**: 취업 목표가 데이터 엔지니어링 쪽으로 명확해지면,
  적합성보다 경험을 우선하는 판단도 가능하다. **그 경우 "적합하지 않음을 알고도 선택했다"는
  사실을 ADR에 명시한다.** 모르고 쓴 것과 알고 쓴 것은 다르다.
