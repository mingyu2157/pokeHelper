# ADR-015: DB 계정을 최소 권한으로 분리한다

- 상태: 채택 (2026-11-17)
- 관련: 운영 체계, `backend/sql/roles.sql`, `backend/scripts/init_roles.sh`, `backend/tests/integration/test_db_privileges.py`
- 관련 결정: [ADR-013](013-attribution-contract.md) (선언과 집행은 다르다), [ADR-014](014-restore-rehearsal.md) (복구 계정), [ADR-010](010-seed-source-of-truth.md) (시드가 진실의 원천)

## 맥락

계정이 하나였고, 그 하나가 전부 했다.

```
POSTGRES_USER=champs   ← postgres 이미지가 만드는 슈퍼유저
DATABASE_URL=postgresql+asyncpg://champs:devpassword@db:5432/champs
```

애플리케이션·마이그레이션·시드 적재·수집·테스트가 **모두 슈퍼유저로** 돌았다.
즉 애플리케이션 버그 하나로 테이블이 사라질 수 있는 상태였고, 그걸 막아주는
장치가 아무것도 없었다.

사용처를 전부 찾아보니 **DDL 이 필요한 곳은 `alembic/env.py` 하나뿐**이었다.
런타임, 시드 적재(`upsert` + `delete`), 수집, 정리, 통합테스트는 전부 DML 이다.
`TRUNCATE` 를 쓰는 곳도 없었다. 분리선이 깔끔하게 그어졌다.

그리고 [ADR-014](014-restore-rehearsal.md) 에서 하나가 확정됐다 — `pg_dump` 는
데이터베이스 하나만 덤프하고 **ROLE 은 담지 않는다.** 백업과 복구가 각각 어떤
권한으로 도는지 정해야 복구 절차가 완성된다.

## 선택지

### 1. 계정을 몇 개로 나눌 것인가

#### A안: 단일 계정 유지
- 장점: 설정이 하나다. 깨질 곳이 없다.
- 단점: **최소 권한이 없다.** 애플리케이션 버그나 SQL 인젝션이 스키마에 닿는다.

#### B안: 2개 — 앱(DML) / 마이그레이션(DDL)
- 장점: 가장 큰 위험(런타임이 DDL 을 쥐는 것)을 제거한다. 설정 둘뿐이다.
- 단점:
  - 디버깅·분석을 할 때 쓸 읽기 전용 계정이 없다. 결국 앱 계정이나 슈퍼유저로 붙는다.
  - **백업을 어느 계정으로 돌릴지 애매하다.** `pg_dump` 에 쓰기 권한은 불필요하다.

#### C안: 3개 — 앱 / 마이그레이션 / 읽기 전용
- 장점:
  - 읽기 작업(디버깅, 분석, **백업**)이 쓰기 권한 없이 돈다.
  - `pg_read_all_data`(PG14+)로 읽기 계정이 **미래 테이블까지** 자동 포함한다.
  - 백업 전용 계정을 따로 두지 않아도 된다 — 읽기 계정이 그 역할을 겸한다.
- 단점:
  - 설정과 비밀번호가 셋으로 늘어난다.
  - 각 계정이 무엇을 할 수 있는지 문서와 테스트로 관리해야 한다.

#### D안: 4개 — C안 + 백업 전용 계정
- 장점: 백업 계정의 권한을 더 좁힐 수 있다(특정 테이블만 등).
- 단점:
  - `pg_dump` 는 **전체 읽기**가 필요하다. 좁히면 덤프가 불완전해지고, 좁히지 않으면
    읽기 계정과 권한이 동일하다. **똑같은 권한의 계정이 둘 생긴다.**
  - 계정이 늘수록 "어느 계정으로 붙어야 하나"를 틀릴 확률이 올라간다.

### 2. 역할을 어떻게 적용할 것인가

#### E안: postgres 이미지의 initdb 훅만 쓴다
- 장점: `docker compose up` 만으로 준비된다. 추가 명령이 없다.
- 단점:
  - **데이터 디렉토리가 빈 첫 기동에만 실행된다.** 이미 시드가 든 개발 DB 에는
    적용되지 않고, `down -v` 로 비우면 시드가 날아간다.
  - **CI 에서 쓸 수 없다.** 서비스 컨테이너에는 파일을 넣을 자리가 없다.

#### F안: 실행 스크립트만 쓴다
- 장점: 모든 환경에서 같은 한 가지 경로. CI 도 같은 명령을 쓴다.
- 단점: 새 환경에서 `docker compose up` 직후 앱이 붙지 못한다 (계정이 없어서).
  처음 쓰는 사람이 막힌다.

#### G안: 둘 다. 멱등 SQL 하나를 두 경로가 공유한다
- 장점: 새 환경은 자동, 기존 DB·CI 는 수동 1회. SQL 은 한 파일이라 어긋나지 않는다.
- 단점: 호출 지점이 둘이라 양쪽을 다 검증해야 한다.

### 3. 비밀번호를 SQL 에 어떻게 넘길 것인가

#### H안: `\getenv` 로 환경변수를 읽는다
- 장점: initdb 훅이 psql 호출을 감쌀 필요가 없다. SQL 파일만 마운트하면 된다.
- 단점:
  - **`\getenv` 는 psql 16 부터다.** CI 러너의 psql 버전을 보장할 수 없다.
  - **환경변수가 없으면 빈 문자열이 된다** → 비밀번호 없는 계정이 조용히 만들어진다.

#### I안: `psql -v` 로 넘긴다
- 장점:
  - `-v` 는 psql 전 버전에서 쓸 수 있다.
  - **변수를 안 넘기면 문법 오류로 즉시 실패한다** (실측 확인). 조용한 실패가 없다.
- 단점: initdb 경로에서 psql 호출을 감싸는 `.sh` 훅이 하나 더 필요하다.

## 결정

**1번은 C안(3개), 2번은 G안(둘 다), 3번은 I안(`-v`).**

세부 사항:

| 계정 | 권한 | 쓰는 곳 |
|---|---|---|
| `champs_migrate` | `USAGE, CREATE ON SCHEMA public` + 객체 소유 | `alembic upgrade`, **`restore.sh`** |
| `champs_app` | SELECT / INSERT / UPDATE / DELETE + 시퀀스 `USAGE, SELECT`. **DDL·TRUNCATE 없음** | FastAPI, 시드 적재, 수집, 정리, 통합테스트 |
| `champs_read` | `pg_read_all_data` | 디버깅·분석, **`backup.sh`** |
| `champs` (기존) | 슈퍼유저 | **`init_roles` 와 긴급 상황 전용. 애플리케이션은 쓰지 않는다** |

1. 네 번째 줄은 새 계정이 아니다. `POSTGRES_USER` 는 postgres 이미지가 반드시 만들고
   없앨 수 없으므로, **"있지만 쓰지 않는다"를 명시하는 것**이 최소 권한이다.
2. **`Settings` 의 기본값을 분리 계정으로 둔다.** 부트스트랩 계정을 기본값으로 두면
   `.env` 를 만들지 않은 환경이 조용히 슈퍼유저로 돈다.
3. `alembic/env.py` 만 `migration_database_url` 을 읽는다. 런타임 코드가 이 값을
   읽으면 분리가 무의미해진다.
4. **기존 객체의 소유권을 `champs_migrate` 로 옮긴다.** 안 하면 alembic 이
   `ALTER TABLE` 에서 권한 오류로 멈춘다 (기존 테이블은 부트스트랩 계정 소유다).
5. ★ **`ALTER DEFAULT PRIVILEGES FOR ROLE champs_migrate`** 를 반드시 건다.
   `GRANT ... ON ALL TABLES` 는 실행 시점의 테이블만 잡는다. `FOR ROLE` 을 빼면
   스크립트를 실행한 역할이 만든 객체에만 적용되고 **정작 alembic 이 만드는 것은
   빠진다.** 오늘은 통과하고 다음 마이그레이션에서 앱이 죽는다.
6. **리허설도 분리된 계정으로 돈다** — 백업은 `champs_read`, 복구는 `champs_migrate`.
   슈퍼유저로 돌리면 "운영에서 백업 계정이 덤프를 못 만드는" 상황을 못 잡는다.
7. **권한 테스트는 기본 실행에 포함한다** (`tests/integration/`, `db` 마커).
   리허설처럼 opt-in 으로 만들면 아무도 안 돌리는 검증이 하나 더 늘어난다.
   거부 테스트는 실패하는 연산이고 허용 테스트는 롤백하므로 개발 DB 를 더럽히지 않는다.

## 포기한 것

- **설정의 단순함.** URL 둘, 비밀번호 셋이 늘었다. `.env` 를 갱신하지 않은 환경은
  앱이 붙지 못하고, 실제로 이 작업 중에 그 상황을 겪었다 (JOURNAL 2026-11-17).
- **`docker compose up` 만으로 끝나는 설치.** 이미 데이터가 있는 DB 는
  `init_roles.sh` 를 한 번 돌려야 한다. 새 환경은 initdb 훅으로 자동이지만,
  **두 경로가 생겼고 둘 다 유지해야 한다.**
- **비밀번호 관리.** 개발용 평문 비밀번호를 `.env.example` 에 적었다. 운영에서는
  시크릿 관리가 필요하고, 그건 배포 대상이 정해진 뒤의 일이다 (ADR-001 미결).
- **ROLE 백업.** 역할은 클러스터 전역 객체라 `pg_dump` 에 들어가지 않는다.
  빈 서버 완전 복구는 `init_roles.sh` 를 먼저 돌려야 하고, `pg_dumpall --roles-only`
  는 아직 없다. 지금은 **스크립트가 백업의 역할을 대신한다** — 역할 정의가
  저장소에 있으므로 재현 가능하다. 다만 운영에서 손으로 바꾼 권한은 유실된다.
- **운영 환경에서의 검증.** CI 단계를 추가했지만 **아직 한 번도 돌지 않았다.**
  러너에 `psql` 이 있다는 전제가 실측되지 않았다.
- **세분화.** 테이블별·컬럼별 권한이나 RLS 는 쓰지 않았다. 스키마가 작고
  멀티테넌시가 없어서 지금은 과하다.

## 되돌리는 조건

- **배포 대상이 정해지면 재검토한다** (Phase 6). RDS 는 슈퍼유저를 주지 않고
  `rds_superuser` 로 대체하며, `pg_read_all_data` 부여 방식도 다르다. 역할 생성
  주체가 달라지므로 `init_roles.sh` 의 전제가 바뀐다.
- **멀티테넌시나 민감 데이터가 들어오면** 테이블 단위 권한이나 RLS 로 내려간다.
  지금의 "스키마 전체에 DML" 은 그때 너무 넓다.
- **읽기 계정의 용도가 갈리면** (예: 외부 분석 도구에 계정을 주게 되면) 백업과
  분석을 분리한다. 그때가 D안을 다시 보는 시점이다 — 지금 D안을 피한 이유는
  "권한이 같은 계정 둘"이었고, 용도가 갈리면 그 이유가 사라진다.
- **CI 에서 `psql` 을 못 쓰게 되면** 역할 생성을 파이썬(asyncpg)으로 옮긴다.
  그 경우 `-v` 대신 파라미터 바인딩을 쓰게 되고, SQL 파일이 단일 원천인 구조가 깨진다.
- **`init_roles.sh` 와 initdb 훅이 어긋나기 시작하면** 둘 중 하나를 버린다.
  같은 SQL 을 공유하는 지금 구조가 유지되는 한에서만 G안이 유효하다.
