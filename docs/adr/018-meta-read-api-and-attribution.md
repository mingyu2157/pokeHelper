# ADR-018: 메타 읽기 API 의 노출 범위와 출처 표기 집행

- 상태: 채택 (2026-11-18)
- 관련: Phase 2-7, `api/v1/meta.py`, [ADR-013](013-attribution-contract.md), [ADR-009](009-move-data-source.md)

## 맥락

Phase 2 에서 수집·저장·검증까지 끝냈지만 **읽는 코드가 없었다.** 수집 결과에
출처 표기(`Attribution`)를 실어 나르는 계약까지 만들어 두고(ADR-013), 정작
그걸 소비하는 화면이 없어서 라이선스 의무가 **이행되지 않은 상태로 남아 있었다.**

championsbattledata 라이선스 조건 중 이 작업과 직접 충돌하는 것이 둘이다.

> - 출처 표기 필수. 데이터를 표시하는 **모든 화면**에 표기와 링크.
>   푸터 한 줄로 끝내지 말고 통계가 나오는 화면마다.
> - **경쟁 API·덤프·대량 다운로드 서비스 금지.** 우리 API 가 이 데이터를
>   그대로 반환하는 공개 엔드포인트를 노출하면 안 된다.

두 번째가 설계를 직접 제약한다. 메타를 화면에 띄우려면 API 가 통계를 실어
보내야 하는데, **어디까지가 "표시에 필요한 만큼"이고 어디부터가 "덤프"인가**를
정해야 한다. 그 선을 문서가 아니라 **코드와 테스트에** 박아 두지 않으면,
다음에 누가 `limit` 을 늘리거나 편의로 모델 전체를 직렬화하는 순간 조용히 넘는다.

### 측정으로 드러난 것 — 한글명 매핑이 비어 있다

작업 전 활성 스냅샷의 선택지 id 를 시드 테이블과 대조했다.

| 카테고리 | 서로 다른 id | 한글명 있음 |
|---|---|---|
| moves | 208 | **208** |
| abilities | 78 | **78** |
| natures | 22 | **22** |
| teammates | 45 | **45** |
| **items** | **89** | **0** |

도구 한영 매핑(Phase 2-3c)이 통째로 비어 있다. 화면을 만들려면 이걸 어떻게
표시할지부터 정해야 했다. 사용률 퍼센트가 전부 `NULL` 인 것도 같이 확인했는데
이건 설계대로다 — 출처 API 가 순위만 준다.

## 선택지

### 1. 노출 범위를 어디까지로 할 것인가

#### A안: 스냅샷 전체를 주는 엔드포인트 하나
- 장점: 프론트가 한 번 받아 전부 처리한다. 호출이 적다.
- 단점: **그게 바로 덤프다.** 라이선스가 금지한 형태와 구분되지 않는다.
  "우리 UI 가 쓰려고 만들었다"는 의도는 엔드포인트에 적히지 않는다.

#### B안: 상한 있는 목록 + 개별 상세 (채택)
- 장점: 한 번에 나가는 양에 **코드로 된 상한**이 있다. 전체를 받으려면
  N 번 호출해야 하고, 그건 요청 패턴으로 드러난다.
- 단점: 호출이 늘고, 상한값을 정해야 한다(자의적이다).

#### C안: 서버 컴포넌트에서만 읽고 API 를 아예 공개하지 않는다
- 장점: 외부에서 호출할 공개 엔드포인트가 없다. 가장 안전하다.
- 단점: SSR 외의 모든 경로(클라이언트 상호작용, 추후 모바일)가 막힌다.
  Phase 3 의 매치업 화면이 곧 클라이언트 호출을 필요로 한다.

### 2. 한글명 매핑이 없는 선택지를 어떻게 표시할 것인가

#### D안: 영문 id 를 그대로 띄운다
- 장점: 화면이 비지 않는다. 구현이 없다.
- 단점: ★ 사용자는 그게 **우리가 고른 표기**라고 읽는다. "choicescarf" 가
  한글명 자리에 있으면 그건 이 서비스의 표기다. CLAUDE.md 8-4 가
  "영문명을 통과시키지 않는다"고 못 박은 바로 그 모양이다.

#### E안: 도구 섹션을 숨긴다
- 장점: 틀린 표기가 나가지 않는다.
- 단점: 화면은 **완성된 것처럼 보이면서** 한 카테고리가 통째로 없다.
  사용자도 나중의 우리도 빠진 걸 모른다. 미완성을 숨기는 쪽이다.

#### F안: `name_ko = null` 로 내보내고 미매핑임을 화면에 표시한다 (채택)
- 장점: 사실대로다. 영문 id 는 **원문**으로 보여주되 "한글명 미등록"을 붙여
  우리 표기가 아님을 밝힌다. 남은 일이 화면에 드러난다.
- 단점: 화면이 덜 깔끔하다. 미매핑이 89건이라 눈에 띈다.

### 3. 프론트 타입을 어떻게 만들 것인가

#### G안: 손으로 쓴다 (현행)
- 장점: 의존성이 없다.
- 단점: 백엔드가 필드를 바꿔도 프론트는 **타입체크를 통과하면서** 틀린 모양을
  믿는다. 실패가 런타임까지 미뤄진다. CLAUDE.md 6장 위반이기도 하다.

#### H안: `openapi-typescript` 도입 (채택)
- 장점: 스키마가 단일 원천이 된다. CI 에서 **재생성 후 비교**로 어긋남을 잡는다.
- 단점: devDependency 가 하나 늘고, 생성물을 커밋해야 한다.

## 결정

**1번은 B안, 2번은 F안, 3번은 H안.**

세부 사항:

1. **`limit` 에 상한을 둔다** (`MAX_ENTRY_LIMIT = 60`, 기본 30). 저장소의
   `ranked_entries()` 는 `limit` 에 **기본값을 두지 않는다** — 기본값이 있으면
   "전부 주세요"가 기본이 되고 그 순간 덤프가 된다.
2. ★ **`pokemon_meta.raw`(수집 원본)는 저장소가 SELECT 조차 하지 않는다.**
   선택하지 않으면 실수로 나갈 일도 없다. 그래도 응답 전체를 훑어
   `raw` 키가 없는지 테스트가 다시 본다 — 누가 편의로 모델 전체를 직렬화하면
   조용히 새기 때문이다.
3. ★ **`attributions` 에 기본값을 두지 않는다.** 표기 누락은 **조용한 위반**이다.
   화면에는 숫자가 멀쩡히 나오고 출처 줄만 비어 있다. 스키마가 막고,
   "기본값이 없다"는 사실 자체를 테스트가 단정한다.
4. **출처 조회는 fail-closed 다.** `source` 문자열 → 표기 변환을 레지스트리로
   두고, 모르는 출처는 `None` 이 아니라 예외다. 두 번째 출처를 붙이는 사람이
   등록을 빠뜨리면 **그 데이터가 처음 화면에 나가려는 순간** 실패한다.
5. **표기는 목록(`list`)으로 내보낸다.** 지금은 하나지만, 기술 **위력·명중**을
   화면에 올리는 순간 op.gg 표기가 함께 나가야 한다 (ADR-009). 그때 구조를
   바꾸지 않아도 되게 미리 목록으로 두고, op.gg 표기도 **미리 등록해 둔다.**
6. **읽기 저장소를 `repositories/meta.py` 로 분리한다.** `snapshots.py` 는
   수집·전환·정리 쪽이다. 한 파일에 두면 조회를 고칠 때 전환 로직을 같이 읽는다.
7. **서비스는 사이트 이름을 모른다.** 출처 표기 레지스트리를 별도 모듈로 떼어,
   읽기 서비스가 `championsbattledata.py` 를 import 하지 않게 했다 (CLAUDE.md 8-6).
8. **스키마를 파일로 커밋한다** (`backend/openapi.json`). 프론트 타입 생성기가
   백엔드 서버를 띄우지 않고도 돌아야 CI 에서 쓸 수 있다.
9. ★ **CI 가 두 지점에서 어긋남을 잡는다.**
   - 백엔드: `dump_openapi --check` — 코드와 커밋된 스키마가 같은가
   - 프론트: `check:api` — 커밋된 타입이 그 스키마에서 나온 그것인가
   둘을 나눈 이유는 어긋남이 두 단계에서 각각 생기기 때문이다.
10. **`check:api` 는 git 에 의존하지 않는다.** 임시 파일로 생성해 `diff` 로
    비교한다. 처음엔 `git diff --exit-code` 로 썼는데 **프론트 컨테이너에
    git 이 없어서** 로컬에서 검증할 수 없었다. CI 에서만 도는 검사는
    RED 를 확인할 수 없다.

## 포기한 것

- **한 번에 전체를 받는 편의.** 프론트가 60종을 넘겨 받으려면 설계를 다시 봐야
  한다. 지금 화면은 30종이면 충분하다.
- **깔끔한 화면.** 도구 89종이 "한글명 미등록"으로 뜬다. 보기 좋지 않지만
  **비어 있는 것보다 정확하다.**
- **의존성 0 의 프론트.** `openapi-typescript` 가 늘었다. 다만 이 패키지가
  들여온 신규 취약점은 **0건**이다 (`npm audit` 상의 `zod` 는 기존
  `eslint-config-next` 경로다).
- **클라이언트 측 데이터 패칭.** 지금은 서버 컴포넌트에서만 읽는다. Phase 3
  에서 상호작용이 생기면 그때 클라이언트 경로를 연다.
- **캐싱.** `cache: "no-store"` 다. 수집 시각을 화면에 띄우는데 캐시된 옛 시각을
  보여주면 그 표시 자체가 거짓이 된다. 트래픽이 생기면 다시 본다.

## 되돌리는 조건

- **도구 한영 매핑이 끝나면** (Phase 2-3c) 미매핑 표시 테스트의 전제 단정
  (`test_the_check_is_not_vacuous`)이 깨진다. 그때 F안의 표시 규칙을 다시 본다 —
  미매핑이 0건이면 그 UI 는 죽은 코드다.
- **출처가 사용률 퍼센트를 주기 시작하면** `usage_rate` 가 채워지고, 화면에
  열을 추가한다. 지금 "퍼센트는 주지 않습니다" 안내문도 같이 내린다.
- **`MAX_ENTRY_LIMIT` 을 올려야 할 요구가 생기면** 그건 화면 요구가 아니라
  배치 요구일 가능성이 높다. 올리기 전에 **누가 왜 필요한지**부터 본다.
  덤프 금지 조항이 걸린 지점이다.
- **두 번째 출처를 붙이면** 표기 레지스트리에 등록해야 하고, 등록을 빠뜨리면
  실패한다. 그 실패는 의도된 것이다.
- **공개 배포하면** 이 API 가 외부에서 호출 가능해진다. rate limit 과
  `/metrics` 차단을 함께 다뤄야 한다 (ADR-016 되돌리는 조건).

## 결과

(2026-11-18, 같은 커밋에서 확인)

- 백엔드 **686 passed** (기존 665 + 메타 21), ruff/format/mypy 전부 통과.
- 프론트 `check:api` / `lint` / `typecheck` / `build` 전부 통과.
- 라우트 실측: `/` 200, `/meta` 200, `/meta/garchomp` 200, `/meta/notapokemon` **404**.
- 화면에서 확인한 것: 한글명(한카리아스·누리레느), 출처 표기와 링크,
  수집 시각, "공식 제휴 아님", 노력치 HABCDS 표기(`H2A32S32`),
  도구의 "한글명 미등록" 표시.
- 두 어긋남 검사를 RED 로 확인했다 — 스키마 설명 한 줄을 고치자
  `dump_openapi --check` 가 1 로 끝났고, 생성 타입의 이름 하나를 고치자
  `check:api` 가 1 로 끝났다.

**작업 중 기존 테스트가 내 실수를 잡았다.** `MetaSpreadOut` 독스트링에
기존 시리즈 노력치 표기를 **부정하는 문장으로** 썼는데
("…표기는 이 프로젝트에 존재하지 않는다"), 그 독스트링이 OpenAPI 설명으로
나가면서 `test_no_ev_or_252_in_the_contract` 가 깨졌다. 가드는 문맥을 모른다 —
계약에 그 문자열이 **있느냐**만 본다. 부정문으로도 쓰지 않는 게 맞다.
