- 상태: 채택 (2026-11-19)
- 관련: Phase 6, `infra/terraform/`
- 관련 결정: [ADR-019](019-deployment-target-and-prerequisites.md) (배포 대상과 선결 조건),
  [ADR-011](011-scheduler-staging.md) (CLI 먼저, 스케줄러는 나중),
  [ADR-012](012-airflow-docker-operator.md) (Airflow·DockerOperator),
  [ADR-013](013-attribution-contract.md) (요청 예절 게이트),
  [ADR-014](014-restore-rehearsal.md) (복구 리허설 — DR 전략의 검증 절차),
  [ADR-016](016-observability-metrics.md) (관측 지표)

## 맥락

ADR-019 가 "ECS Fargate 에 Terraform 으로 올린다"까지 정했다. 그 안에서 실제로
무엇을 몇 개 띄우는지는 정하지 않았고, 거기서 비용이 결정된다.

작업에 들어가기 전에 **단가를 먼저 조회했다.** 추측한 비용으로 고른 구성은
청구서를 받고 나서야 틀린 것을 안다. 아래는 전부 AWS 공개 가격표 API 에서
받은 서울 리전(`ap-northeast-2`) 값이다 (2026-11-19 조회, 월 환산 730시간).

| 항목 | 단가 | 월 |
|---|---|---|
| Fargate x86 vCPU / 메모리 | $0.04656/h · $0.00511/GB·h | — |
| **Fargate ARM vCPU / 메모리** | **$0.03725/h · $0.00409/GB·h** | — |
| ALB | $0.0225/h + $0.008/LCU·h | $16.43 + LCU |
| **NAT Gateway** | **$0.059/h + $0.059/GB** | **$43.07** + 데이터 |
| VPC 인터페이스 엔드포인트 | $0.013/h (AZ당) | $9.49 |
| 공인 IPv4 | $0.005/h | $3.65 |
| RDS PostgreSQL `db.t4g.micro` Single-AZ | $0.025/h | $18.25 |
| RDS `db.t4g.micro` Multi-AZ | $0.051/h | $37.23 |
| ElastiCache `cache.t4g.micro` | $0.024/h | $17.52 |
| EKS 컨트롤 플레인 (참고) | $0.10/h | $73.00 |
| CloudWatch Logs 수집 / 저장 | $0.76/GB · $0.0314/GB·월 | — |
| CloudWatch 알람 | $0.10/알람·월 | — |

★ **ARM(Graviton)이 x86 보다 약 20% 싸다.** 우리 이미지는 파이썬이고 의존
패키지 전부 `aarch64` 휠이 있다. 아래 Fargate 비용은 전부 ARM 기준이다.

세 가지가 서로 얽혀 있어 따로 정할 수 없었다.

1. **NAT Gateway 를 둘 것인가**가 월 $43 을 좌우하고, 그 선택이 스케줄러를
   Lambda 로 할 수 있는지까지 결정한다.
2. **Prometheus 가 ECS 태스크를 어떻게 찾는가.** 태스크는 재배치되면 IP 가 바뀐다.
3. **Airflow 가 그대로는 올라가지 않는다.** 현재 DAG 는 `DockerOperator` +
   `unix://var/run/docker.sock` 인데, **Fargate 에는 Docker 소켓이 없다.**

## 선택지

### 1. 태스크를 어느 서브넷에 두는가

#### A안: 프라이빗 서브넷 + NAT Gateway — 월 $43.07 + $0.059/GB

- 장점: 교과서 구성. 태스크에 공인 IP 가 없고, **보안그룹을 잘못 고쳐도
  라우팅이 없어서 외부에서 닿지 않는다.** 방어선이 둘이다.
- 단점: 이 프로젝트 전체 비용의 1/3 이 여기 들어간다.

#### B안: 퍼블릭 서브넷 + 공인 IP, 인바운드는 ALB 보안그룹만 — 태스크당 월 $3.65

- 장점:
  - 태스크 2~3개면 월 $7~11. NAT 대비 **$32~36 절약.**
  - 외부 API 호출이 자기 공인 IP 로 바로 나간다.
- 단점:
  - ★ **방어선이 하나로 줄어든다.** 보안그룹 한 줄(`0.0.0.0/0:8000`)이 틀리면
    바로 열린다. 프라이빗이면 같은 실수를 해도 닿지 않는다.
  - **공인 IP 가 고정되지 않는다.** 태스크 재배치 시 바뀌므로, 외부 API 가
    IP 허용목록을 요구하면 깨진다.
  - 보안 벤치마크(CIS 등)가 "워크로드는 프라이빗에"를 항목으로 둔다. 설명이 필요하다.
- 손익분기: 공인 IP $3.65 × N vs NAT $43.07 → **태스크 12개를 넘으면 A안이 싸다.**

#### C안: 프라이빗 + VPC 인터페이스 엔드포인트만 (NAT 없음)

- ★ **이 아키텍처에서 불가능하다.** 엔드포인트는 **AWS 서비스만** 뚫는다.
  우리 수집기는 `championsbattledata.com` 을 호출한다 → 수집이 죽는다.
- 비용도 안 싸다: ECR api·ECR dkr·logs·ssm 4개면 AZ 하나에 $37.96.

#### D안: NAT 인스턴스를 직접 운영 — 월 $4 내외

- 장점: 싸다.
- 단점: 단일 장애점을 직접 운영한다. 얻는 학습 대비 운영 부담이 크다.

### 2. Redis

#### E안: ElastiCache `cache.t4g.micro` — 월 $17.52

- 장점: 공유 카운터가 실제로 공유된다. Phase 4 의 LLM 응답 캐시(TTL 7일)도
  재배포를 넘어 살아남는다.
- 단점: 월 $17.52.

#### F안: 태스크 안에 Redis 사이드카 — 월 ~$2

- 단점: ★ **태스크마다 별도 Redis 라 공유가 깨진다.** ElastiCache 를 쓰려던
  이유 자체를 무효화한다.

#### G안: 태스크 1개 + 메모리 저장소 — 무료

- 단점:
  - ★ 운영 이미지가 `gunicorn -w 2` 다. **실효 한도가 2배**(계산 40/분)가 된다.
    이 사실은 `TestMemoryStoreIsPerProcess` 가 이미 테스트로 박아뒀다.
  - `assert_production_ready()` 가 기동을 거부한다 (ADR-019 9번).
  - LLM 캐시가 재배포마다 날아간다.

### 3. DB

#### H안: RDS PostgreSQL `db.t4g.micro` Single-AZ — 월 $18.25 + 스토리지

- 장점: 자동 백업·PITR·스냅샷을 AWS 가 맡는다. ★ **ADR-014 가 검증한 복구
  절차의 운영 대응물이 RDS 스냅샷**이다.
- 단점: AZ 하나가 죽으면 서비스가 멈춘다. 복구는 가능하지만 자동이 아니다.

#### I안: 같은 인스턴스 Multi-AZ — 월 $37.23

- 장점: AZ 장애 시 자동 페일오버.
- 단점: 가용성 요구가 없는 포트폴리오에서 두 배를 낸다.

#### J안: Fargate 태스크 안의 Postgres + EFS — 월 ~$8

- 단점: ★ **자동 백업도 PITR 도 스냅샷도 없다.** ADR-014 로 검증한 복구 절차를
  운영에서 쓸 수 없다. **검증한 절차를 못 쓰는 DB** 를 고르는 건 거꾸로다.

#### K안: Aurora Serverless v2

- 단점: ACU 단가가 높아 상시 가동이면 H안보다 비싸다. ETL 이 매일 깨우므로
  auto-pause 의 이득도 제한적이다.

### 4. 스케줄러 — Airflow 를 어떻게 하는가

현재 DAG 의 독스트링이 이미 이렇게 적어뒀다.

> DAG 는 "언제, 몇 번 시도할지"만 안다. 실제 일은 `pokehelper-backend` 이미지
> 안의 CLI 가 한다. 그래서 **Airflow 를 걷어내도 수집이 돈다.**

ADR-011 의 "CLI 를 먼저, 스케줄러는 나중"이 여기서 값을 치른다.

#### L안: Airflow 를 ECS 에 올리고 `EcsRunTaskOperator` 로 교체 — 월 ~$61

- 장점: "Airflow 를 운영했다"가 남는다. 재시도·의존 그래프가 그대로 산다.
- 단점: 태스크 3개(scheduler/apiserver/dag-processor) + 전용 DB. 스케줄 하나에
  월 $61 이다.

#### M안: MWAA (관리형 Airflow)

- 단점: 최소 구성도 수백 달러대. 이 프로젝트 전체 비용의 몇 배다.

#### N안: EventBridge Scheduler → **ECS RunTask** — 월 ~$0.2

- 장점:
  - cron 표현식으로 **백엔드 이미지를 그대로** 한 번 실행한다. 진입점도 같다.
  - 15분 제한이 없다. 요청 간 1초 지연(ADR-013)이 하드 제약이라 수집 대상을
    늘리면 수 분이 걸리는데, 상한이 없는 구조가 안전하다.
- 단점: ★ **재시도·의존 표현이 약하다.** 지금 DAG 의
  `[수집] --성공하면--> [만료 정리]` 를 EventBridge 만으로는 그릴 수 없다.
  Step Functions 를 붙이면 되지만 컴포넌트가 또 하나 는다.

#### O안: EventBridge Scheduler → **Lambda**

- ★ **구조적으로 불가능하다.** 수집은 외부 인터넷과 프라이빗 RDS **양쪽**에
  닿아야 하는데 Lambda 는 둘을 동시에 만족시키지 못한다.

  | Lambda 구성 | 외부 API | 프라이빗 RDS |
  |---|---|---|
  | VPC 에 붙이지 않음 | ✅ | ❌ |
  | VPC 에 붙임 (프라이빗/퍼블릭 어느 쪽이든) | ❌ **NAT 필요** | ✅ |

  AWS 공식 문서:
  > Connecting a function to a public subnet doesn't give it internet access
  > or a public IP address.

  즉 Lambda 를 쓰면 **결정 1에서 없앤 NAT 가 월 $43 로 되살아난다.**
  비용이 가장 적을 것 같았던 선택지가 실제로는 가장 비싸다.
- 부수적으로: 핸들러 진입점이 따로 필요해 **배포 산출물이 두 벌**이 되고,
  15분 타임아웃이 수집 대상 수의 상한이 된다.

### 5. Prometheus 가 스크랩 대상을 어떻게 찾는가

#### P안: Cloud Map 서비스 디스커버리 + `dns_sd_configs`, Prometheus 는 별도 태스크

- 장점: 백엔드 태스크가 여러 개여도 전부 찾는다. 표준적인 방법이다.
- 단점: 태스크 2개($16.58) + 공인 IP 2개($7.30) = 월 $23.88.
  `prometheus.yml` 의 타깃을 DNS 기반으로 바꿔야 한다.

#### Q안: CloudWatch Metrics 로 지표를 보낸다

- 장점: 관리형. 알람·대시보드가 콘솔에 있다.
- 단점: ★ **PromQL 을 버린다.** 함께 버려지는 것:
  `rules/alerts.yml`(경보 3개), `grafana/dashboards/*.json`, 그리고
  **`test_alert_rules.py`** — 경보가 참조하는 지표명을 노출 지표와 교차검증하는
  테스트다. 검증할 대상 자체가 사라진다.

#### R안: Prometheus·Grafana 를 **백엔드 태스크의 사이드카**로 — 월 ~$3

- 장점:
  - ★ **서비스 디스커버리 문제가 사라진다.** `localhost:8000/metrics` 를 긁는다.
    Cloud Map 이 필요 없다.
  - `prometheus.yml` 을 거의 그대로 쓴다. ADR-016 의 자산 전부가 산다.
  - 비용은 메모리 증설분(1GB)뿐이다.
- 단점:
  - **태스크가 교체되면 지표 이력이 날아간다.** (EFS 로 완화 가능, 월 $1 미만)
  - **백엔드 태스크를 늘리면 각 Prometheus 가 자기 태스크만 본다.**

### 6. 프론트엔드

#### S안: ECS 서비스로 Next.js SSR — 월 $8.29 + 공인 IP $3.65

- 장점: CLAUDE.md 2장이 Next.js 를 고른 이유(SSR → SEO)를 유지한다.
  `/meta/[pokemonId]` 는 매일 바뀌는 스냅샷을 서버에서 렌더해야 한다.
- 단점: 태스크가 하나 는다.

#### T안: S3 + CloudFront (static export) — 월 ~$1

- 단점: ★ **SSR 을 버린다.** 크롤러는 JS 실행을 보장하지 않아 CSR 페이지를
  빈 페이지로 본다. 그리고 `/meta/[pokemonId]` 는 **매일 수집되는 DB 스냅샷에
  따라 내용이 바뀌므로**, 빌드 시점 고정이면 매일 재빌드 파이프라인이 필요하다.
  월 $7 아끼려고 파이프라인을 하나 더 만드는 셈이다.

### 7. 상시 가동인가

#### U안: 상시

- 장점: 언제든 보여줄 수 있는 URL 이 있다.
- 단점: 월 전액.

#### V안: 필요할 때만 `terraform apply` → `destroy`

- 장점: 시간 과금 항목이 1/4 로 줄어든다. 왕복 자체가 IaC 증빙이다.
- 단점: 즉시 보여줄 수 없다. 공인 주소가 매번 바뀐다.

### 세부 사항

1. **보안그룹 인바운드는 아래 넷뿐이다.** 소스를 CIDR 이 아니라 **다른
   보안그룹 ID** 로 지정한다.

   | 보안그룹 | 포트 | 소스 |
   |---|---|---|
   | ALB | 443 | `0.0.0.0/0` ← **유일하게 전체 개방** |
   | 태스크 | 8000, 3000 | ALB 보안그룹 |
   | RDS | 5432 | 백엔드 태스크 보안그룹 |
   | ElastiCache | 6379 | 백엔드 태스크 보안그룹 |

2. ★ **보안그룹 규칙을 테스트가 집행한다.** `terraform plan -out` 의 JSON 출력을
   읽어 "ALB 보안그룹 말고는 `0.0.0.0/0` 인바운드가 없다"를 단정한다.
   B안의 방어선이 하나뿐이므로, 그 하나가 맞는지는 사람의 눈이 아니라 테스트가
   본다. **보안그룹은 틀려도 서비스가 멀쩡히 돈다** — ADR-013·015 와 같은 모양이다.

3. **공인 IP 가 필요한 이유는 외부 API 만이 아니다.** ECR 이미지 pull,
   CloudWatch Logs 전송, SSM 파라미터 조회에도 인터넷 경로가 필요하다.
   외부 API 를 부르지 않아도 퍼블릭이거나 NAT 거나 엔드포인트여야 한다.

4. **DR 전략은 백업/복구(Backup & Restore)다.** 먼저 목표를 정하고 수단을 골랐다.

   | | 목표 | 수단 | 추가 비용 |
   |---|---|---|---|
   | RPO | **5분** | 자동 백업 + PITR | 0 (할당 스토리지만큼 무료) |
   | RTO | **1시간** | 스냅샷 복원 + `terraform apply` | 0 |
   | 리전 장애 | 복구만 | 크로스리전 스냅샷 복사 | 스냅샷 저장분 |

   ★ **파일럿 라이트는 채택하지 않는다.** 다른 리전에 최소 구성을 **켜두는**
   전략이고, RDS 로 하면 크로스리전 읽기 복제본이 필요해 인스턴스 비용이
   그대로 또 든다(+$18.25/월). 단일 AZ 로 비용을 줄인 결정과 어긋난다.
   RTO 가 분 단위여야 할 때 쓰는 것이고, 우리는 그런 요구가 없다.

5. ★ **ADR-014 의 복구 리허설이 이 DR 전략의 검증 절차다.** 백업→DROP→복구를
   pytest 로 돌리고 행 수·체크섬·제약 집행·시퀀스 4층으로 비교하는 것을 이미
   갖고 있다. 운영판은 "스냅샷으로 새 인스턴스를 복원하고 같은 4층을 비교"로
   그대로 옮긴다. **검증되지 않은 DR 전략은 DR 전략이 아니다.**

6. **이미지는 ARM(`linux/arm64`)으로 빌드한다.** x86 대비 약 20% 싸고,
   의존 패키지 전부 `aarch64` 휠이 있다. `docker buildx` 를 CI 에 추가한다.

7. **CloudWatch 는 로그와 청구 알람에 쓴다.** 지표·대시보드·경보는 Prometheus
   와 Grafana 가 맡는다. "CloudWatch" 한 단어가 가리키는 두 제품을 구분한다 —
   **Logs** 는 Fargate 에서 사실상 선택이 아니고, **Metrics** 는 Prometheus 와
   경쟁하는 선택이다.

8. ★ **청구 알람을 반드시 둔다** (월 $0.10). 예상치의 1.5배에서 울린다.
   비용 절감 장치가 아니라 **사고 방지 장치**다 — 로그 폭증이나 데이터 전송
   증가는 조용히 일어나고, 없으면 월말 청구서로 알게 된다.

## 포기한 것

- ★ **프라이빗 서브넷의 두 번째 방어선.** 보안그룹 한 줄이 틀리면 백엔드가
  인터넷에 열린다. 그 한 줄을 테스트로 지키지만, **테스트가 보는 것은
  `terraform plan` 이지 실제 계정 상태가 아니다.** 콘솔에서 손으로 고친 규칙은
  다음 `apply` 전까지 아무도 모른다.
- **공인 IP 의 고정.** 태스크 재배치 시 바뀐다. 외부 API 가 IP 허용목록을
  요구하면 깨진다.
- **AZ 장애 내성.** 단일 AZ 다. AZ 하나가 죽으면 **서비스가 멈추고, 복구는
  수동**이다. RTO 1시간을 받아들였다는 뜻이다.
- ★ **Airflow 의 재시도·의존 그래프.** EventBridge 는
  `[수집] --성공하면--> [만료 정리]` 를 표현하지 못한다. 두 스케줄을 각각
  띄우므로, **수집이 실패해도 만료 정리는 그대로 돈다.** 지금 만료 정리는
  보존 기간이 지난 스냅샷만 지우므로 피해가 없지만, 순서 의존이 생기면
  Step Functions 가 필요해진다.
- **운영 Airflow 경험.** 로컬 compose 에만 남는다. 즉 운영에서 도는 것과
  로컬에서 보는 것이 다른 물건이다.
- **지표 이력.** Prometheus 가 사이드카라 태스크 교체 시 날아간다.
  "지난달보다 느려졌나"는 알 수 없다.
- **백엔드 태스크의 수평 확장.** 사이드카 Prometheus 는 자기 태스크만 보고,
  메모리가 아닌 Redis 를 쓰므로 속도 제한은 괜찮지만 **관측이 파편화**된다.
- ★ **CI 는 x86 에서 테스트하고 운영은 arm64 에서 돈다.** 740개 테스트가
  전부 x86 러너에서 돌고, 실제로 배포되는 이미지는 arm64 다. 즉 **테스트한
  것과 배포하는 것의 아키텍처가 다르다.** `arm-image.yml` 은 "빌드되고 뜨는가"
  까지만 보고 **테스트를 돌리지 않는다.**
  우리 계산 엔진은 파이썬 정수·IEEE 754 배정밀도 연산뿐이라 아키텍처 간 결과가
  달라질 여지가 사실상 없어서 받아들인다. 다만 **네이티브 확장을 쓰는 의존성이
  늘면 이 가정이 깨진다.**
- **월 $98.** 포트폴리오 한 건의 상시 운영 비용으로는 작지 않다.

## 되돌리는 조건

- **네이티브 arm64 러너로 옮기는 조건**: ① 저장소가 퍼블릭이어서 무료로 쓸 수
  있다고 확인되고, ② ARM 빌드 8분이 실제로 불편해졌을 때. 둘 다여야 한다.
  옮기면 paths 필터를 풀고 매 PR 로 돌린다.
- **arm64 에서 테스트를 돌려야 하는 조건**: 네이티브 확장(C/Rust)을 쓰는
  의존성이 추가될 때. 지금은 `asyncpg`·`pydantic-core` 가 있지만 우리가 쓰는
  경로는 순수 연산이라 아키텍처 의존이 없다.
- **첫 달 청구서가 위 $98 과 크게 다르면 비용표를 고친다.** 프리 티어가
  실제로 적용돼 있었다면 더 싸게 나오는데, 그건 **만료되는 날 다시 오른다**는
  뜻이므로 그때 이 ADR 을 다시 연다. 할인을 전제로 고른 구성은 없다.
- **태스크가 12개를 넘으면 결정 1을 A안(NAT)으로 되돌린다.** 공인 IP
  $3.65 × N 이 NAT $43.07 을 넘는 지점이다.
- **백엔드 태스크를 2개 이상으로 늘리면 결정 5를 P안(Cloud Map)으로 옮긴다.**
  사이드카 Prometheus 는 자기 태스크만 본다.
- **외부 API 가 IP 허용목록을 요구하면** 결정 1을 다시 본다. 공인 IP 는
  고정되지 않는다.
- **수집과 만료 정리 사이에 진짜 순서 의존이 생기면** Step Functions 를 넣거나

- **AZ 장애를 한 번이라도 겪으면** 결정 3을 I안(Multi-AZ)으로 올린다.
  월 $18.98 을 더 내는 결정이고, 겪기 전에는 내지 않는다.
- **청구 알람이 울리면** 예상과 실제가 어긋난 것이다. 어느 항목인지 확인해
  이 ADR 의 비용표를 고친다.
- **사용자가 상시 운영을 중단하기로 하면** V안으로 옮긴다 — 결정 7의 근거에
  "후에 바뀔 수 있다"가 명시돼 있다.

**2026-11-19 — ARM 빌드 비용을 측정했다 (세부사항 6)**

ARM 을 고른 이유는 월 $6.96 절약인데, **빌드 비용을 재보지 않고 정했다.**
로컬에서 캐시 없이 측정했다.

| 이미지 | x86 | arm64 (QEMU) | 배율 |
|---|---|---|---|
| 백엔드 | **11.5초** | **2분 45초** | 14배 |
| 프론트 | **1분 10초** | **7분 47초** | 6.6배 |
| 합계 | 1분 22초 | **10분 32초** | — |

★ **결정은 유지하되 CI 전략을 바꿨다.** PR 마다 9분을 더 쓰는 것은 월 $6.96
에 비해 비싸다. 그렇다고 아예 안 돌리면 ARM 고유 실패를 배포 당일에 안다.

범위를 좁혔다 — **ARM 고유 실패는 베이스 이미지와 의존성에서만 나온다.**
aarch64 휠이 없는 패키지나 아키텍처별 바이너리가 원인이고, 애플리케이션 코드가
바뀐다고 ARM 에서만 깨지지 않는다. 그래서 `.github/workflows/arm-image.yml` 은
**Dockerfile·`pyproject.toml`·`uv.lock`·`package.json`·`package-lock.json` 이
바뀐 PR** 과 **주 1회 스케줄**에만 돈다.

확인한 것: 두 이미지 모두 `linux/arm64` 로 빌드되고 `Architecture = arm64` 다.
현재 의존성에 aarch64 휠이 없는 것은 없었다.

**2026-11-19 — CI 에서 실제로 돌려보니 8분이었다**

잡은 **초록**이었다. `정말 arm64 인가` 스텝이 두 이미지 모두 `Architecture =
arm64` 로 통과했으므로, **빌드가 됐다**가 아니라 **ARM 이미지가 나왔다**까지
확인된 것이다. 현재 의존성에 aarch64 휠이 없는 것은 없다.

로컬 10분 32초를 보고 "GitHub 러너는 코어가 적으니 **20~35분**" 이라고
예상했는데, 실제로는 **약 8분**이었다. 예상이 2~4배 보수적이었다.

★ **로컬 측정을 CI 로 외삽한 것이 틀렸다.** 로컬은 Windows 의 Docker Desktop
(VM + 파일시스템 변환)이고 CI 는 리눅스 네이티브다. 그 차이가 코어 수 차이를
덮었다. **환경이 다르면 배율도 다르다** — 다음에 빌드 시간을 추정할 때
로컬 숫자를 그대로 곱하지 않는다.

**결정은 그대로 둔다.** 8분 × 월 2~3회(Dockerfile·락파일이 바뀔 때)는 무시할
수준이다. 반대로 매 PR 로 바꾸면 **모든 PR 이 2~3분에서 8분이 된다** — 그쪽이
훨씬 비싸다. 숫자가 바뀌었지만 결론은 같다.

네이티브 arm64 러너(`ubuntu-24.04-arm`)로 옮기면 에뮬레이션이 사라져 1~2분이
되고, 그러면 매 PR 로 돌려도 된다. 퍼블릭 저장소면 무료다. 지금 하지 않는 것은
**해결할 문제가 없기 때문**이다 — 아래 되돌리는 조건에 적어둔다.

**2026-11-23 — ARM 이미지를 ECR 에 올렸다 (14초)**

`push-images.ps1` 로 백엔드·프론트를 밀었다. 두 이미지 모두 `아키텍처 확인:
arm64` 단정을 통과했다. 태그는 커밋 SHA(`a5fa6b99a4f1`), 저장 크기는 백엔드
332MB / 프론트 228MB 다. ECR 수명주기가 최신 10개만 남기므로 누적되지 않는다.

★ **빌드 시간 예측이 또 틀렸다. 이번엔 반대 방향이다.** "백엔드 3분, 프론트
8분"으로 안내했는데 실제로는 **12.3초 + 1.7초**였다. 11월 19일 측정 때 만든
**arm64 레이어가 빌더 캐시에 남아 있어** 에뮬레이션을 다시 할 필요가 없었다.
실제로 에뮬레이션한 것은 `backend/scripts/` 가 바뀌어 무효화된 마지막 두
레이어(`COPY ./scripts` + `adduser`/`chown`)뿐이고, 그게 6.9초였다.

**같은 실수의 두 번째다.** 11월 19일에는 로컬 측정을 CI 로 외삽해 2~4배
보수적으로 틀렸고, 오늘은 **캐시 상태를 빼고 "에뮬레이션은 느리다"를 그대로
적용해** 40배 보수적으로 틀렸다. 공통점은 **측정값을 조건에서 떼어내 옮긴
것**이다. 빌드 시간은 환경과 캐시 상태의 함수이고, 그 둘을 적지 않은 숫자는
다음번에 쓸 수 없다. 앞으로 빌드 시간을 적을 때는 **캐시 유무를 함께 적는다.**

★ **그래서 아키텍처 단정이 여기서 값을 했다.** 캐시 적중 빌드는 "빌드가
성공했다"가 거의 아무것도 증명하지 않는다 — 캐시가 x86 레이어였다면 그대로
재사용되고 ECS 가 태스크를 못 띄울 때까지 모른다. 단정이 통과했으므로
**캐시에서 나온 레이어도 arm64** 임이 확인됐다. 캐시를 믿을 수 있게 만드는
것이 저 한 줄이다.

**아직 확인되지 않은 것**: 매니페스트가 arm64 라는 것까지만 확인됐고, 로컬
실행은 QEMU 에뮬레이션이다. **진짜 Graviton CPU 위에서 도는지는 ECS 가 띄울
때 처음 드러난다.**
