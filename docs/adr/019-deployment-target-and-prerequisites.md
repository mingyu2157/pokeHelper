# ADR-019: 배포 대상은 ECS Fargate, 쿠버네티스는 로컬 kind 로 비교한다

- 상태: 채택 (2026-11-19)
- 관련: Phase 6, `infra/terraform/`, `backend/app/core/ratelimit.py`,
  `backend/app/api/deps.py`, `backend/app/core/config.py`
- 관련 결정: [ADR-001](001-tech-stack.md) (기술 스택 — ECS Fargate 를 처음 고른 곳),
  [ADR-012](012-airflow-docker-operator.md) (Airflow·DockerOperator),
  [ADR-013](013-attribution-contract.md) (선언과 집행은 다르다),
  [ADR-015](015-least-privilege-db-accounts.md) (최소 권한),
  [ADR-016](016-observability-metrics.md) (관측 지표 — `/metrics` 차단을 되돌리는 조건으로 예고했다)

## 맥락

배포를 시작하기 직전에 세 가지가 동시에 걸렸다.

**1. 운영 이미지를 한 번도 돌려본 적이 없었다.**
`docker-compose.prod.yml` 이 CLAUDE.md 3장의 디렉터리 구조에 적혀 있지만 존재하지
않았고, `Dockerfile` 의 운영 스테이지는 빌드만 되고 **기동된 적이 없었다.**
처음 띄워보니 두 가지가 바로 깨졌다 — `alembic` 이 이미지에 없어 마이그레이션을
돌릴 수 없었고, 기동 로그에 예외가 섞여 나왔다. 배포 당일에 알았을 결함이다.

**2. ADR-016 이 이 작업을 예고해뒀다.** 그 ADR 의 되돌리는 조건에 이렇게 적혀 있다.

> **배포하면 7번이 강제된다.** `/metrics` 를 막지 않으면 경로별 지연·오류율이
> 외부에 공개된다. 배포 대상이 정해질 때 함께 다룬다.

**3. 쿠버네티스를 어떻게 할지 정해지지 않았다.** ADR-001 은 "EKS 대비 운영 부담이
낮다"는 이유로 ECS Fargate 를 골랐다. 그런데 쿠버네티스를 **직접 다뤄본 경험**은
이 프로젝트의 목적(서버·클라우드 직무 지원 증빙) 안에서 별개의 가치가 있다.
배포 대상 선택과 학습 경험은 같은 질문이 아니다.

여기서 세 가지 선결 조건이 공통점을 가진다. ★ **셋 다 열린 채로 배포해도
아무것도 깨지지 않는다.** 서비스는 멀쩡히 응답하고 화면도 정상이다. 그래서 사람이
알아채지 못한다 — ADR-013 이 다룬 "선언했지만 집행되지 않는" 것과 같은 모양이다.

## 선택지

### 1. 쿠버네티스를 어디서 접하는가

비용은 전부 서울 리전(`ap-northeast-2`) **AWS 공개 가격표 조회값**이다
(2026-11-19 조회, `pricing.us-east-1.amazonaws.com/offers/v1.0/aws/...`).
월 환산은 730시간 기준이다.

#### A안: EKS 로 배포한다

- 장점: 실물 쿠버네티스를 운영한다. IAM·IRSA·ALB 컨트롤러·노드 스케일링까지
  전부 겪는다. "써봤다"의 깊이가 가장 깊다.
- 단점:
  - **컨트롤 플레인만 시간당 $0.10 = 월 $73.** 워커(Fargate 또는 EC2)는 별도다.
  - ADR-001 을 뒤집는다. 되돌리는 조건에 해당하는 사건이 없었는데 뒤집는 것이다.
  - ECS 도 하려면 **배포를 두 벌** 만든다. Terraform 모듈도 두 벌이다.

#### B안: ECS 만 하고 쿠버네티스는 하지 않는다

- 장점: 비용 0. 집중이 흐트러지지 않는다.
- 단점: 쿠버네티스 경험이 남지 않는다.

#### C안: ECS Fargate 로 배포하고, **같은 앱을 로컬 kind 매니페스트로도 올린다**

- 장점:
  - 비용 0. 클러스터가 노트북 안에 있다.
  - ★ **같은 앱의 두 구성을 비교한 기록**이 남는다. "ECS 를 골랐다"보다
    "둘을 만들어보고 ECS 를 골랐고 차이가 이것이었다"가 강한 증빙이다.
  - `Deployment`/`Service`/`ConfigMap`/`Secret`/`CronJob` 이 ECS 의 태스크 정의·
    서비스·SSM 파라미터·EventBridge 와 **어디서 1:1 이고 어디서 어긋나는지**를
    손으로 확인한다.
- 단점:
  - kind 는 **클라우드 운영을 겪지 않는다.** IAM 연동, 로드밸런서 프로비저닝,
    노드 오토스케일링, 영속 볼륨의 실제 동작이 전부 빠진다.
  - 매니페스트를 유지해야 한다. 앱이 바뀌면 두 곳을 고친다.

#### D안: EKS 를 하루만 올리고 destroy 한다

- 장점: 하루면 컨트롤 플레인 $2.4 + 워커. 실물을 만진다.
- 단점: 하루는 운영 경험이 아니다. 그리고 그 하루를 위해 Terraform 모듈을
  두 벌 유지한다 — 비용은 싸지만 **유지 부담은 A안과 같다.**

### 2. 속도 제한을 어디에 두는가

#### E안: ALB + AWS WAF 의 rate-based rule

- 장점:
  - 요청이 **앱에 닿기 전에** 거부된다. Fargate vCPU 를 쓰지 않는다.
  - 운영 표준이다.
- 단점:
  - ★ **테스트할 수 없다.** 배포하지 않으면 동작을 확인할 방법이 없고,
    확인은 "배포하고 때려본다" 뿐이다. 이 프로젝트가 반복해서 피해온 방식이다.
  - WAF 는 웹ACL·규칙·요청에 각각 과금이 붙는다.
  - 로컬에 ALB 가 없으므로 **로컬에서는 제한이 아예 없다.** 즉 제한이 있는
    환경과 없는 환경이 갈린다.

#### F안: 앱 안에 판정기를 둔다

- 장점:
  - ★ **시계도 네트워크도 없이 경계를 전부 집을 수 있다.** 저장소를 끼워 넣으면
    한도 직전·정확히·직후, 창 만료, 저장소 장애를 단위 테스트로 검증한다.
  - 로컬과 운영이 **같은 코드 경로**를 쓴다.
  - 스코프별 한도(읽기 60/분, 계산 20/분)를 애플리케이션 지식으로 정한다.
    ALB 는 경로가 비싼지 싼지 모른다.
- 단점:
  - 요청이 **앱까지 도달한 뒤** 거부된다. 대량 공격은 그대로 Fargate 를 쓴다.
  - 저장소가 필요하다. 프로세스 메모리로 하면 워커 수만큼 한도가 곱해진다.
  - 코드와 테스트가 늘어난다.

### 3. `/metrics` 를 어떻게 막는가

#### G안: ALB 리스너 규칙으로 `/metrics` 를 차단한다

- 장점: 애플리케이션이 모른다. 설정 한 줄이다.
- 단점:
  - **Prometheus 도 같이 막힌다.** 같은 ALB 를 지나면 구분할 방법이 호스트
    헤더나 소스 IP 뿐이고, 둘 다 Terraform 에만 존재하는 사실이 된다.
  - E안과 같은 문제 — 테스트할 수 없다.

#### H안: 앱이 Bearer 토큰을 검사한다

- 장점:
  - 인증 경로가 **코드 안에 있어 테스트된다.**
  - ★ **로컬에서도 켤 수 있다.** 그러면 인증 경로가 매일 돈다.
  - ALB 를 거치지 않는 경로(태스크 간 직접 스크랩)에서도 유효하다.
- 단점:
  - 토큰을 운영·로컬 양쪽에 배포해야 한다.
  - 앱이 인증을 알게 된다. 지금까지 인증이 없던 서비스다.

### 4. 시크릿을 어디에 두는가

#### I안: SSM Parameter Store (`SecureString`)

- 장점: **표준 파라미터는 무료다.** ECS 태스크 정의의 `secrets` 가 직접 읽는다.
  KMS 기본 키를 쓰면 키 비용도 없다.
- 단점: 자동 로테이션이 없다. 손으로 바꾼다.

#### J안: AWS Secrets Manager

- 장점: 자동 로테이션, RDS 와의 통합.
- 단점: **시크릿당 월정액 + API 호출 과금.** 로테이션이 필요 없는 단계에서
  쓰는 돈이다.

#### K안: 태스크 정의에 환경변수로 직접 적는다

- 장점: 가장 간단하다.
- 단점: **태스크 정의는 콘솔과 API 로 평문으로 읽힌다.** Terraform state 에도
  남는다. 할 이유가 없다.

### 5. 관측 스택을 배포하는가

#### L안: 배포하지 않는다. 로컬 전용으로 둔다

- 장점: 비용 0.
- 단점: 배포된 서비스의 지표를 볼 수 없다. ADR-016 으로 만든 경보·대시보드가
  **운영에서는 한 번도 쓰이지 않는다.**

#### M안: 인증을 걸고 같이 배포한다

- 장점: 경보·대시보드가 실제로 일을 한다. 배포 후의 지연·오류율을 측정값으로
  남길 수 있다.
- 단점: 비용과 구성이 늘어난다. **Prometheus 가 ECS 태스크를 어떻게 찾는지**가
  새 설계 문제로 생긴다 — 태스크는 재배치되면 IP 가 바뀐다.

### 6. 운영에서 열린 설정을 어떻게 막는가

#### N안: 경고 로그를 남긴다

- 장점: 기동을 막지 않는다.
- 단점: **아무도 안 본다.** 로그에 남은 경고는 로그를 읽는 사람에게만 작동한다.

#### O안: CI 에서 검사한다

- 장점: 배포 전에 걸린다.
- 단점: CI 는 운영 환경변수를 모른다. 검사할 대상이 CI 에 없다.

#### P안: 기동을 거부한다

- 장점: ★ **배포 파이프라인이 멈춘다.** 사람이 반드시 본다.
- 단점: 설정 하나가 비면 서비스가 안 뜬다. 그 거부가 틀렸을 때
  (예: 제한을 의도적으로 끈 구성) 배포가 막힌다.

## 결정

**1번은 C안(ECS + 로컬 kind), 2번은 F안(앱 내부 판정기), 3번은 H안(앱 토큰),
4번은 I안(SSM Parameter Store), 5번은 M안(인증 걸고 배포), 6번은 P안(기동 거부).**

세부 사항:

1. **배포 대상은 ECS Fargate 다.** ADR-001 을 유지한다. 쿠버네티스는 **로컬
   kind 에 같은 앱을 올려 비교**하고, 그 비교 결론을 이 ADR 의 `## 결과` 에 적는다.
   EKS 는 올리지 않는다.

2. **IaC 는 Terraform 이다.** 콘솔로 만든 것은 되돌릴 수 없고 재현할 수 없다.
   ★ `destroy` 후 `apply` 로 같은 것이 올라오는지가 **IaC 가 작동한다는 증거**이고,
   동시에 이 프로젝트의 비용 레버다 — 쓰지 않을 때 내려둘 수 있다.

3. **속도 제한은 스코프별로 다르다.**

   | 스코프 | 한도 | 이유 |
   |---|---|---|
   | 읽기 (`/api/v1/meta/*`) | 60/분 | 화면이 연달아 호출한다 |
   | 계산 (`/api/v1/calc/ev-tune`) | 20/분 | 솔버가 CPU 를 쓴다 |
   | `/health` | **없음** | 로드밸런서가 때리는 경로다. 여기에 한도를 걸면 스스로 내려간다 |

4. ★ **저장소는 갈아끼운다. 운영에서는 Redis 다.** 메모리 저장소는 **프로세스당**
   센다. gunicorn 워커가 2개면 실효 한도가 2배, 태스크가 늘면 더 벌어진다.
   이 한계를 `TestMemoryStoreIsPerProcess` 가 테스트로 기억한다 — 나중에
   "메모리로 충분하지 않나"가 나오면 그 테스트가 답한다.

5. ★ **저장소가 죽으면 통과시킨다(fail-open). 다만 센다.** 막는 쪽을 고르면
   Redis 가 잠깐 흔들릴 때 API 전체가 멈춘다. 가용성을 지키려는 장치 때문에
   가용성을 잃는 건 거꾸로다. 대신
   `pokehelper_rate_limit_store_failures_total` 로 센다 — **"제한이 걸렸다"와
   "저장소가 죽어서 전부 통과했다"는 똑같이 200 을 돌려주므로**, 카운터가 없으면
   구분할 수 없다.

6. ★ **`X-Forwarded-For` 를 조건 없이 믿지 않는다.** 그 헤더는 클라이언트가
   마음대로 적어 보낼 수 있다. 프록시 뒤가 아닌데 믿으면 매 요청 다른 값을 넣어
   제한을 통째로 우회한다. `TRUST_PROXY_HEADERS` 가 켜졌을 때만 보고, 체인이면
   맨 앞을 쓴다.

7. **토큰 비교는 `secrets.compare_digest` 다.** `==` 는 다른 글자를 만나면 바로
   끝나서 응답 시간으로 토큰을 한 글자씩 알아낼 수 있다.

8. ★ **`/metrics` 토큰을 로컬에서도 켠다.** 끄면 인증 경로가 배포 전까지 한 번도
   돌지 않고, **처음 도는 곳이 운영**이 된다. 로컬 Prometheus 는
   `credentials_file` 로 인증한다. 토큰 파일(`dev-metrics-token`)은 커밋한다 —
   이미 커밋된 `devpassword` 와 같은 지위의 로컬 개발값이다.

9. **운영 기동 거부 조건은 셋이다.** `METRICS_TOKEN` 이 비었거나,
   `RATE_LIMIT_BACKEND` 가 `memory` 인데 제한이 켜져 있거나, `CORS_ORIGINS` 에
   `localhost` 가 남아 있으면 `InsecureProductionConfigError` 로 기동을 거부한다.
   **개발 환경은 검사하지 않는다** — 개발을 막는 가드는 결국 우회된다.

10. **예외 계층 베이스가 넷이 됐다.** `ConfigError` 를 `app/core/exceptions.py` 에
    추가했다. ruff N818 과 `test_exception_layering.py` 가 새 예외를 바로 잡았고,
    규칙을 굽히는 대신 베이스를 늘렸다.

## 포기한 것

- ★ **실물 쿠버네티스 운영 경험.** kind 는 IAM 연동, 로드밸런서 프로비저닝,
  노드 오토스케일링, 실제 영속 볼륨을 겪지 않는다. "쿠버네티스 매니페스트를
  작성하고 같은 앱을 두 방식으로 올려봤다"까지가 이 선택으로 얻는 전부이고,
  "EKS 클러스터를 운영했다"는 **얻지 못한다.** 숨기지 않고 그대로 적는다.
- **ALB·WAF 수준의 방어.** 앱 내부 제한은 요청이 앱까지 도달한 뒤 거부한다.
  즉 **대량 요청은 그대로 Fargate vCPU 를 쓴다.** 429 를 돌려주는 비용도 비용이다.
- **사용자·API 키 단위 제한.** 지금은 IP(또는 프록시 뒤의 전달된 IP) 기준이다.
  CLAUDE.md 7장이 적어둔 "사용자별 일일 호출 한도"는 **미구현**이고, 로그인이
  없으므로 지금 구현할 수도 없다. NAT 뒤의 여러 사용자는 한 바구니로 센다.
- **고정 창(fixed window)의 경계.** 창이 바뀌는 순간 직전·직후에 몰아 보내면
  순간적으로 한도의 2배가 통과한다. 슬라이딩 윈도우나 토큰 버킷이 아니다.
  한도의 목적이 비용 보호라서 받아들인다.
- **시크릿 자동 로테이션.** SSM 은 손으로 바꾼다.
- **`/metrics` 의 세분화된 권한.** 토큰 하나뿐이고 읽기 전용 구분이 없다.
- **Grafana 로컬 비밀번호.** 여전히 `admin/admin` 이다. 필수 변수 가드를
  넣었더니 **compose 의 변수 보간이 파일 전체에서 한 번에** 일어나 Grafana 와
  무관한 `docker compose exec backend` 까지 전부 실패했다. 가드를 없앤 게 아니라
  **자리를 옮겼다** — 강제는 배포 경로(9번)에 둔다.

## 되돌리는 조건

- **429 가 전체 요청의 의미 있는 비율이 되면 ALB·WAF 를 앞에 둔다.** 판단 기준은
  `pokehelper_rate_limit_rejected_total / http_requests_total` 이다. 앱이
  거부하느라 CPU 를 쓰는 상태가 측정되면 E안으로 옮긴다.
- **`pokehelper_rate_limit_store_failures_total` 이 0 이 아니게 되면** fail-open
  정책을 다시 본다. 지금 열어둔 이유는 "Redis 장애가 드물다"는 가정이고,
  그 가정이 깨지면 전제가 바뀐다.
- ★ **LLM(Phase 4)을 붙이면 IP 기준 제한으로는 비용을 못 막는다.** 토큰 비용이
  요청당 발생하므로 사용자 단위 식별이 필요해진다. 그때 로그인과 함께 다시 본다.
- **시크릿이 10개를 넘거나 로테이션 요구가 생기면** Secrets Manager(J안)로 옮긴다.
- **kind 비교에서 ECS 로 해결되지 않는 요구가 드러나면** EKS 를 다시 본다.
  구체적으로: 태스크 간 복잡한 의존 순서, 사이드카 간 공유 볼륨, 또는 ECS 가
  표현할 수 없는 배치 스케줄링이 필요해지는 경우다.
- **기동 거부(9번)가 정당한 구성을 막으면** 조건을 좁힌다. 지금 이미 한 번
  좁혔다 — 제한을 끈 구성에서는 `RATE_LIMIT_BACKEND` 를 검사하지 않는다.
