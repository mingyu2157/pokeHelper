# ADR-004: 별도 NoSQL 없이 PostgreSQL 단일 + JSONB 하이브리드

- 상태: 채택 (2026-09-20)
- 관련: Phase 2, `DEVELOPMENT_GUIDE` 4장, `CLAUDE.md` 2장
- 기록: 소급 작성 (2026-11-03)
- 관련 ADR: 데이터 파이프라인 스택은 [ADR-006](006-data-pipeline-stack.md)에서 따로 다룬다

## 맥락

이 서비스의 데이터는 성격이 뚜렷하게 세 덩어리로 갈린다.

| 그룹 | 테이블 | 출처 | 변경 빈도 | 스키마 |
|---|---|---|---|---|
| 마스터 | `pokemon`, `moves`, `abilities`, `items`, `pokemon_learnset` | 우리가 직접 시드 | 레귤레이션/패치 때만 | 고정 |
| 메타 통계 | `meta_snapshots`, `pokemon_meta` | 외부 API 수집 | 매일 | **가변** |
| 사용자 | `users`, `teams`, `team_members` | 사용자 입력 | 수시 | 고정 |

마스터와 사용자 그룹은 관계형이 명확하다. `pokemon_learnset` 같은 다대다 중간 테이블이 필수고
("이 포켓몬이 이 기술을 배울 수 있는가"를 검증해야 파티 저장 시 불가능한 조합을 막을 수 있다),
파티-멤버-포켓몬-기술이 전부 참조 무결성을 요구한다.

반면 메타 통계는 다르다. 채용률 구조가 외부 API의 응답 형태에 종속되고, 엔드포인트와 필드가
예고 없이 바뀔 수 있다([ADR-002](002-data-source.md) 참조). 고정 컬럼으로 못 박으면 상대가
필드를 하나 추가할 때마다 마이그레이션을 돌려야 한다.

여기서 흔한 선택지가 **"관계형은 Postgres, 가변 문서는 MongoDB"** 로 저장소를 쪼개는 구성이다.

## 선택지

> ⚠️ 이 절은 2026-11-03에 소급 정리했다. 결정 당시 아래 대안을 실제로 비교한 기록은 없다.
> `## 근거` 참조.

### A안: PostgreSQL 단일 + JSONB
- 장점:
  - 저장소가 하나다. 백업·마이그레이션·모니터링·접속 설정이 전부 한 벌이다.
  - 마스터 ↔ 메타 통계를 **한 쿼리에서 조인**할 수 있다. "사용률 상위 30마리의 종족값"처럼
    두 그룹을 섞는 질의가 실제로 핵심 기능에 쓰인다.
  - JSONB는 GIN 인덱스를 걸 수 있어 문서 내부 조회도 가능하다.
  - 트랜잭션이 한 곳에서 끝난다. 수집 적재와 메타데이터 갱신이 원자적으로 묶인다.
- 단점:
  - JSONB 내부는 DB가 스키마를 강제하지 않는다. 검증 책임이 애플리케이션으로 넘어온다.
  - 문서 지향 질의 문법이 MongoDB보다 번거롭다.
  - 문서가 아주 커지면 전용 문서 DB보다 불리할 수 있다.

### B안: PostgreSQL + MongoDB (폴리글랏 퍼시스턴스)
- 장점:
  - 가변 문서를 본래 용도에 맞는 저장소에 둔다.
  - 포트폴리오에서 다중 저장소 운영 경험을 보여줄 수 있다.
- 단점:
  - **1인 운영에서 비용이 두 배가 된다** — 로컬 컨테이너 추가, 백업 2종, 마이그레이션 2종,
    운영 환경에서 RDS + DocumentDB 요금.
  - 마스터와 메타를 조인할 수 없다. 애플리케이션에서 두 번 조회해 합쳐야 한다.
  - 두 저장소에 걸친 일관성을 직접 관리해야 한다.

### C안: 전면 MongoDB
- 장점: 저장소가 하나로 유지된다.
- 단점: `pokemon_learnset` 같은 다대다 참조 무결성을 DB가 보장하지 못한다.
  "배울 수 없는 기술이 든 파티"를 막는 게 제품 요구사항이라 치명적이다.

## 결정

**PostgreSQL 16 단일.** 가변 스펙은 `pokemon_meta.data` JSONB 컬럼으로 흡수한다.
별도 NoSQL을 두지 않는다. 캐시(Redis)는 저장소가 아니라 휘발성 캐시로만 쓴다.

## 근거

(2026-11-03, 개발자 본인 기록)

**별도 NoSQL을 붙일지 비교했는가**
하지 않았다. MongoDB를 붙일지 고민하다 안 붙인 게 아니라, 쪼갤 생각 자체를 하지 않았다.
Postgres 단일은 **비교해서 고른 결정이 아니라 기본값을 유지한 것**에 가깝다.

**가변 문서에 대해 생각하고 있던 것**
저장소를 나누는 쪽이 아니라, 현재 공부 중인 데이터 엔지니어링 강의(카프카·스파크·에어플로)의
지식을 적용해 실시간 데이터 파이프라인을 붙이는 쪽을 생각하고 있었다.
실제 운영 효율보다는 **학습과 경험**이 동기였다. → [ADR-006](006-data-pipeline-stack.md)

**운영 복잡도를 고려했는가**
고려하지 않았다. 저장소를 둘 쓸 때의 백업·마이그레이션·요금 부담은
2026-11-03 대화에서 처음 검토했고, 그 결과 단일 저장소 유지가 타당하다고 판단했다.

## 포기한 것

- **스키마 강제력.** JSONB 내부는 DB가 막아주지 않는다. 외부 API 필드가 바뀌어도 적재는 성공하고,
  깨진 건 조회 시점에 드러난다. 따라서 **적재 전 정규화·검증이 애플리케이션 책임**이 된다.
  `CLAUDE.md` 8-6의 "사이트별 필드명을 DB에 그대로 넣지 않는다"가 이 책임의 구현이다.
- **폴리글랏 퍼시스턴스 경험.** 포트폴리오에서 다중 저장소 운영을 보여줄 기회를 포기했다.
  다만 근거 없이 저장소를 늘리는 건 오히려 감점 요인이라, 이 손실은 크지 않다고 본다.
- **문서 질의 표현력.** 복잡한 중첩 문서 집계가 필요해지면 SQL + JSONB 연산자로 쓰기 번거롭다.

## 되돌리는 조건

- **JSONB 질의 성능 한계**: `pokemon_meta` 조회가 GIN 인덱스로도 목표 응답 시간을 못 맞추면
  해당 테이블만 분리를 검토한다. 전면 이전이 아니다.
- **스키마 붕괴 빈발**: 외부 API 필드 변경으로 적재 깨짐이 반복되면, 저장소 문제가 아니라
  정규화 계층 설계 문제이므로 **DB를 바꾸기 전에 `ingestion/` 을 먼저 고친다.**
- **사용자 이벤트 데이터 등장**: Phase 7의 선출 훈련·복기 코치가 대량 이벤트를 만들면
  그 데이터는 성격이 다르다. 그때 별도 저장소를 재검토한다 → [ADR-006](006-data-pipeline-stack.md)

**데이터 증가로 인한 분리 압력은 구조적으로 작다.** [ADR-002](002-data-source.md)의 라이선스
조건이 영구 미러·아카이브를 금지하므로 메타 스냅샷을 무한 누적할 수 없다. 보존 기간을 둔 캐시로
설계해야 하고, 그 결과 테이블이 무한정 커질 일이 없다. 외부 제약이 뜻하지 않게 저장소 선택의
리스크를 줄여주고 있다.
